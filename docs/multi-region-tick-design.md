## 0. 结论

1. **分两层。** 外层叫“岛”，就是总设计稿里的 region：一片连在一起的已加载区块，岛和岛之间隔着没加载的区块，各走各的时钟。内层叫“单元”：一个岛里按“哪些区块真的有方块活动”划出来的小块，同一个岛里的单元齐步走、并行执行。
2. **单元是这份设计新增的。** 总设计稿只有岛。视距 10 时两名玩家相距不到约 530 格就一定在同一个岛里，岛内的方块逻辑全是串行，所以玩家聚在一起时（最常见的情况）多区域带不来任何并行。单元补的就是这一块。
3. **单元的粒度是单个区块。** 有活动的区块加一圈缓冲区块归一个单元；机器长到哪个区块，就只把那个区块纳进来。没有活动的区块不属于任何单元。
4. **越界不会晚一刻。** 单元执行到一半要碰自己范围以外的东西时，它原地等，等其他单元都跑完再接着跑。结果仍在同一刻生效，只是和别的单元之间的先后与原版可能不同。
5. **精确模式保留，只当测试基准。** 生产路径不为它让步。单元并行的正确性靠“同一场景，并行和精确两种跑法逐刻比对世界状态”来证明。
6. **现在没有证据说明它值得做。** 现有压测里一刻最多 4–7 ms（200 人），远没到 50 ms 的预算，而且耗时最多的是随机刻、收包、实体同步，不是红石。所以第一步是造出重负载场景并测量，数字不够就先不做后面的步骤。见第 7 节。

## 2. 现状

`[事实]`，来源写在每条后面。

- **一条世界线程、一个 `Region`。** 没有主控线程，没有 tick 线程池（总设计稿第 16 节第 4、5、6 步都是“没做”）。
- **一刻的阶段顺序**（`crates/mc-bamboo-game/src/world.rs` 的 `Phase`）：`Inbox` → `Delivery` → `LightUpdates` → `WeatherAndTime` → `ScheduledTicks` → `RandomTicks` → `BlockEvents` → `Entities` → `BlockEntities` → `PlayerMisc` → `Views` → `BlockChangeBroadcast` → `EntitySyncAndTracking` → `ChunkSending` → `Flush` → `TickTail`。
- **带位置的状态是全 region 一张表，但已有按单元的拆合接口。** 计划刻、方块事件、方块实体、红石记忆、容器等保持全局形状；第 1 步实测否决了按区块分存（4.8），改为按单元存：现在只有一个单元，`split_off` / `absorb` 给第 3 步用，另有忙区块活动索引。
- **实体已经能并行算**，开关是 `bamboo.toml` 的 `entity_threads`；现在只有下落方块、点燃的 TNT、掉落物三种实体。
- **一刻现在花多少**（`docs/profiling.md` 第一份基线，超平坦世界，假玩家）：

  | 场景 | tick p50 / p95 (ms) | 耗时最多的三阶段（平均 ms） |
  |---|---|---|
  | 50 人扎堆 | 1.5 / 3.5 | 收包 0.62，随机刻 0.62，发区块 0.27 |
  | 200 人扎堆 | 4.2 / 6.6 | 收包 1.34，实体同步和追踪 1.30，随机刻 1.15 |
  | 20 人飞行 | 2.6 / 4.6 | 随机刻 2.13，发区块 0.43，收包 0.23 |

  这些场景里没有红石机器，也没有生物。真实地形接进来之后的同一组数字**还没量过**。
- **原版的几个数值**（对 26.3 的 jar 用 `javap` 核对）：
  - 活塞一次最多推 12 格：`PistonStructureResolver.MAX_PUSH_DEPTH = 12`。
  - 方块事件在同一刻里循环到队列空为止：`ServerLevel.runBlockEvents` 反复 `removeFirst` 直到 `isEmpty`。所以活塞连锁可以在一刻内走很多步。
  - `ServerChunkCache.tickChunks` 只打乱刷怪用的区块列表（`shuffleSpawningChunks`）。

## 3. 两层结构

```text
维度
└─ 岛（= 总设计稿的 region）      连通的已加载区块；岛之间隔着未加载区块；各走各的时钟
   ├─ 单元 A  忙区块 + 一圈缓冲    ┐
   ├─ 单元 B                      ├ 方块侧的阶段并行执行，齐步走
   ├─ 单元 C                      ┘
   └─ 其余区块                    没有方块活动，只有随机刻和实体
```

| | 岛 | 单元 |
|---|---|---|
| 按什么划分 | 已加载区块的连通性（由玩家的票决定） | 方块活动 |
| 边界 | 未加载的区块 | 已加载但安静的区块 |
| 时钟 | 各走各的 | 同一个岛里齐步走 |
| 并行什么 | 整刻 | 计划刻、方块事件、方块实体三个阶段 |
| 解决什么 | 玩家分散在各处 | 玩家聚在一起、附近有多台机器 |
| 来源 | 总设计稿 6.1–6.6 | 本稿新增 |

**为什么单元必须齐步走** `[推导]`：单元之间隔着的是已加载的区块，这些区块里有实体、有随机刻，方块状态随时被两边读到。如果两个单元的时钟不同，边界上的一格水、一个掉落物就没有确定的“现在”。岛之间可以不同步，是因为中间什么都没加载。

**这是对“region 各走各的时钟”的细化**：各走各的时钟只在岛之间成立。同一个岛里卡了，整个岛一起慢。

## 4. 单元

### 4.1 定义

- **忙区块**：满足下面任意一条的已加载区块。
  1. 最近 `quiet_ticks` 刻内**排入过**方块或流体计划刻（默认 100 刻，也就是 5 秒）；
  2. 最近 `quiet_ticks` 刻内排入过方块事件；
  3. 有醒着的方块实体（休眠的不算，见总设计稿 9.5）；
  4. 最近 `quiet_ticks` 刻内满足过第 3 条。

  第 1 条用「最近排入过」而不是「现在有还没执行的刻」：第 7 节第 1 步的实测表明，
  精确维护待执行计数会让计划刻热路径慢 13%–20%；而时钟、中继器、流体这类持续活动
  的东西每几刻就排一次刻，结果一样能一直算忙。唯一漏掉的是延迟超过 `quiet_ticks`
  的单发刻，见 4.2 的尾段说明。
- **缓冲圈**：忙区块周围 `halo` 圈区块（默认 1），不含忙区块本身。
- **单元**：忙区块按“切比雪夫距离 ≤ 2 × `halo`”连成的每个连通块，加上它的缓冲圈。
- 其余已加载区块不属于任何单元，叫**安静区块**。

有没有玩家、有没有实体都不影响一个区块忙不忙，理由见 4.5。

**不变量** `[推导]`：不同单元的范围（忙区块加缓冲圈）互不重叠。`halo = 1` 时，两个单元的忙区块之间至少隔 2 个区块；隔得更近的在划分时已经连成一个单元了。

**粒度的例子**：一台机器占 3 个区块，后来多建了一段伸进第 4 个区块。第 4 个区块一有计划刻或醒着的方块实体就变成忙区块，单元多出这 1 个区块和它新带来的缓冲区块，别的不动。

### 4.2 一刻怎么跑

一个岛的一刻，顺序和现在的 `Phase` 一样，只标出变化的部分：

| 阶段 | 执行方式 |
|---|---|
| 收包、交付、光照、天气和时间 | 串行，不变 |
| **划分** | 串行。按 4.1 更新忙区块和单元，只处理这一刻变了的区块 |
| **计划刻** | 各单元并行，然后尾段（4.3） |
| 随机刻 | 先串行；以后可以着色并行（4.6） |
| **方块事件** | 各单元并行，然后尾段 |
| 实体 | 整个岛“并行算、按顺序落地”，不变 |
| **方块实体** | 各单元并行，然后尾段 |
| 玩家杂项到 flush | 不变 |

每个并行阶段里，一个单元只执行**位置在自己忙区块里**的触发（一次计划刻、一个方块事件、一个方块实体 tick），可以读写自己范围内的所有区块。

**到期的刻不在任何单元的忙区块里时**（只有延迟超过 `quiet_ticks` 的单发刻会这样），在串行的尾段执行，和越界走同一条路；它排出的新刻会把所在区块标成最近活动过，下一刻就纳入划分。结果仍在同一刻生效，不会晚一刻。

**和原版的关系** `[推导]`：原版在整个世界里按一个全局顺序执行这些触发。两个单元的范围不重叠，所以只要没有越界，一个单元里的触发读不到也写不到另一个单元的东西，全局顺序怎么交错都得到同样的方块状态；单元内部的相对顺序照原版保留。剩下的差别只有随机数（4.7）。

**玩家的操作不受影响**：放方块、破坏方块在收包阶段串行执行，那时没有单元在跑。实体对方块的影响（下落方块落地、TNT 爆炸、物品进漏斗、踩压力板）在实体落地阶段串行执行，也没有单元在跑。所以爆炸半径、实体速度这些都不影响缓冲圈要多宽。

### 4.3 越界：原地等，到尾段接着跑

一个单元在并行阶段里遇到下面两种情况，叫越界：

1. 要读或写自己范围以外的区块；
2. 轮到执行的触发不在自己的忙区块里。这只可能是本刻新产生的方块事件落在了缓冲圈里，或者是 4.2 说的延迟超过 `quiet_ticks` 的单发刻。

处理办法：**这个单元的线程原地等待**。等所有没越界的单元跑完这个阶段，越界的单元按单元编号依次恢复，每次只有一个在跑，这时它可以访问整个岛。全部跑完，这个阶段才结束。这一段叫**尾段**。

- 不需要回滚，也不需要把触发拆成两半：线程只是暂停，恢复后从停下的地方接着执行。
- 结果是确定的 `[推导]`：一个单元在越界之前只碰自己的范围，所以它在哪里越界和线程调度无关；尾段按编号串行。同样的输入，任何线程数都得到同样的结果。
- 和原版的差别：越界的单元剩下的触发，排在了别的单元这一阶段全部触发之后。原版里它们可能交错。**仍在同一刻生效，不会晚一刻。**
- 越界过的单元和它碰到的区块，在下一刻的划分里并成一个单元（碰到的区块记为忙区块）。

**缓冲圈要多宽** `[推导]`：一次触发能走多远决定越界有多频繁。

| 机制 | 一次触发的水平范围 | 依据 |
|---|---|---|
| 普通方块更新、流体、火 | 1–2 格 | 更新邻居和邻居的邻居 |
| 活塞 | 12 格再加邻居更新 | `MAX_PUSH_DEPTH = 12` `[事实]` |
| 红石线 | 15 格再加邻居更新 | 信号强度 15；具体的更新范围 UNVERIFIED |
| 动力铁轨 | 8 格左右 | UNVERIFIED |

忙区块最靠边的一格离缓冲圈外沿是 16 格。活塞够用；红石线从最边上出发、正好拉满 15 格时可能差一两格。所以默认用 1 圈，越界靠尾段兜住，同时统计越界次数；统计出来太频繁再改成 2 圈。这个数是配置项。

### 4.4 合并和拆分

- 单元不是长期存在的对象，每一刻的划分阶段按忙区块重新得出。“合并”就是两片忙区块连上了，“拆分”就是中间的区块不再忙。
- 划分要做成增量的：只有忙状态变了的区块才触发局部重算。目标是没有变化的那一刻，划分的耗时接近 0。
- **防止反复拆合**：忙区块要安静满 `quiet_ticks` 刻才退出（4.1 第 4 条）。时钟电路一直有没到期的计划刻，所以一直是忙的，不会抖动。
- **单元太小就不并行** `[判断]`：把一个只花几微秒的单元交给另一条线程，比直接算还慢。每个单元记一个最近耗时的滑动平均，只有至少两个单元各自超过门槛（初值 50 微秒，实测后定）时才并行，否则这个阶段整体串行跑。和红石缓存“只在划算的触发点生效”是同一个思路。

### 4.5 实体

**实体不参与单元的划分。** `[推导]` 生物接进来之后，玩家周围几乎每个区块都有动物或怪物；如果有实体就算忙，所有区块会连成一个单元，细粒度就没有了。实体的并行由总设计稿第 8 节负责：整个岛一起并行算，再按顺序落地。

以后落地阶段成为瓶颈时，可以按单元分组并行落地。现在不做，总设计稿第 17 节第 3 条的测量说它在现有负载里只占 0.002 ms/刻。

### 4.6 随机刻

随机刻在每个 ticking 区块里都有，现有基线里它是耗时最多的阶段之一，所以值得单独考虑。它不适合放进单元，因为它不分忙不忙、到处都有。

候选做法 `[判断]`：把岛按 2×2 个区块切成块，块按 2×2 的图案染成 4 种颜色，同色的块之间隔 2 个区块。4 种颜色依次执行，每种颜色内部并行。一次随机刻的影响范围在 1 个区块以内（树苗长成树是最大的一类，UNVERIFIED），同色的块互不干扰；超出的用 4.3 的办法等到这一色的尾段。

先不做，原因有两条：它改变了区块之间随机刻的先后和随机数的分配；真实地形下随机刻占多少还没量。第 7 节把它放在单独的一步，测量之后再决定。

### 4.7 随机数和顺序号

- 原版一个世界只有一个随机源，所有触发按执行顺序从里面取数。单元并行之后做不到这一点。每个单元用自己的随机源，按（世界种子、当前刻、单元里坐标最小的忙区块）派生。尾段和串行阶段用岛的随机源。
- 结果：方块逻辑里用到随机数的地方（例如发射器选哪一格、活塞音效的音高）和精确模式取到的数不同。分布相同，具体值不同。写进差异清单。
- 计划刻的排序键里有一个全局递增的顺序号。各单元并行时没法共用一个计数器，改成“单元内的顺序号”加“产生它的单元编号”。它只影响两个当时互相独立的单元以后合并时，同一刻、同优先级的计划刻谁先谁后。原版每刻最多执行 65536 个计划刻的上限，改成按岛统计（UNVERIFIED：上限的具体取法，移植时读字节码）。

### 4.8 数据怎么放 `[事实：第 1 步实测后修改]`

**结论：带位置的状态按「单元」存，不按「区块」存。** 这是对初稿（第 7 节第 1 步
「按区块分存」）的修改，依据是第 1 步的三轮实测，数字见
`docs/performance-optimizations.md` 第 13 节。

- 单元并行时，每个单元要的是「自己范围内的触发，按全局顺序排好的一条队列」，
  并且能往里排新的触发而不碰别的单元。按 4.1，**有排入过计划刻的区块一定是
  忙区块**，而单元是半稳定的（要安静 `quiet_ticks` 刻才退出），所以一棵队列
  按单元放就够了：单元合并时两棵队列并起来，拆分时按区块集合拆开。合并拆分
  只在拓扑变化时发生，不在每刻热路径上。
- 现在只有一个单元（整个 region）。所以**所有带位置的表保持原来的全局形状**：
  `BlockTicks` 一棵全局 `BTreeMap<TickOrder, …>`，`BlockEvents` 一条全局队列，
  `BlockEntities` 一套全局 ticker 槽位和运行顺序，`RedstoneMemory` 六张按位置的
  表和按时刻升序的火把抖动表，游戏层的 `containers` / `block_items` /
  `command_blocks` / 讲台的书四张 `BTreeMap<BlockPos, _>`。热路径、遍历顺序
  和发包顺序天然不变。
- 第 7 节第 1 步交付的是**拆合接口**和**活动索引**，不是把表切碎：
  - `BlockTicks::split_off(chunks, unit)` / `absorb`、`BlockEvents::split_off` /
    `absorb`、`BlockEntities::split_off` / `absorb`、`RedstoneMemory::split_off` /
    `absorb`，以及游戏层 `Region::split_off_unit` / `absorb_unit`。每一类都有
    随机拆合测试和「按区块再按位置」的改坏确认对照。
  - `TickOrder` 和方块实体 ticker 的 ordinal 用单元编号占高位，拆出去那份
    新登记的号不会和别的单元撞；合回来后全局顺序确定。
  - `BlockEvents` 和 `RedstoneMemory` 的火把抖动表各记一份全局入队序号，
    `absorb` 按序号稳定归并，同刻先后和从没拆过逐条相同。
  - `BlockEntities` 的关注关系可以跨区块：两边都保留完整登记，
    `watchers_cross_chunks` 报告「有跨界关注」这个事实。下一步划单元时必须把
    两侧合成一个单元，否则关注者收不到另一边的叫醒。
  - 活动索引：计划刻的 `drain_touched_chunks` / `last_scheduled`（并进已有的
    存盘标脏，一次哈希查表同时更新两样）、方块事件的 `drain_touched_chunks` /
    `chunk_has_queued`、方块实体的 `awake_chunks()`；游戏层 `Region::busy_chunks()`
    把三者并起来。全都不扫大表。
- 卸载和存盘仍走原来的按区块装盒 / x 带扫描（第 4.2 节的 `RegionColumn`），
  那不在 tick 热路径上。`EntityStore` 和 `entity_tracking` 的玩家配对仍留给第 5 步。

**为什么否决了按区块存**（三轮实测，详见性能文档第 13 节）：

| 尝试 | 结果 |
|---|---|
| 每区块一份计划刻队列 + 六种不同的队头/归并结构 | 100 万条刻在 16 / 1024 / 4096 个区块里，排入加执行中位数比一棵全局队列慢 19%–99% |
| 游戏层四张表改成「每区块一份小 BTreeMap」 | 1 万个箱子的每刻全表遍历从 0.021 ms 变 2.085 ms（约 100 倍），按位置查反而快 61% |

根因是排刻 / 遍历这些热路径每刻都要走：原来是一次全局树操作，按区块存多出
「算区块 + 哈希查表 + 建/查小表 + 队头或位置归并」。并行带来的收益按第 0 步的
基线本来就不大，付不起这个常数。单元的队列粒度同时满足了「能整份拿走」
和「串行路径不能变慢」。

## 5. 岛

沿用总设计稿 6.1–6.6，不重写。只有两处说明：

1. **总设计稿里说的 region，在本稿里就是岛。** 它的形成规则（4×4 区块的网格、距离 ≤ 2 合并、相距 ≥ 4 持续 10 秒拆分）、“不同岛的已加载区块不相邻”的不变量、离境和到达、全局状态都不变。
2. **岛的时钟各走各的，岛内的单元齐步走**（第 3 节）。

用户说的“按玩家聚集动态合并和拆分”，对应的就是岛这一层：岛由玩家的票决定，玩家走近了合并，走远了拆分。

## 6. 精确模式和差异清单

- 精确模式：每个维度一个岛、不划单元、全部串行、一个随机源。所有 oracle 和探针继续在这个模式下跑。
- 生产路径不为精确模式让步：两种模式共用同一份方块逻辑（都写在 `Level` 接口上），区别只在驱动，所以保留它不需要把逻辑写两遍。

**单元并行相对精确模式的差异**，加进总设计稿第 13 节：

1. 每个单元有自己的随机源（4.7）。
2. 越界的单元，剩下的触发排在同一阶段其他单元之后（4.3）。同一刻内生效。
3. 来自不同单元的计划刻，同刻同优先级时的先后（4.7）。
4. 如果做随机刻着色（4.6）：区块之间随机刻的先后和随机数分配。

没有“晚一刻”的差异。

**怎么测**：

1. **逐刻比对**。同一个场景分别用精确模式和单元并行跑，每一刻比较全部方块状态、方块实体内容、计划刻表。场景选不用随机数的机器（大多数红石电路都是）。做法照搬红石缓存的 `cache_diff`。必须做改坏确认：故意让一个单元读到别的单元的区块，比对要能报出来。
2. **不变量的随机测试**。随机放机器、随机移动玩家，每刻断言“单元的范围不重叠”“并行阶段里没有单元碰到范围以外的区块而没走越界流程”。
3. **线程数无关**。同一场景 1、4、8 条线程，世界状态逐刻相同。
4. 用到随机数的机器只能比统计性质，写明哪些场景属于这一类。

## 7. 实施顺序

每一步单独合并、单独测量。前三步不改变任何可观察的行为。

| 步 | 内容 | 做完能知道什么 | 和世界生成的关系 |
|---|---|---|---|
| 0 | **造重负载场景并测量**：多台机器分散在一个岛里；多人加机器；真实地形下的随机刻。给压测工具加“每个区块在计划刻、方块事件、方块实体三个阶段各花了多少”的统计 | 方块侧的阶段到底占一刻的多少，值不值得做第 3 步 | 不冲突，可以现在做 |
| 1 | **拆合接口和活动索引（做完）**：带位置的状态按单元存而不是按区块存（4.8）；现在只有一个单元，存储形状不变。四类状态各有 `split_off` / `absorb`，加计划刻 / 方块事件 / 方块实体的忙区块活动索引；`Level` trait 不变 | 第 3 步和岛的拆合的前提。实测确认按区块存会让串行路径慢 19%–100 倍，改成了按单元存。oracle 全绿 | 改 `mc-bamboo-blocks` 和 `mc-bamboo-game` 的拆合接口，和世界生成、Director 不重叠 |
| 2 | **忙区块索引和单元划分，只算不用**：每刻算出单元，照常串行执行，同时统计单元个数、大小、划分耗时，以及“如果并行会越界多少次” | 真实场景里能分出几个单元、缓冲圈 1 圈够不够。这一步的数字决定第 3 步做不做 | 不冲突 |
| 3 | **单元并行**：计划刻、方块事件、方块实体三个阶段；尾段；逐刻比对测试 | 多台机器的场景快多少 | 改 tick 主循环，要等世界生成这一批合完 |
| 4 | 随机刻着色并行（4.6），先测再定 | 随机刻阶段快多少 | 同上 |
| 5 | **岛**：主控、tick 线程池、岛的拆合、各自的时钟（总设计稿第 16 节第 4、5 步） | 玩家分散时的并行 | 改 Director 和主循环，冲突最大，放最后 |
| 6 | 广播从推改成拉、实体落地并行 | 多人同屏 | 依赖第 5 步的线程池 |

**为什么先做单元、后做岛** `[判断]`：

- 单元不需要主控线程、不需要各自的时钟、不需要离境和到达，改动面小得多。
- 单元并行可以和精确模式逐刻比对，岛不行（岛之间的先后本来就不固定）。先做能比对的。
- 玩家聚在出生点附近是更常见的情况，这时只有单元有用。

**第 0 步的判断标准** `[判断]`：如果在几个“像真实服务器”的场景里，计划刻、方块事件、方块实体三个阶段加起来不到一刻的三分之一，第 3 步最多把一刻缩短三分之一，这时应该先去做占大头的那一项（可能是随机刻、收包或广播），而不是按这张表往下走。

## 8. 风险

1. **收益可能很小。** 见第 0 节第 6 条。这是最大的风险，所以第 0 步和第 2 步都只是测量。
2. **一台大机器就是一个大单元。** 一片连在一起的红石会合成一个单元，内部仍是串行。这是这类设计的固有限制，Folia 也一样。它需要的是红石缓存这类手段，不是分区。
3. **按区块分存确实让串行路径变慢（已实测，已改方案）。** 第 1 步把四类状态逐个试了一遍：计划刻按区块存让密集 / 中等 / 稀疏三种形状的排入加执行慢 19%–99%（六种队头结构都没救回来），游戏层四张表让 1 万个箱子的每刻全表遍历从 0.021 ms 变 2.085 ms。最终改成按单元存（4.8），串行路径回到基线：三种形状逐对比值中位数 −1.2%/+2.1%、+0.3%/−10.5%、−13.7%/−16.5%，红石线阵列 −3.3%。完整数字和走不通的做法见 `docs/performance-optimizations.md` 第 13 节。
4. **等待的线程占着线程池的名额。** 越界频繁时，尾段会退化成串行再加等待的开销。第 2 步的越界统计就是为了提前知道这一点。
5. **发包顺序。** 各单元并行产生的方块变化、音效、粒子要按确定的顺序汇总后再发，否则同样的输入会发出不同顺序的包。按单元编号、单元内按产生顺序排。
6. **光照。** 并行阶段里改方块会产生光照更新，现在光照队列是全 region 一个。每个单元各攒一份，阶段结束后按单元编号并入。UNVERIFIED：光照传播本身能不能跨出单元范围，要读代码确认。
7. **红石缓存。** 缓存按触发点记录，和单元怎么划分无关，原则上可以直接用；但它现在是全 region 一份，要改成每个单元能并发访问，或者每个单元一份。

## 9. 已经定的四件事

2026-11-16 用户确认，全部照下面写的做。

1. **两层结构**：同一个岛里的单元齐步走，“各走各的时钟”只在岛之间成立。这是对之前决定的细化。
2. **顺序**：先做单元，后做岛（第 7 节）。
3. **越界的处理**：同一刻的尾段里接着跑，先后可能和原版不同，但不晚一刻（4.3）。
4. **精确模式**：保留，只当测试基准（第 6 节）。

另外，第 0、1、2 步和世界生成不冲突。第 0 步只加测量，第 1 步是存储重构，都可以在世界生成收尾的同时开始。
