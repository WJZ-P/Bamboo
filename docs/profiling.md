# 剖析器与压测工具

`mc-bamboo-game/src/profiler.rs` 给世界线程每刻记一份耗时直方图。本文说明怎么打开它、
报告里每一项是什么、怎么用假玩家给服务端加负载，以及第一份基线数据。后面几节按时间顺序
记了区块平面（第 8–10 节）、交付/收回的分配（10.6）和区块计算池（第 11 节）的对比；
`world_dir` 和 `chunk_worker_threads` 都能从压测工具的 `serve` 子命令行给，见第 3 节。

## 1. 打开剖析器

设环境变量 `BAMBOO_PROFILE=<秒>` 后启动服务端。世界创建时读一次，按这个间隔用
`tracing::info!` 打一份报告，打完把样本清零，下一份报告只覆盖之后的那些 tick。
没设、设成 0、负数或解析不了都当成关闭（仍累计但不打印）。

```bash
BAMBOO_PROFILE=10 cargo run --release --bin bamboo
```

`RUST_LOG` 可以调日志级别，默认是 `info`；剖析报告是 `info` 级别的，日志级别调到
`warn` 以上就看不到。报告打在服务端进程的标准输出里。

## 2. 报告里每一项

报告分两段。第一段 `phases (by mean)` 按平均耗时降序列出 `World::tick` 的阶段：
`inbox`（处理入站消息）、`delivery`（Director 信箱泵和区块交付/收回）、
`light_updates`、`weather_and_time`、`scheduled_ticks`、
`random_ticks`、`block_events`、`entities`、`entity_compute`、`entity_commit`、
`block_entities`、`player_misc`、`views`、`block_change_broadcast`、
`entity_sync_and_tracking`、`chunk_sending`、`flush`、`tick_tail`。
每行是 `count`（样本数）、`mean`、`p50`、`p95`、`p99`、`max`，单位 ms。
分位数落在对数直方图的桶下界上，是偏保守的估计；桶在 0..15 ns 是逐纳秒，
之上每个 2 的幂再分 8 份，相对误差不超过 12.5%。

实体阶段按驱动分：精确驱动（默认，`bamboo.toml` 里 `entity_threads = 0`）只记
`entities` 一段，算完立刻落地；并行驱动（`entity_threads ≥ 1`）记
`entity_compute`（只读算阶段）和 `entity_commit`（发布状态、按 uid 升序应用命令、
发效果）两段，`entities` 没有样本。所以报告里有 18 个阶段，但任何一次运行只会有
17 个阶段有样本。**实体并行驱动仍用 `ScopedThreads` 每刻起线程**，剖析数字包含这项开销；
常驻的 `ComputePool` 是区块计算池，只跑区块的 `Decode` / `Generate` / `Save`，不接实体驱动
（`chunk_worker_threads` 控制，见第 11 节）。两处不要混淆。

第二段 `metrics` 里，`tick_total`、`tick_start_lateness` 和
`tick_interval_deviation` 是时间（ms）：

| 名称 | 含义 |
|---|---|
| `tick_total` | `end_tick − begin_tick`，一刻的实际总耗时 |
| `tick_start_lateness` | 实际开始时刻减去调度器给出的应开始时刻；提前醒了记 0 |
| `tick_interval_deviation` | \|相邻两刻**实际起点**的间隔 − 50 ms\|，设计稿 1.2「抖动 < 2 ms」看这一项 |
| `inbound_messages` | 每刻从信箱取出并处理的入站消息数 |
| `online_players` | 每刻开始时的在线玩家数 |
| `due_scheduled_ticks` | 每刻开始时到期的方块/流体计划刻数 |
| `entities` | 每刻开始时的实体数 |
| `chunks_sent` | 每刻写进出站缓冲的区块数；这一刻一个都没发也要记 0 |
| `chunks_delivered` | 这一刻 region 收下的区块数；一个都没收也要记 0 |
| `chunks_reclaimed` | 这一刻 region 交还的区块数；一个都没交还也要记 0 |
| `chunk_latency_us` | 一个区块从进入待发送集合到写进出站缓冲，过了多少微秒（墙上时间） |
| `flush_bytes` | 这一刻 `Links::flush` 交给连接层的全部 `Outgoing` 的未压缩字节数；一个都没有也记 0 |
| `skipped_catch_ups` | 这段时间内放弃追赶的次数（只有累计值，没有直方图） |
| `loaded_chunks` | 这一刻开始时已加载的区块数；无限模式记 0 |
| `parked_chunks` | 这一刻交付/收回之后停放表里的区块数 |
| `compute_in_flight` | 这一刻交付/收回之后已经交给计算池、还没回来的区块任务数（上限是线程数 × 4，存盘不受上限）；内联执行器（`chunk_worker_threads = 0`）恒为 0 |
| `compute_backlog` | 同一时刻宿主手里还没交给计算池的区块任务数（按离玩家的距离补进池子）；内联执行器恒为 0 |

`tick_start_lateness` 量的是「每刻都比计划晚多少」，`tick_interval_deviation` 量的是
「刻与刻之间均不均匀」：睡眠精度带来的固定 4 ms 偏差只会出现在前一项里。
刻间隔偏差的口径是**只统计相邻两刻都按 50 ms 网格正常调度**的那一对
（上一刻睡过、这一刻没在追赶、也没放弃过追赶）：落后时连续跑的刻之间没有睡眠，
间隔由上一刻的耗时决定，量的是完全不同的东西，会把偏差撑成几十毫秒，
所以追赶中的刻既不记样本、也不作为下一对的基准；放弃追赶后重新起步的
第一对同理不记。每份报告打印清零样本时也会丢掉「上一刻」的基准，
所以跨报告的第一对不算样本。

`chunk_latency_us` 是墙上时间：区块进入 `pending` 时记 `Instant`，写进出站
缓冲时取经过的微秒数，不再是「过了几 tick」。稳态下同一刻入队、同一刻
发出的区块读数很小但不是恒为 0；它只覆盖排队到写出这一段，不含读盘，
不能直接和设计稿的「读盘 p95 < 100 ms」比较。`flush_bytes` 是压缩前的字节数
（共享区块帧按引用展开计数），用来看每刻出站量，不含连接层自己的心跳等包。

第三段 `sub-phases (per tick total, ms)` 把一个阶段拆成互不重叠的子段，
格式和 `phases` 一样，但每刻每个子段**只记一条「这一刻合计」样本**
（同一刻调用多次就累加），所以子段的 `count` 和 tick 数相同：

| 名称 | 含义 |
|---|---|
| `ticket_update` | `TicketOp` 应用到票表 + `TicketTable::run_updates()` + Director 消费等级变化列表 |
| `director_events` | Director 处理事件、派任务和写信箱（不包含 region 的插入/取出） |
| `director_ack` | 交付/收回的回执（含盒子判「原不原样」，`pristine_check` 单独再记一份） |
| `pristine_check` | 收回的盒子判「原不原样」的独占耗时 |
| `delivery_light_finish` | 交付/收回之前强行把光照算完 |
| `deliver_storage` | 交付：把世界层（方块、光照、3×3 段状态）放进 `ChunkStore` |
| `deliver_tables` | 交付：容器、计划刻、方块实体、实体等各张表放进 region |
| `reclaim_storage` | 收回：从 `ChunkStore` 取出区块柱（含 `unload` 的段状态重算） |
| `reclaim_ticks` | 收回：从计划刻队列取出属于这批区块的刻 |
| `reclaim_block_entities` | 收回：从方块实体表取出 |
| `reclaim_tables` | 收回：容器等按方块位置索引的表、红石记忆、变化和区块包缓存 |
| `reclaim_entities` | 收回：从实体表取出 |
| `levels_update` | 一批交付/收回/等级变化之后增量重算 `TickLevels` 的档位集合 |
| `mail_sort` | 信箱里剩下的交付/收回按到玩家的距离排序 |
| `return_boxes` | 把收回的盒子（或还在信箱里排队的盒子）交还 Director |
| `encode_body` | 发区块：编包体（`encode_chunk_body` 及其输入） |
| `make_frame` | 发区块：拼包头、做完整帧、放进共享帧 |
| `compress_frame` | 发区块：压缩共享帧 |

子段和父阶段的 `lap` 用各自独立的时钟起点，互不重叠也不互相截断：父阶段
仍是从上一次 `lap` 到这一次的全部墙上时间，子段只是它内部几段的合计，
所以父阶段通常比子段之和大。`compress_frame` 发生在连接任务里，
用两个原子计数器把耗时取进世界线程的 tick 边界（可能和连接被唤醒的时刻
差一刻），**不计入 `tick_total`**。

数量指标的直方图记的是「每刻多少个」（区块延迟是「每个区块多少微秒」），
所以这些行的 `mean`、`p50`、`p95`、`p99`、`max` 单位不是 ms，而是每行末尾的 `unit`。
`count` / `samples` 是这段报告的样本数：`phases`、`tick_total`、
`tick_start_lateness`、`tick_interval_deviation` 和 `flush_bytes` 每刻一次
（追赶和放弃追赶的刻少掉一条间隔偏差样本），`chunk_latency_us` 每发出一个区块一次。
报告头部 `N ticks` 是这段时间内跑了多少刻。

## 3. 假玩家压测工具

`tools/mc-bamboo-loadtest`（二进制 `bamboo-loadtest`）是自己写的最小协议客户端，
不用真实的 Minecraft 客户端或服务端。它只依赖 `mc-bamboo-protocol`、tokio 和仓库里
已有的 crate。所有假玩家共用一个 tokio 运行时，每名玩家一条异步任务，
不会一名玩家一个线程。

```bash
cargo build --release -p mc-bamboo-loadtest

./target/release/bamboo-loadtest \
    --addr 127.0.0.1:25565 --bots 50 --pattern walk --layout spread \
    --duration 60 --ramp 5
```

参数：

- `--addr`：服务端地址，默认 `127.0.0.1:25565`。
- `--bots`：假玩家数，默认 1。`--ramp` 秒内均匀放人。
- `--pattern`：`stand`（原地）、`walk`（固定方向匀速，默认 4.3 格/秒）、
  `fly`（固定方向 33 格/秒，创造模式飞行）、`wander`（出生点附近半径 8 格内随机游走，
  默认 4.3 格/秒）。`--speed` 可以覆盖速度，超过 200 格/秒会被拒绝。
- `--layout`：`cluster`（都在出生点附近）、`spread`（每人一个不同方向，越走越远）。
- `--duration`：跑多少秒；`--ramp`：多少秒内把假玩家陆续连上。
- `--json <文件>`：额外写一份机器可读的报告，基线脚本用。
- `--view-distance` 只属于 `serve`；假玩家请求的视距固定为 8，和 Bamboo 默认值一致。
- `--name-prefix`：玩家名前缀，默认 `Bot`，加四位编号后不超过 16 个字符。

假玩家走完握手 → 登录 → 配置 → Play，离线模式，支持服务端默认的压缩（阈值 256），
不支持加密。配置阶段回应 `select_known_packs`（声明认识官方内容包）；进服之后发
`player_loaded`，回应心跳、传送确认和 `chunk_batch_finished`（期望速率 64 区块/tick，
服务端允许的上限），按 20 Hz 发 `move_player_pos` 和 `client_tick_end`。
`fly` 还发一次 `player_abilities` 的飞行位，服务端默认游戏模式是创造模式，允许飞行。
收到的其它包只统计，不解析。位置每 50 ms 前进不到 2 格（33 格/秒），
在服务端的速度检查范围内。

结束时打印：连上的、登录失败的、中途掉线的（带原因）、每秒收到的字节/包数/区块数、
每秒发出的字节数、心跳往返时间的 p50/p95/p99/max。往返时间由每秒一次的
`ping_request` / `pong_response` 量出，和心跳回应走同一条连接任务路径。

`--json` 报告里还有每名掉线玩家的编号、掉线时刻和原因，以及每秒的逐秒计数。

### 内置服务端 `serve`

命令行版 `bamboo` 和桌面端现在都从服务器目录的 `server.properties` /
`bamboo.toml` 读配置（见 `configuration.md`），人数上限、视距、压缩阈值都能改。
基线仍用压测工具自己的子命令起服：它直接用 `ServerConfig::default()`、
不读配置文件，这样 50 人和 200 人场景不必先准备一份配置文件，两个进程也分开，
不共用 tokio 运行时：

```bash
BAMBOO_PROFILE=10 ./target/release/bamboo-loadtest serve \
    --addr 127.0.0.1:25977 --max-players 500 --view-distance 8
```

`serve` 用现有的公开接口（`Server::new`、`Server::run`）起服，日志初始化方式相同；
配置是 `ServerConfig::default()`，命令行只覆盖 `max_players`（默认 500）、`view_distance`
（默认沿用 `ServerConfig::default()` 的 8）、`world_dir`（`--world-dir <目录>`，不给就纯内存）
和 `chunk_worker_threads`（`--chunk-worker-threads <N>`，缺省 0 = 内联）。
`run-baseline.sh` 里对应的环境变量是 `WORLD_DIR` 和 `CHUNK_THREADS`；`WORLD_DIR` 给了目录时
每个场景写在 `WORLD_DIR/<场景名>/`，第 11 节的计算池对比就靠这两个开关跑。
和命令行版 `bamboo` 的差别是：它不读配置文件、上面四项由命令行给、日志里第一行写的是
"loadtest server is listening"、玩家名前缀是 `Bot`。游戏逻辑、tick 顺序和网络参数
都没改。

（2026-11-14 按实现更新：`tools/mc-bamboo-loadtest/src/main.rs` 的 `serve`、
`tools/mc-bamboo-loadtest/run-baseline.sh` 的 `WORLD_DIR` / `CHUNK_THREADS`、本文第 11 节；合并提交 `7bc6422`、`021a26f`、`082a7c9`）

`ops.json` 的 `bypassesPlayerLimit` 现在参与登录准入：满员时只有这个位为真的 OP
能进来（官方 `DedicatedPlayerList.canBypassPlayerLimit`）。基线里的假玩家都不是 OP，
所以这一项不影响上面任何一组数据。

## 4. 一键跑基线

```bash
tools/mc-bamboo-loadtest/run-baseline.sh [结果目录] [场景名...]
```

不带参数时依次跑五个场景，每个场景结束后重启服务端，收集服务端的剖析报告
（`server.log`）和压测工具的统计（`client.log`、`client.json`）到临时目录，
结束时杀掉服务端、删掉临时目录。传了结果目录就保留目录；`KEEP=1` 也保留。
`PORT`（默认 25977）、`RAMP`（默认 5 秒）、`PROFILE_SECS`（默认 10 秒）可以改。
只想跑其中几个场景就把名字列在结果目录后面。

| 场景 | 假玩家 | 移动 | 布局 | 时长 |
|---|---|---|---|---|
| idle | 1 | stand | cluster | 30 s |
| crowd-50 | 50 | wander | cluster | 60 s |
| crowd-200 | 200 | wander | cluster | 60 s |
| walk-50 | 50 | walk | spread | 60 s |
| fly-20 | 20 | fly | spread | 60 s |

`WORLD_DIR` 和 `CHUNK_THREADS` 也在这里生效：带 `WORLD_DIR` 时每个场景用
`WORLD_DIR/<场景名>/` 下的独立真实世界目录，不带时全部纯内存；`CHUNK_THREADS`
原样传给 `serve --chunk-worker-threads`。第 11 节的计算池对比就是这两个开关加
`BAMBOO_FAKE_GEN_DELAY_US` 跑出来的。

（2026-11-14 按实现更新：`tools/mc-bamboo-loadtest/run-baseline.sh`、本文第 3 / 11 节；合并提交 `7bc6422`、`021a26f`）

脚本最后用 `summarize.py` 打一张汇总表并写 `summary.tsv` / `summary.json`。
剖析器每 10 秒打完报告就清零样本，没法从多份直方图精确合并分位数，
所以表里的时间分位数、阶段平均耗时和数量指标是**多份 10 秒报告按样本数加权的平均**；
`tick max` 是这些报告各自最大值的最大者；只统计在线人数峰值达到目标人数 90%
以上的报告。客户端的「每秒收到字节数」是整个 `--duration` 的逐秒平均。

## 5a. 第二份基线数据（新指标）

  `tick_total` 最大值从 5.6..6.1 ms 降到 5.5..7.2 ms（在同一负载段内基本持平），
  但单刻交付量的尾部从 441 变成 73，正是这次改动要去掉的尖峰。
- 稳态（第二、三份报告）每刻交付的均值两种配置几乎相同（24.2..24.4 和
  36.0..36.1），`tick_total` 的 p50 也基本没变；改之前偶发的 81 / 103 / 108
  个/刻被夹到 64。也就是说限速只在尖峰那一刻生效，飞行途中不欠账。
- `delivery` 阶段在第三份报告里两种配置都是 2.4..2.9 ms 的均值，主要来自
  飞行途中大量区块改等级后 `finish_light_updates()` 和信箱重排，不是插入本身；
  两种配置的差别在噪声范围内。
- 第一份报告 `delivery` 的 p99 从 0.006 / 0.007 ms 升到 0.426 / 0.524 ms，
  是限速之后每刻重排剩余信箱的固定开销；它比省下的插入时间小一个数量级。

### 光照：`finish_light_updates()` 的独占耗时

信箱里有东西时仍按原做法强行把光照算完（没有改成别的）。在两个测量用例里
单独量它（release，已交付世界，改不同数量的方块后直接调用）：

| 改动方块数 | `finish_light_updates()` (us) |
|---|---|
| 0 | 0 |
| 1 | 5 |
| 32 | 20 |
| 256 | 102 |

飞行的第三份 10 秒报告里 `delivery` 均值 2.4..2.9 ms，其中光照只是几十到
几百微秒量级，主要成本是信箱重排和逐柱 `rebind_area`；**没有观察到光照独占
明显时间的场景**（最大 0.102 ms，对比单刻预算 50 ms），所以按任务要求保持
原做法，没有触发升级给主代理。

### N 的默认值和理由

**N = 64。** 理由：

1. 视距 8 时单个玩家进服要交付 441 个完工区块，全交付是 3.8 ms 的单刻尖峰；
   64 把它拆成 7 刻（第一刻 73 个，含 3×3 豁免），降到 2.4 ms，而收齐整个
   视野仍是 6 刻，和全交付一样，不增加玩家等待。
2. 16 太慢（23 刻才收齐），256 的进服尖峰还有 3.1 ms。64 是这批数据里
   唯一既削掉尖峰又不拖慢视野收敛的值。
3. 飞行稳态每刻新产生的交付请求均值 24..36 个，64 有一倍余量；
   20 名玩家飞行时 `chunks_delivered` 的 p99 贴到 64 但没有持续欠账。
4. 官方 `chunk_batch_received` 的发送速率上限也是 64 区块/刻，交付和发送
   用同一个数量级，不会出现「交了一大堆却发不出去」的积压。

- `ChunkMap.forEachBlockTickingChunk` 调的是
  `DistanceManager.forEachEntityTickingChunk`（`javap -c -p net.minecraft.server.level.ChunkMap`）；
- 后者遍历 `SimulationChunkTracker.chunks`，对每个等级满足

### 10.3 剩下的时间在哪

计数固定了两版 tick 的区块数、段数、方块数完全相同，因此**全部差距都是单价**。
按子项：7d 把「问位图」从 3.77 降到 1.12 ms（`fly-20` 稳态，省 2.65 ms）、
列集合省 0.33 ms；但同一段里「逐段 tick」从 0.65 涨到 3.10 ms（多 2.45 ms），
天气骰子多 0.20 ms、收尾多 0.08 ms。净下来就是文档里的 1.7 ms 量级；
空服从 0.09 涨到 0.53 ms（+0.44 ms），对应 0.45 ms 的差距。

逐段 tick 里两版做的事逐位相同：每段 3 次 `block_random_pos` + 3 次 `tick_one`，
约 19% 的格子真的落到草方块上，草会读上面一格、读两次光照、再随机挑 4 个邻居
读方块。区别在 `ChunkStore::block`：区块平面之后是 `loaded_chunk()` 的一次哈希
查表，加上每个区块各自的一份 `Chunk` 和光照柱（几千到两万份，随机访问时缓存
不命中）；之前没改过的区块共用一份一直在缓存里的模板。这与
`random-tick-notes/sample-before.txt` 里 `tick_one` 约 430 个样本、
`ChunkStore::block` / `light_value` / `LightStorage::column` 是主要叶子一致。
`sample` 把时间记在收尾几条指令上，是别的停顿落在那里，不是搬大结构体。

父阶段 absolute 数（上表最后一行）受机器噪声影响很大，两轮同一配置能差到两倍；
「剩下的 1.7 ms / 0.45 ms」这两个数来自 7d 的历史测量，10.5 用干净二进制在
安静窗口里重新量了一次，以后者为准。

## 11. 区块计算池（`chunk_worker_threads`，2026-11-13 PST）

设计和实现见 `world-model-design.md` 5.3.1。这里量两件事：慢生成器挪到池子之后
世界线程是不是不再被拖慢，以及真实的超平坦生成和编解码用池子之后有没有变慢。

- **c、d 两组只量到了生成走池子，没量到编解码**：这个场景里玩家飞走后收回的区块
  都是原样（pristine），直接丢掉，盘上一个区块文件都没写（世界目录里只有玩家存档），
  也就没有读盘解析。编解码另外用 11.3 的基准量。

### 11.2 加上在途上限之后（提交 `fc97c82`，**不在安静窗口**）

池子里同时最多放「线程数 × 4」个任务，其余留在宿主的待办表里按距离补进去，
撤票直接丢。重跑 a、b 两组；这时机器上还有别的编译和测试在跑（开始时 1 分钟
平均负载 12.3，结束时 5.1），数字有噪声，只看量级。

| 组 | 设置 | tick p50 / p95 / p99 / max (ms) | inbox 平均 (ms) | 发出区块/刻 | `compute_in_flight` 平均 | `compute_backlog` 平均 | `chunk_latency_us` p50 / p95 |
|---|---|---|---|---|---|---|---|
| a2 | 假生成器，0 线程 | 20.325 / 649.939 / 1228.431 / 3226.239 | 118.6 | 49.2 | 0 | 0 | 288 / 2 359 296 |
| b2 | 假生成器，4 线程 | 8.355 / 13.895 / 14.682 / 24.500 | 5.9 | 30.4 | 16.0 | 12 442 | 3 932 160 / 5 242 880 |

- 池子里的在途数恒为 16（4 线程 × 4），积压都在宿主的待办里，可以按玩家的新位置
  重排、撤票时直接丢掉。区块延迟 p95 从 9.4 s 降到 5.2 s（同样有噪声）。
- 假生成器的总吞吐没变，所以待办仍有 1.2 万：生成慢于需求时积压是必然的，
  上限只是让积压留在能重排、能丢的地方。
- 世界线程这一侧和 11.1 一样：tick p95 13.9 ms，不随生成变慢。

### 11.3 编解码基准（**不在安静窗口**）

`cargo test --release -p mc-bamboo-game --lib codec_throughput -- --ignored --nocapture`：
512 个改过方块的区块（几层石头里散着四种方块，平均每个 22 838 字节未压缩 NBT），
序列化和解析各跑一批。「世界线程」是提交任务加收回执的时间（池子的等待不算，
正式运行时世界线程不等，下一刻开头才收）；「墙钟」是这一批全部做完的时间。
连跑两遍，两遍相差不到 3%，下表是第一遍。

| | 内联：世界线程 = 墙钟 | 4 线程：世界线程 | 4 线程：墙钟 |
|---|---|---|---|
| 序列化 | 92.0 ms（179.6 µs/区块） | 0.1 ms | 27.4 ms（53.4 µs/区块） |
| 解析 | 261.5 ms（510.7 µs/区块） | 0.2 ms | 72.6 ms（141.9 µs/区块） |

- 世界线程上的编解码时间基本归零；4 线程的吞吐是内联的 3.4–3.6 倍。
- 解析一个改过的区块约 0.5 ms，比 `world-model-design.md` 5.4 估的「读盘每个 1.5 ms」里的解析部分小；
  压缩/解压在 IO 线程，不在这张表里。
- 这张表只量解析 / 序列化，不含 `Generate` 阶段；正式配置下 `chunk_worker_threads`
  默认仍是 0（内联），打开池子时 `Read` 仍在 IO 线程、`Assemble` 仍内联
  （`world-model-design.md` 5.3.1）。世界生成到噪声阶段已有纯函数和 `chunkgen` oracle，
  但还没接进 Director 的 `Generate` 阶段，所以这里量到的生成仍只是超平坦模板或假延迟。
