# 剖析器与压测工具

`mc-bamboo-game/src/profiler.rs` 给世界线程每刻记一份耗时直方图。本文说明怎么打开它、
报告里每一项是什么、怎么用假玩家给服务端加负载，以及第一份基线数据。后面几节按时间顺序
记了区块平面（第 8–10 节）、交付/收回的分配（10.6）和区块计算池（第 11 节）的对比；
第 12 节是重负载场景和按区块的三个方块侧阶段耗时（多区域 tick 第 0 步）。
`world_dir` 和 `chunk_worker_threads` 都能从压测工具的 `serve` 子命令行给，见第 3 节。

## 1. 打开剖析器

设环境变量 `BAMBOO_PROFILE=<秒>` 后启动服务端。世界创建时读一次，按这个间隔用
`tracing::info!` 打一份报告，打完把样本清零，下一份报告只覆盖之后的那些 tick。
没设、设成 0、负数或解析不了都当成关闭（仍累计但不打印）。
`BAMBOO_PROFILE_CHUNKS=1` 另外打开「按区块记计划刻 / 方块事件 / 方块实体三个阶段」的统计，
报告末尾多一段 `chunk-phases`；默认关，关着时零开销。见第 12 节。

```bash
BAMBOO_PROFILE=10 cargo run --release --bin bamboo
```

`RUST_LOG` 可以调日志级别，默认是 `info`；剖析报告是 `info` 级别的，日志级别调到
`warn` 以上就看不到。报告打在服务端进程的标准输出里。

## 2. 报告里每一项

报告分两段。第一段 `phases (by mean)` 按平均耗时降序列出 `World::tick` 的阶段：
`inbox`（处理入站消息）、`delivery`（Director 信箱泵和区块交付/收回）、
`light_updates`、`weather_and_time`、`scheduled_ticks`、
`random_ticks`、`block_events`、`entities`、`entity_compute`、`entity_commit`、
`block_entities`、`player_misc`、`views`、`block_change_broadcast`、
`entity_sync_and_tracking`、`chunk_sending`、`flush`、`tick_tail`。
每行是 `count`（样本数）、`mean`、`p50`、`p95`、`p99`、`max`，单位 ms。
分位数落在对数直方图的桶下界上，是偏保守的估计；桶在 0..15 ns 是逐纳秒，
之上每个 2 的幂再分 8 份，相对误差不超过 12.5%。

实体阶段按驱动分：精确驱动（默认，`bamboo.toml` 里 `entity_threads = 0`）只记
`entities` 一段，算完立刻落地；并行驱动（`entity_threads ≥ 1`）记
`entity_compute`（只读算阶段）和 `entity_commit`（发布状态、按 uid 升序应用命令、
发效果）两段，`entities` 没有样本。所以报告里有 18 个阶段，但任何一次运行只会有
17 个阶段有样本。**实体并行驱动仍用 `ScopedThreads` 每刻起线程**，剖析数字包含这项开销；
常驻的 `ComputePool` 是区块计算池，只跑区块的 `Decode` / `Generate` / `Save`，不接实体驱动
（`chunk_worker_threads` 控制，见第 11 节）。两处不要混淆。

第二段 `metrics` 里，`tick_total`、`tick_start_lateness` 和
`tick_interval_deviation` 是时间（ms）：

| 名称 | 含义 |
|---|---|
| `tick_total` | `end_tick − begin_tick`，一刻的实际总耗时 |
| `tick_start_lateness` | 实际开始时刻减去调度器给出的应开始时刻；提前醒了记 0 |
| `tick_interval_deviation` | \|相邻两刻**实际起点**的间隔 − 50 ms\|，设计稿 1.2「抖动 < 2 ms」看这一项 |
| `inbound_messages` | 每刻从信箱取出并处理的入站消息数 |
| `online_players` | 每刻开始时的在线玩家数 |
| `due_scheduled_ticks` | 每刻开始时到期的方块/流体计划刻数 |
| `entities` | 每刻开始时的实体数 |
| `chunks_sent` | 每刻写进出站缓冲的区块数；这一刻一个都没发也要记 0 |
| `chunks_delivered` | 这一刻 region 收下的区块数；一个都没收也要记 0 |
| `chunks_reclaimed` | 这一刻 region 交还的区块数；一个都没交还也要记 0 |
| `chunk_latency_us` | 一个区块从进入待发送集合到写进出站缓冲，过了多少微秒（墙上时间） |
| `flush_bytes` | 这一刻 `Links::flush` 交给连接层的全部 `Outgoing` 的未压缩字节数；一个都没有也记 0 |
| `skipped_catch_ups` | 这段时间内放弃追赶的次数（只有累计值，没有直方图） |
| `loaded_chunks` | 这一刻开始时已加载的区块数；无限模式记 0 |
| `parked_chunks` | 这一刻交付/收回之后停放表里的区块数 |
| `compute_in_flight` | 这一刻交付/收回之后已经交给计算池、还没回来的区块任务数（上限是线程数 × 4，存盘不受上限）；内联执行器（`chunk_worker_threads = 0`）恒为 0 |
| `compute_backlog` | 同一时刻宿主手里还没交给计算池的区块任务数（按离玩家的距离补进池子）；内联执行器恒为 0 |
| `master_busy` | 只在分离驱动（`island_threads ≥ 1`）下记：主控线程这一刻自己干活的时间，即 `tick_total` 减去等岛交回的那段（岛的实施计划第 7 步） |
| `island_busy` | 只在分离驱动下记：岛这一刻在 tick 线程上跑的时间 |
| `island_handoff` | 只在分离驱动下记：交接本身，派出到 tick 线程开跑，加上岛跑完（主控自己的活也做完）到主控接着干活 |
| `island_unify` / `island_divide` | 多岛：要整个世界的命令把全部岛临时拼成一个 / 再按原样拆回去的耗时（每次一条样本，第 10 步 c 段） |
| `island_world_command` | 多岛：这条命令本身在拼好的世界上执行的耗时，夹在拼和拆之间（每次一条样本，第 12 步） |
| `island_split_deferrals` | 多岛：因为某名玩家跟踪的区块跨了拆分切口而推迟的次数（每推迟一次一条样本，第 12 步；见 18.5） |

分离驱动下 `delivery` 阶段记的是和岛并行的那段里主控推进 Director 的耗时；岛在 tick 线程上
开跑和交回主控时各重新计一次 `lap`，交接本身只进 `island_handoff`，不混进相邻的阶段。

`tick_start_lateness` 量的是「每刻都比计划晚多少」，`tick_interval_deviation` 量的是
「刻与刻之间均不均匀」：睡眠精度带来的固定 4 ms 偏差只会出现在前一项里。
刻间隔偏差的口径是**只统计相邻两刻都按 50 ms 网格正常调度**的那一对
（上一刻睡过、这一刻没在追赶、也没放弃过追赶）：落后时连续跑的刻之间没有睡眠，
间隔由上一刻的耗时决定，量的是完全不同的东西，会把偏差撑成几十毫秒，
所以追赶中的刻既不记样本、也不作为下一对的基准；放弃追赶后重新起步的
第一对同理不记。每份报告打印清零样本时也会丢掉「上一刻」的基准，
所以跨报告的第一对不算样本。

`chunk_latency_us` 是墙上时间：区块进入 `pending` 时记 `Instant`，写进出站
缓冲时取经过的微秒数，不再是「过了几 tick」。稳态下同一刻入队、同一刻
发出的区块读数很小但不是恒为 0；它只覆盖排队到写出这一段，不含读盘，
不能直接和设计稿的「读盘 p95 < 100 ms」比较。`flush_bytes` 是压缩前的字节数
（共享区块帧按引用展开计数），用来看每刻出站量，不含连接层自己的心跳等包。

第三段 `sub-phases (per tick total, ms)` 把一个阶段拆成互不重叠的子段，
格式和 `phases` 一样，但每刻每个子段**只记一条「这一刻合计」样本**
（同一刻调用多次就累加），所以子段的 `count` 和 tick 数相同：

| 名称 | 含义 |
|---|---|
| `ticket_update` | `TicketOp` 应用到票表 + `TicketTable::run_updates()` + Director 消费等级变化列表 |
| `director_events` | Director 处理事件、派任务和写信箱（不包含 region 的插入/取出） |
| `director_ack` | 交付/收回的回执（含盒子判「原不原样」，`pristine_check` 单独再记一份） |
| `pristine_check` | 收回的盒子判「原不原样」的独占耗时 |
| `delivery_light_finish` | 交付/收回之前强行把光照算完 |
| `deliver_storage` | 交付：把世界层（方块、光照、3×3 段状态）放进 `ChunkStore` |
| `deliver_tables` | 交付：容器、计划刻、方块实体、实体等各张表放进 region |
| `reclaim_storage` | 收回：从 `ChunkStore` 取出区块柱（含 `unload` 的段状态重算） |
| `reclaim_ticks` | 收回：从计划刻队列取出属于这批区块的刻 |
| `reclaim_block_entities` | 收回：从方块实体表取出 |
| `reclaim_tables` | 收回：容器等按方块位置索引的表、红石记忆、变化和区块包缓存 |
| `reclaim_entities` | 收回：从实体表取出 |
| `levels_update` | 一批交付/收回/等级变化之后增量重算 `TickLevels` 的档位集合 |
| `mail_sort` | 信箱里剩下的交付/收回按到玩家的距离排序 |
| `return_boxes` | 把收回的盒子（或还在信箱里排队的盒子）交还 Director |
| `encode_body` | 发区块：编包体（`encode_chunk_body` 及其输入） |
| `make_frame` | 发区块：拼包头、做完整帧、放进共享帧 |
| `compress_frame` | 发区块：压缩共享帧 |

子段和父阶段的 `lap` 用各自独立的时钟起点，互不重叠也不互相截断：父阶段
仍是从上一次 `lap` 到这一次的全部墙上时间，子段只是它内部几段的合计，
所以父阶段通常比子段之和大。`compress_frame` 发生在连接任务里，
用两个原子计数器把耗时取进世界线程的 tick 边界（可能和连接被唤醒的时刻
差一刻），**不计入 `tick_total`**。

数量指标的直方图记的是「每刻多少个」（区块延迟是「每个区块多少微秒」），
所以这些行的 `mean`、`p50`、`p95`、`p99`、`max` 单位不是 ms，而是每行末尾的 `unit`。
`count` / `samples` 是这段报告的样本数：`phases`、`tick_total`、
`tick_start_lateness`、`tick_interval_deviation` 和 `flush_bytes` 每刻一次
（追赶和放弃追赶的刻少掉一条间隔偏差样本），`chunk_latency_us` 每发出一个区块一次。
报告头部 `N ticks` 是这段时间内跑了多少刻。
`BAMBOO_PROFILE_CHUNKS=1` 时报告末尾还有第四段 `chunk-phases`：一行一个区块，
五列是 `chunk <x> <z> <计划刻ns> <方块事件ns> <方块实体ns>`，数值是这段报告的
累计纳秒（不是 ms），默认关时不打这一段；口径和读法见第 12 节。

## 3. 假玩家压测工具

`tools/mc-bamboo-loadtest`（二进制 `bamboo-loadtest`）是自己写的最小协议客户端，
不用真实的 Minecraft 客户端或服务端。它只依赖 `mc-bamboo-protocol`、tokio 和仓库里
已有的 crate。所有假玩家共用一个 tokio 运行时，每名玩家一条异步任务，
不会一名玩家一个线程。

```bash
cargo build --release -p mc-bamboo-loadtest

./target/release/bamboo-loadtest \
    --addr 127.0.0.1:25565 --bots 50 --pattern walk --layout spread \
    --duration 60 --ramp 5
```

参数：

- `--addr`：服务端地址，默认 `127.0.0.1:25565`。
- `--bots`：假玩家数，默认 1。`--ramp` 秒内均匀放人。
- `--pattern`：`stand`（原地）、`walk`（固定方向匀速，默认 4.3 格/秒）、
  `fly`（固定方向 33 格/秒，创造模式飞行）、`wander`（出生点附近半径 8 格内随机游走，
  默认 4.3 格/秒）。`--speed` 可以覆盖速度，超过 200 格/秒会被拒绝。
- `--layout`：`cluster`（都在出生点附近）、`spread`（每人一个不同方向，越走越远）。
- `--duration`：跑多少秒；`--ramp`：多少秒内把假玩家陆续连上。
- `--json <文件>`：额外写一份机器可读的报告，基线脚本用。
- `--view-distance` 只属于 `serve`；假玩家请求的视距固定为 8，和 Bamboo 默认值一致。
- `--name-prefix`：玩家名前缀，默认 `Bot`，加四位编号后不超过 16 个字符。

假玩家走完握手 → 登录 → 配置 → Play，离线模式，支持服务端默认的压缩（阈值 256），
不支持加密。配置阶段回应 `select_known_packs`（声明认识官方内容包）；进服之后发
`player_loaded`，回应心跳、传送确认和 `chunk_batch_finished`（期望速率 64 区块/tick，
服务端允许的上限），按 20 Hz 发 `move_player_pos` 和 `client_tick_end`。
`fly` 还发一次 `player_abilities` 的飞行位，服务端默认游戏模式是创造模式，允许飞行。
收到的其它包只统计，不解析。位置每 50 ms 前进不到 2 格（33 格/秒），
在服务端的速度检查范围内。

结束时打印：连上的、登录失败的、中途掉线的（带原因）、每秒收到的字节/包数/区块数、
每秒发出的字节数、心跳往返时间的 p50/p95/p99/max。往返时间由每秒一次的
`ping_request` / `pong_response` 量出，和心跳回应走同一条连接任务路径。

`--json` 报告里还有每名掉线玩家的编号、掉线时刻和原因，以及每秒的逐秒计数。

### 内置服务端 `serve`

命令行版 `bamboo` 和桌面端现在都从服务器目录的 `server.properties` /
`bamboo.toml` 读配置（见 `configuration.md`），人数上限、视距、压缩阈值都能改。
基线仍用压测工具自己的子命令起服：它直接用 `ServerConfig::default()`、
不读配置文件，这样 50 人和 200 人场景不必先准备一份配置文件，两个进程也分开，
不共用 tokio 运行时：

```bash
BAMBOO_PROFILE=10 ./target/release/bamboo-loadtest serve \
    --addr 127.0.0.1:25977 --max-players 500 --view-distance 8
```

`serve` 用现有的公开接口（`Server::new`、`Server::run`）起服，日志初始化方式相同；
配置是 `ServerConfig::default()`，命令行只覆盖 `max_players`（默认 500）、`view_distance`
（默认沿用 `ServerConfig::default()` 的 8）、`world_dir`（`--world-dir <目录>`，不给就纯内存）
和 `chunk_worker_threads`（`--chunk-worker-threads <N>`，缺省 0 = 内联）。
`run-baseline.sh` 里对应的环境变量是 `WORLD_DIR` 和 `CHUNK_THREADS`；`WORLD_DIR` 给了目录时
每个场景写在 `WORLD_DIR/<场景名>/`，第 11 节的计算池对比就靠这两个开关跑。
和命令行版 `bamboo` 的差别是：它不读配置文件、上面四项由命令行给、日志里第一行写的是
"loadtest server is listening"、玩家名前缀是 `Bot`。游戏逻辑、tick 顺序和网络参数
都没改。

（2026-11-14 按实现更新：`tools/mc-bamboo-loadtest/src/main.rs` 的 `serve`、
`tools/mc-bamboo-loadtest/run-baseline.sh` 的 `WORLD_DIR` / `CHUNK_THREADS`、本文第 11 节；合并提交 `7bc6422`、`021a26f`、`082a7c9`）

`ops.json` 的 `bypassesPlayerLimit` 现在参与登录准入：满员时只有这个位为真的 OP
能进来（官方 `DedicatedPlayerList.canBypassPlayerLimit`）。基线里的假玩家都不是 OP，
所以这一项不影响上面任何一组数据。

## 4. 一键跑基线

```bash
tools/mc-bamboo-loadtest/run-baseline.sh [结果目录] [场景名...]
```

不带参数时依次跑五个场景，每个场景结束后重启服务端，收集服务端的剖析报告
（`server.log`）和压测工具的统计（`client.log`、`client.json`）到临时目录，
结束时杀掉服务端、删掉临时目录。传了结果目录就保留目录；`KEEP=1` 也保留。
`PORT`（默认 25977）、`RAMP`（默认 5 秒）、`PROFILE_SECS`（默认 10 秒）可以改。
只想跑其中几个场景就把名字列在结果目录后面。

| 场景 | 假玩家 | 移动 | 布局 | 时长 |
|---|---|---|---|---|
| idle | 1 | stand | cluster | 30 s |
| crowd-50 | 50 | wander | cluster | 60 s |
| crowd-200 | 200 | wander | cluster | 60 s |
| walk-50 | 50 | walk | spread | 60 s |
| fly-20 | 20 | fly | spread | 60 s |

`WORLD_DIR` 和 `CHUNK_THREADS` 也在这里生效：带 `WORLD_DIR` 时每个场景用
`WORLD_DIR/<场景名>/` 下的独立真实世界目录，不带时全部纯内存；`CHUNK_THREADS`
原样传给 `serve --chunk-worker-threads`。第 11 节的计算池对比就是这两个开关加
`BAMBOO_FAKE_GEN_DELAY_US` 跑出来的。

（2026-11-14 按实现更新：`tools/mc-bamboo-loadtest/run-baseline.sh`、本文第 3 / 11 节；合并提交 `7bc6422`、`021a26f`）

脚本最后用 `summarize.py` 打一张汇总表并写 `summary.tsv` / `summary.json`。
剖析器每 10 秒打完报告就清零样本，没法从多份直方图精确合并分位数，
所以表里的时间分位数、阶段平均耗时和数量指标是**多份 10 秒报告按样本数加权的平均**；
`tick max` 是这些报告各自最大值的最大者；只统计在线人数峰值达到目标人数 90%
以上的报告。客户端的「每秒收到字节数」是整个 `--duration` 的逐秒平均。

## 5. 第一份基线数据

> 这一节和下一节是**历史记录**，里面的指标名（`jitter` / `chunk_latency_ticks`）
> 是当时的旧名，对应现在的 `tick_start_lateness` / `chunk_latency_us`（口径已改，
> 数值不能直接比较）。第 5a 节是改名之后重新跑的基线。

测量环境：

- Apple M4 Pro，10 个性能核 + 4 个能效核（共 14 核），48 GiB 内存，macOS，arm64。
- Rust 1.99.1，`cargo build --release -p mc-bamboo-loadtest`（release，默认优化档）。
- 提交 `8eec7d8`（2026-11-09，PST）。基线跑的是这一版的 release 二进制；
  之后的提交只动文档和压测工具的 tick 节奏整理，服务端的剖析器和游戏逻辑没变。

- 发区块阶段（编码第一批 9 个区块）在四种预算下都是 42..56 us，没变。

### N 的默认值和理由

**N = 64。** 理由：

1. 视距 8 时单个玩家进服要交付 441 个完工区块，全交付是 3.8 ms 的单刻尖峰；
   64 把它拆成 7 刻（第一刻 73 个，含 3×3 豁免），降到 2.4 ms，而收齐整个
   视野仍是 6 刻，和全交付一样，不增加玩家等待。
2. 16 太慢（23 刻才收齐），256 的进服尖峰还有 3.1 ms。64 是这批数据里
   唯一既削掉尖峰又不拖慢视野收敛的值。
3. 飞行稳态每刻新产生的交付请求均值 24..36 个，64 有一倍余量；
   20 名玩家飞行时 `chunks_delivered` 的 p99 贴到 64 但没有持续欠账。
4. 官方 `chunk_batch_received` 的发送速率上限也是 64 区块/刻，交付和发送
   用同一个数量级，不会出现「交了一大堆却发不出去」的积压。

最后一类值得单独说：已加载模式下新视图的 49 个区块**每个都编一份自己的包体**

## 10. 随机刻剩下的差距：先计数，再拆子项（2026-11-11/12 PST）

`docs/performance-optimizations.md` 第 7d 节补回了一半的开销：`fly-20` 的
`random_ticks` 从 6.4–6.8 ms 降到 4.7–4.8 ms，但仍比区块平面之前（3.0 ms）慢；
空服 0.69–0.75 ms 对 0.26 ms。这一节的目的是回答「是每个区块变贵了，还是 tick 的
区块变多了」，并把剩下的时间拆开。

**三个版本、三份二进制。** 旧是 `b99f8b5`（区块平面之前，另开一棵工作树、
自己的 `target`），新是 `ec68ced`（7d 合入之后，本任务的起点）。计数和子项用的是
只在临时构建里存在、没有提交的仪表（`rt_probe` 模块 + 包住全局分配器的计数器，
`BAMBOO_RT_PROBE=1` 打开）；计时对比用的是三份**没有任何仪表**的 release 二进制：
`b99f8b5`（旧）、`ec68ced`（新）、`423cd12`（新 + 一次尝试性的优化，见 10.5）。
仪表在测量结束后全部撤销，`b99f8b5` 那棵临时工作树也已删除。

**口径。** 除 10.5 外，这一节的数据都量于 2026-11-11/12 PST 的**非安静窗口**
（机器上还有别的任务在编译，1 分钟平均负载 3.5–5.5），且带临时仪表。
计数不受机器噪声影响；子项的绝对值会随整机状态成倍变化，**只看同一轮里新旧各项的
比例**，不和别的章节的 ms 混用。10.5 是安静窗口、干净二进制，见该节说明。
剖析器每 10 秒打一份报告并清零，下面的数是稳态报告按样本数加权的平均。
压测场景照 `run-baseline.sh`：`idle` 1 人 30 s、`fly-20` 20 人 60 s，
`--ramp 5`，视距 8、模拟距离 10、压缩阈值 256、离线模式、超平坦世界。

**区块数一模一样，不是 tick 的区块变多了。** 旧版按每名玩家半径
`min(模拟距离 10, 视距 8 + 1) = 9` 的方形；区块平面之后改成按 ticket 的模拟等级
（`crates/mc-bamboo-game/src/tick_levels.rs` 的 `random` 集合：模拟等级 ≤31、
加载等级 ≤32、3×3 已交付）。用官方 26.3 的字节码核对过：

- `ChunkMap.forEachBlockTickingChunk` 调的是
  `DistanceManager.forEachEntityTickingChunk`（`javap -c -p net.minecraft.server.level.ChunkMap`）；
- 后者遍历 `SimulationChunkTracker.chunks`，对每个等级满足
  `ChunkLevel.isEntityTicking`（≤31）的位置调 consumer
  （`net.minecraft.server.level.DistanceManager`）；
- `DistanceManager.addPlayer` 加的 `PLAYER_SIMULATION` 票等级是
  `max(0, ENTITY_TICKING_LEVEL(31) - simulationDistance)`，模拟距离 10 时是 21，
  扩散 10 圈后等级 ≤31 的正好是玩家周围半径 9 的方形；
- `ServerChunkCache.tickChunks` 里逐区块 tick 用的就是这个集合，加载等级还要 ≤32
  且 3×3 就绪；这些条件在超平坦压测里全都满足。

所以在这两个场景里，新旧两套判断给出的是同一个集合，**新版的口径符合官方**，
不需要改 gating。超平坦只有最底下一段有草，所以每个区块恰好 tick 一段。

**effects 全空、视图零分配。** 计数回答了上一轮没查的两件事：收尾搬的、析构的
不是效果内容（超平坦随机刻一个效果都不发），`World::new` 里两个 `Vec` 都是
`Vec::new()`、容量 0，构造时不碰堆。上一次尝试的「就地取结果」
（`random-tick-notes/finish-in-place.patch`）把 `_platform_memmove` 换成
`drop_glue<Outcome>`，没有可测收益，和这里的计数一致：搬的是空的 `Vec`
和 168 字节 `Outcome` 的栈上副本。

### 10.3 剩下的时间在哪

计数固定了两版 tick 的区块数、段数、方块数完全相同，因此**全部差距都是单价**。
按子项：7d 把「问位图」从 3.77 降到 1.12 ms（`fly-20` 稳态，省 2.65 ms）、
列集合省 0.33 ms；但同一段里「逐段 tick」从 0.65 涨到 3.10 ms（多 2.45 ms），
天气骰子多 0.20 ms、收尾多 0.08 ms。净下来就是文档里的 1.7 ms 量级；
空服从 0.09 涨到 0.53 ms（+0.44 ms），对应 0.45 ms 的差距。

逐段 tick 里两版做的事逐位相同：每段 3 次 `block_random_pos` + 3 次 `tick_one`，
约 19% 的格子真的落到草方块上，草会读上面一格、读两次光照、再随机挑 4 个邻居
读方块。区别在 `ChunkStore::block`：区块平面之后是 `loaded_chunk()` 的一次哈希
查表，加上每个区块各自的一份 `Chunk` 和光照柱（几千到两万份，随机访问时缓存
不命中）；之前没改过的区块共用一份一直在缓存里的模板。这与
`random-tick-notes/sample-before.txt` 里 `tick_one` 约 430 个样本、
`ChunkStore::block` / `light_value` / `LightStorage::column` 是主要叶子一致。
`sample` 把时间记在收尾几条指令上，是别的停顿落在那里，不是搬大结构体。

父阶段 absolute 数（上表最后一行）受机器噪声影响很大，两轮同一配置能差到两倍；
「剩下的 1.7 ms / 0.45 ms」这两个数来自 7d 的历史测量，10.5 用干净二进制在
安静窗口里重新量了一次，以后者为准。

## 12. 重负载基线与按区块的三阶段耗时（多区域 tick 第 0 步，2026-11-16）

这一节回答 `docs/multi-region-tick-design.md` 第 7 节第 0 步的问题：计划刻、方块事件、
方块实体三个阶段在一刻里到底占多少，值不值得把它们按「单元」并行。前面 5–11 节的场景里
没有红石机器，一刻只有几毫秒，量不出方块侧阶段的份额。

### 12.1 怎么测

**场景。** `tools/mc-bamboo-loadtest/src/scenario.rs` 用 `mc-bamboo-hit-rate` 的九台机器

互质时钟汇合、熔炉阵列），世界内容完全由固定构造函数和固定网格决定，不用手工存档、
不启动真实的 Minecraft 服务端或客户端。九台机器按编号轮换，每台都带自己的周期输入
（翻红石块 / 往源头箱子补物品），各机输入相位错开，避免同一种机器在同一刻一起翻转造成
人为尖峰。

三个阶段的驱动循环本来就会发 `Observation::TriggerBegin` / `TriggerEnd`，
`RegionLevel::observe` 把它们按触发位置所在的区块累加纳秒，报告末尾多一段
`chunk-phases`，一行一个区块：`chunk <x> <z> <计划刻ns> <方块事件ns> <方块实体ns>`。
开关关着时 `RegionLevel` 不挂这个钩子，世界循环只多三次 `Option` / 布尔判断；
阶段顺序、方块逻辑、存储结构都没动。`setup` 和每刻的输入回调用 `WorldConfig` 上一个
`#[doc(hidden)]` 的压测钩子挂在 `inbox` 阶段（收包之后、计划刻之前），
它的耗时算进 `inbox`，**不算进三个方块侧阶段**。开关默认 `None`，正式服务端从不安装。

红石缓存打开时驱动会套 `Recording` 包装，它不转发 `observe`，所以这两个开关不要一起用；
本次测量全部用默认的缓存关闭状态。

### 12.3 按区块的分布和单元

忙区块按设计稿 4.1 的定义粗算：本报告窗口内三个阶段累计耗时大于 0 的区块。
单元是把忙区块按切比雪夫距离 ≤ 2 连成的每个连通块（**只离线算，没有实现划分**）。
「前 1 / 4 / 16 个区块」是三阶段耗时按区块降序后的累计占比；
「最大单元占三阶段」是**最贵的那个单元**（按耗时，不按区块数）占三阶段总耗时的比例。

表中「理论加速」按 8 线程、完美并行、最大单元仍串行粗算：设一刻平均 `T`、
三阶段合计 `S`、最贵单元占 `u`，三阶段并行后的下界是
`max(S / 8, S × u)`，加速上限 `T / (T − S + max(S / 8, S × u))`。
它没有算划分、越界尾段、线程调度、缓冲圈、汇总发包的开销，所以是**乐观上界**。

几个读数：

- 分散 4 台机器时，一台 15×15 红石线阵列就占了三阶段的 98.2%，
  其它三台几乎不花时间；4 个单元、最大单元 98.2%，8 线程最多缩短 1.2%。
- 分散 64 台时忙区块 71 个、分出 64 个单元，最大单元降到 14.6%，
  但前 4 个区块仍占一半（50.4%），所以上界只有 **1.702×（缩短 41.3%）**。
- `big-16` / `big-64` 的全部忙区块连成 1 个单元（19 / 81 个区块），
  最大单元占 100%，理论加速 **1.000×**：一条连成一片的红石，分区一点忙也帮不上。
  这是设计稿第 8 节第 2 条已经写明的固有限制，本轮把它量出来了。
- 加 50 名假玩家之后（`spread-16-players`），三阶段占比从 56.1% 降到 46.8%，
  `inbox` 从 3.7% 升到 13.6%（收包、票表传播），上界从 1.420× 降到 1.341×。
- 真实地形四个场景没有机器，三阶段合计只有 **0.3–0.6%**，
  `random_ticks` 占 28.4–58.9%、`inbox` 占 31.2–59.8%；
  忙区块 1–3 个，理论加速 ≈ 1.00×。这些场景里该先做的是随机刻和收包，
  不是方块侧三个阶段。

### 12.4 结论（按设计稿第 7 节的判断标准）

1. **有机器时三阶段远超一刻的三分之一**（46.8–68.8%），`scheduled_ticks` 一项就占
   43.9–65.9%；`block_events` 几乎为 0（0.1%），`block_entities` 只有 0.3–2.9%。
   也就是说真正值得并行的是**计划刻**这一个阶段，方块事件和方块实体在这批机器里
   不是瓶颈。九台机器的输入是外部驱动的，绝大多数触发都落在计划刻里。
2. **没有机器时三阶段只有 0.3–0.6%**，远低于三分之一。按第 7 节的判断标准，
   普通世界（真实地形 + 20/50 人走飞）应该先去做占大头的随机刻（28–59%）、
   收包（31–60%）和 `light_updates`（机器场景里 8.5–32.6%，由同一批方块改动引出，
   却不在三个并行阶段里）。
3. **即便在最有利的 `spread-64`，8 线程的理论上限也只有 1.702×（一刻最多缩短
   41.3%）；16 台是 1.420×，4 台 1.012×，连成一片或真实地形是 1.000×。**
   上界还没扣掉划分开销、越界尾段、缓冲圈和 4.4 节「单元太小就不并行」的门槛
   （初值 50 µs）：本轮 71 个忙区块里前 16 个占 95.1%，多数单元单个触发只有几微秒，
   按门槛它们本来就会退回串行。实际收益必然低于上表。
4. **第 3 步（单元并行）的收益高度依赖负载形态**：只有「很多台互不相连、负载又大致
   均匀的重机器」才划算；一台大机器、普通世界、或玩家聚集但没有红石，都拿不到收益。
   建议先做设计稿第 2 步（忙区块索引和单元划分，只算不用），在真实场景里量出
   「过 50 µs 门槛的单元有几个」和越界次数，再决定第 3 步做不做。
   本轮数据**不支持**跳过第 2 步直接实现并行。

### 12.5 口径和已知限制

- 世界是超平坦（机器场景）或固定种子 `20261116` 的 normal 地形；没有生物、没有
  结构/地物之外的内容（世界生成队员正在做），机器由脚本搭而非玩家搭建。
- `light_updates` 是机器翻转红石块引出的光照重算，占 8.5–32.6%。它在 `Phase` 里
  排在计划刻之前，不在三个并行阶段内；如果单元并行真的落地，这一段仍然是串行的，
  所以 12.3 的上界还偏乐观。
- 机器的周期输入在 `inbox` 阶段执行，等价于管理员在世界线程上操作；它有几百微秒到
  几毫秒的开销，已经算进 `inbox`，没有偷偷塞进三阶段。
- 按区块统计只记「触发自己所在的区块」，不记触发读写到的邻居区块；设计稿 4.1 的
  忙区块定义还包括「有没到期的计划刻 / 醒着的方块实体」和「最近 100 刻内忙过」，
  本次离线统计用的是「这一窗口内真的触发过」，是**下界**（安静但排队中的区块没算）。
  它会让单元数偏多、最大单元偏小，因此 12.3 的加速上界仍然偏乐观。
- `normal` 场景只预生成了出生点周围 21×21 个区块；飞行玩家很快走出这片区域，
  `inbox` 里因此仍有票表传播和生成任务派发的开销（59.8% 的 `normal-50-fly`）。
  这一项不是随机刻，但没有从表里扣掉。
- 每个场景 3 轮、每轮多个 10 秒报告；分位数是多份报告按样本数加权的平均，
  再从 3 轮里取中位数，不能从直方图精确合并（同第 4 节的口径）。
- 测量时机器不空闲，见 12.1；**只用占比和同轮内的相对量作证据**。

`tools/mc-bamboo-loadtest/run-heavy.sh`、`summarize-heavy.py`；本文档第 12 节）

## 13. 多区域 tick 第 2 步：实际单元划分与越界（2026-11-16）

这一节回答 `docs/multi-region-tick-design.md` 第 7 节第 2 步的问题：真实划分能分出
几个单元、划分本身花多少、如果并行会越界多少次，以及按**实际划分**重算第 12 节
那个乐观上界之后还剩多少收益。第 3 步（真正并行）做不做，由这里的数字决定。

### 13.1 做了什么和怎么测

**代码。** `region/partition.rs` 维护忙区块（最近 `quiet_ticks = 100` 刻内排入过
计划刻 / 方块事件、有排队事件、有醒着方块实体，或最近 100 刻内满足过「醒着」的
区块），按切比雪夫距离 `≤ 2 × halo` 连成连通块，每块加缓冲圈是一个单元；
`halo = 1` 和 `2` 同时各维护一份。加入用局部 BFS 并联相邻单元，退出只把受影响
的那个连通块拆开重算；`naive_partition` 是全量朴素对照，只在测试和一个调试开关
`BAMBOO_PROFILE_PARTITION=2` 下每刻运行并断言两套划分逐刻相同。跨区块的方块实体
关注关系（第 1 步的 `watchers_cross_chunks`，这里细化成 `watcher_pairs`）是一条
额外的连接边；它可能让两个相距很远的单元范围相交，划分最后把这样的单元并起来，
保证「不同单元范围不重叠」的不变量。

越界统计在 `Level` 的每个带位置读写入口上观察一次实际碰到的区块
（`Observation::ChunkAccess`，共 65 个调用点，见 `mc-bamboo-blocks/src/world.rs`），
以 `TriggerBegin` / `TriggerEnd` 界定一次触发。两类越界分别统计：

1. 触发读或写了自己单元范围（忙区块加缓冲圈）以外的区块；
2. 触发位置不在任何单元的忙区块里（设计 4.3 的第 2 种，含延迟超过
   `quiet_ticks` 的单发刻）。

每刻记越界触发数、涉及的单元数、越界时碰到的最远距离（按区块算）；按「读 / 写」
和「触发方块的注册名」分组。报告还记全部访问数，用来证明观察点没有漏报。
三个阶段照常**串行**执行，划分结果只用来统计，不改变任何可观察行为。
开关是 `BAMBOO_PROFILE_PARTITION`，默认关：关着时 `World` 循环只判一次布尔值，
`World::new` 问一次 `Level`，之后每次读写只有一次布尔判断（连虚调用都没有）。
和红石缓存一样按第 0 步的口径，本轮**不同时开**缓存与划分统计；录制包装
（`Recording::observe`）会转发 `ChunkAccess`，所以两个开关同开也不会漏记。

**场景和复现。** 第 0 步的十个场景（`tools/mc-bamboo-loadtest/run-heavy.sh`：
spread-4 / 16 / 64、big-16 / 64、spread-16-players、normal-20/50 的 walk / fly），
每场景 3 轮、每轮 60 秒，开关打开（`PARTITION=1`）跑一遍、关闭（`PARTITION=0`）
再跑一遍；每 10 秒一份报告并清零，汇总脚本只统计「场景已搭好 + 人数达到目标」
的稳态报告，先在同一轮内按样本数加权算平均和占比，再取 3 轮中位数。

```bash
CARGO_PROFILE_RELEASE_DEBUG=0 cargo build --release -p mc-bamboo-loadtest
PORT=25994 PROFILE_SECS=10 ROUNDS=3 SKIP_BUILD=1 PARTITION=1 \
    tools/mc-bamboo-loadtest/run-heavy.sh /tmp/bamboo-partition-full
PORT=25994 PROFILE_SECS=10 ROUNDS=3 SKIP_BUILD=1 PARTITION=0 \
    tools/mc-bamboo-loadtest/run-heavy.sh /tmp/bamboo-partition-full
python3 tools/mc-bamboo-loadtest/summarize-partition.py /tmp/bamboo-partition-full
# 全量朴素对照（每刻断言增量 == 全量）
PORT=25997 PARTITION=2 ROUNDS=1 DURATION=10 \
    tools/mc-bamboo-loadtest/run-heavy.sh /tmp/bamboo-partition-verify spread-16
```

**测量时机器不空闲**：这台机器上同时有别的代码任务在编译，10 场景 × 3 轮 ×
开关两遍共约 73 分钟。绝对毫秒数噪声很大（同一场景跨轮 p50 可以差 3 倍），
**占比、单元个数、越界比例和同轮内的相对量才是主证据**。剖析器的分位数落在
对数直方图桶下界，是偏保守的估计（第 2 节）。

### 13.4 越界：halo = 1 和 2 的对比

| 场景 | 每刻越界触发占比（halo 1 / 2） | 第 1 种（读 / 写越界） | 第 2 种（未归属） | 最远距离 | 越界主要方块 |
|---|---:|---:|---:|---:|---|
| spread-4 | 0.00% / 0.00% | 0 / 0 | 0 | 0 区块 | — |
| spread-16 | 0.17% / 0.17% | 0 / 0 | 6 | 0 区块 | 计划刻（未归属） |
| spread-64 | 0.40% / 0.40% | 0 / 0 | 54 | 0 区块 | 计划刻（未归属） |
| big-16 | 0.30% / 0.30% | 0 / 0 | 10 | 0 区块 | 计划刻（未归属） |
| big-64 | 0.36% / 0.36% | 0 / 0 | 49 | 0 区块 | 计划刻（未归属） |
| spread-16-players | 0.25% / 0.25% | 0 / 0 | 9 | 0 区块 | 计划刻（未归属） |
| normal-* | 0.00% / 0.00% | 0 / 0 | 0 | 0 区块 | — |

**读数解释，和「漏记」区分开**：`spread-16` 的短窗口里统计到 356 万次读、
1.9 万次写，全部落在各自单元范围内；越界统计的观察点是真的在报，不是开关没接上。
这批机器由脚本每 12 刻翻红石块、往源头箱补物品，所有触发都落在刚排过刻的
忙区块里；越界的 6 / 54 / 10 / 49 次是**第 2 种**：延迟超过 `quiet_ticks` 的
单发计划刻到期时，所在区块已经退出忙集合，按设计 4.2 走串行尾段，
下一刻重新标忙。它们占总触发的 0.17%–0.40%，尾段占三阶段耗时 < 0.01%。

**halo = 1 和 2 在这批场景里完全一样**：没有一次第 1 种越界，最远距离都是 0，
说明 1 圈缓冲（16 格）已经覆盖了九台机器一次触发的全部读写（活塞 12 格、
动力铁轨 8 格、默认红石线的单格更新都在范围内；15 格拉满的红石线连锁和
实验求值器没出现在这批机器里）。构造好的单元测试
`a_write_outside_the_halo_is_reported_as_an_out_of_unit_trigger` 用活塞从忙区块
推进缓冲圈外，验证 halo 1 的最远距离 2 区块、halo 2 是 1 区块，两套都能报出来；
故意漏记「写」这一种访问时，同一个场景会报出越界数掉到 0
（`a_missing_write_access_is_detected_by_the_piston_scenario`）。

换句话说：**在这些负载里 `halo` 用 1 就够了，2 圈白白多占区块**。但第 10 节
核对过的实验红石求值器一次能扩散 15 格线网再加 1 格邻居，从忙区块最边上出发
仍可能碰到 1 圈之外；`halo` 保持配置项，等有真实红石线大阵列时再量。

### 13.5 用实际划分重算第 0 步的上界

第 12 节用「本窗口内真的触发过」的区块离线粗算，把越界、划分、缓冲圈和
「单元太小就不并行」的门槛都当 0，得到 1.0–1.7 倍的乐观上界。这里用实际
划分（每个单元的三阶段累计耗时）、越界尾段（越界 / 未归属触发的耗时进串行）
重算 8 线程上界；`halo = 1 / 2` 结果相同，因为没有第 1 种越界。

| 场景 | 第 12 节离线估计 | 本次实际划分（halo 1 = 2） | 差在哪 |
|---|---:|---:|---|
| spread-4 | 1.012× | 1.011× | 一致 |
| spread-16 | 1.420× | 1.683× | 本轮三阶段占比更高（77.6% 对 56.1%） |
| spread-64 | 1.702× | 2.590× | 同上（74.0% 对 48.9%）；本轮噪声更大 |
| big-16 | 1.000× | 1.003× | 一致，1 个单元 |
| big-64 | 1.000× | 1.002× | 一致，1 个单元 |
| spread-16-players | 1.341× | 1.491× | 本轮三阶段占比 63.9% 对 46.8% |
| normal-20-walk | 1.001× | 1.004× | 一致（噪声） |
| normal-20-fly | 1.002× | 1.003× | 一致 |
| normal-50-walk | 1.002× | 1.002× | 一致 |
| normal-50-fly | 1.000× | 1.002× | 一致 |

**这张表不能被读成「第 3 步能加速 2.6 倍」**：两轮测量的绝对毫秒数差别很大
（同一 `spread-64` 第 12 节 tick 平均 15.4 ms，本轮开关打开时 p50 就 10.5 ms、
p95 81 ms），三阶段占比随之从 48.9% 涨到 74.0%；上界对这一段特别敏感。
**能用的结论是结构性的**：连成一片和真实地形仍是 ≈ 1.00×；只有分散的、
负载又大致均匀的重机器能分出几十个单元；越界尾段在这批场景里 < 0.01%，
不构成瓶颈。按第 12 节已经指出的另两项再扣：`light_updates` 占 8–33%
且不在并行范围；设计 4.4 的 50 µs 门槛下，spread-64 的 61 个单元里前 16 个
占了三阶段耗时的 95%，多数单元单个触发只有几微秒，本来就会退回串行。

### 13.6 开关关闭时对 main 的性能

严格 A-B-A 交替（`compare-partition-micro.sh`，A = 第 1 步结束时的
`a134487a` 独立工作树，B = 本分支且开关关闭；5 轮，每轮取两份 A 的中位数，
逐对比值再取中位数）：

| 基准 | 逐对比值中位数 | 硬指标 |
|---|---:|---|
| 九台机器 `cache_bench 4000 1`（关缓存那侧） | **1.003** | ≤3% ✅ |
| 三种计划刻形状 `ticks_bench`（16 / 1024 / 4096 区块，batch + rolling） | **1.000** | ≤3% ✅ |

九台机器逐项：0.974–1.015；三种形状的六个数字：0.987–1.005。
`compare-partition-overhead.sh` 的 `spread-16` 压测（3 对，每对 A-B-A）逐对
p50 比值 1.125 / 1.823 / 1.091、p95 比值 0.929 / 1.436 / 0.957，波动来自同时

系统 Killed）。**这一项数据不足以判定 3%**，正式判定以两个微基准为准。

开关打开时（同轮 A-B-A 交替，A = 开、B = 关）`spread-16` 的

涨到约 1.10 ms（约 +17%，且 p95 因噪声反而更低）。**打开开关明显变慢**，
它只是测量工具，正式服务端不开。

### 13.7 结论：第 3 步做不做、`halo` 用几

1. **`halo` 用 1。** 十个场景里第 1 种越界一次都没有，`halo=2` 和 `halo=1`
   的越界次数、尾段耗时、理论上限逐位相同；2 圈只会让每个单元的缓冲区块从
   9 个变 25 个，把分散机器更快连成一片。保持它可配置，留给出真实红石线
   大阵列（实验求值器）时再测。
2. **越界不是问题。** 第 2 种越界（迟到的单发计划刻）占触发的 0.17–0.40%，
   尾段占三阶段 < 0.01%；设计 4.3 的「原地等到尾段」足够兜住。
3. **划分阶段本身也不是问题**：p50 1–11 µs，占一刻 ≤ 0.40%，关着时零开销。
4. **第 3 步只在「很多台互不相连、负载大致均匀的重机器」里值得做**，而且
   预计实际加速远低于上界。`spread-64` 是最有利的场景：61 个单元，但按
   50 µs 门槛多数单元会退回串行，`light_updates` 还占着 8–33% 的串行段；
   第 12 节实测的 1.702× 上界和本轮 2.590× 都只是「完美并行 + 不扣门槛」的
   乐观值，实际收益估计在 1.1–1.3× 量级，且只对这一类人造场景成立。
5. **普通世界（真实地形 + 20/50 人）和连成一片的机器都拿不到收益**
   （≈ 1.00×）。按第 7 节的判断标准，应该先去做随机刻、`light_updates`
   和收包，而不是按表往下实现单元并行。**本轮数据不支持现在做第 3 步。**

### 13.8 独立复核与一次瞬时探针失败

`docs/multi-region-tick-design.md` 第 10 节的三项原版数值在本步按 26.3 字节码
核对：默认红石求值器单格 ±2 格、连锁最多 15 格，实验求值器一次可达 15 格
线网再加 1 格邻居；动力铁轨沿轨道两个方向各 8 格（`depth >= 8` 提前返回）
再加 1 格邻居查询；`ServerLevel.tick` 给 `blockTicks` 和 `fluidTicks` **各**
65536 的独立配额，`LevelTicks.canScheduleMoreTicks` 到上限是「留到下一刻」
而不是丢弃，由全世界一条 `toRunThisTick` 队列计数。结论写进了设计稿
4.3 的表、4.7 末段和第 10 节，没有抄反编译源码。

联机探针跑过多轮：官方 hy4 探针全部 719/719；`tools/probe.sh --loaded`
两遍全过（各 2 × 719/719）多轮复现。其中有一次 `--loaded` 的第二遍出现
`PROBE RESULT 717/719`，两条失败都是 `placement: the log and the torch arrive
in one section update ...` / `the breaker gets the same section update`；紧接着
的三次重跑（含同一端口前后各一次）都是 2 × 719/719，第 1 步基线工作树的
`--loaded` 也是 2 × 719/719。这两条是官方探针里和区块交付时序有关的检查，
本次改动不碰交付路径（默认开关关闭时只有 `clear_activity_touched` 两个
`Vec::clear`），判为第 0 步报告里已经写明的整机负载 / 时序噪声，不是回归；
报告里如实保留。

### 13.9 口径和限制

- 只统计三个方块侧阶段里的触发；玩家放 / 破坏方块、实体落地在串行阶段执行，
  按设计 4.2 不进划分，也不进越界统计。
- 观察点覆盖 `World` 里 65 个带位置的 `Level` 调用点；短窗口里 `spread-16`
  统计到 356 万次读 / 1.9 万次写，全部在范围内。没有覆盖的读写只会让越界数
  偏小，构造好的改坏确认测试用来防住「漏记一种访问」这类实现错误。
- 划分统计和红石缓存按第 0 步的口径不同时打开；`Recording::observe` 会
  转发 `ChunkAccess`，两个开关同开也不会漏记，但没有在这批测量里用。
- 第 2 种越界只报「触发不在忙区块里」，不按方块类型分组（报告里
  `out-block` 一行为空）；延迟超过 `quiet_ticks` 的单发刻是这一类的全部来源。
- 单元耗时按「单元里坐标最小的忙区块」做稳定编号累计；划分拓扑变化时
  旧编号的耗时不会串到新单元。理论上限按 8 线程、完美并行、最贵单元串行
  粗算，没扣线程调度、汇总发包和 4.4 门槛，仍是乐观上界。
- 两遍测量共 73 分钟，机器上同时有别的代码任务；**只用占比、单元数、
  越界比例和同轮内的相对量作证据**，跨轮 / 跨章节的绝对 ms 不能直接相减。

## 14. 岛的基线：玩家分成 K 组、相距很远（2026-11-16）

这一节是 `docs/island-implementation-plan.md` 每一步的对照基线：玩家分散在几处、
各处都有机器和掉落物时，**现在**（一条世界线程、一个 `Region`）每刻花多少、花在哪，
以及「如果 K 组各自独立跑」理论上最多能快多少。

### 14.1 场景和怎么测

`tools/mc-bamboo-loadtest/src/scenario.rs` 新增 `islands-1` / `islands-2` / `islands-4` /

**口径。**

### 14.3 读数

1. **玩家分散时，岛的收益是线性的，主控不是瓶颈。** 每组平均耗时在 2.5–3.1 ms 之间，
   K 组的总耗时近似 K 倍；以后留在主控上的串行段 0.02–0.04 ms，按 Amdahl 定律
   K = 8 的上限仍是约 8 倍。这和第 12、13 节的单元并行（普通世界约 1.00 倍）是
   两种负载形态：单元帮的是「一个地方很多机器」，岛帮的是「玩家分散」。
2. **基线里 `islands-8` 的上限 8.18× 略超过 8，原因是实体阶段在一个大 `Region` 里超线性
   （已查清并修掉，见 `docs/performance-optimizations.md` 第 19 节）。**
   改之前掉落物每个每刻的 `entities` 耗时：`islands-1` 3.5 µs、`islands-2` 3.4 µs、
   `islands-4` 4.2 µs、`islands-8` 6.3 µs。不是漏斗关注表、吸取盒扫描或
   `EntityStore.grid` / `index` / `taken` 的缓存问题，而是
   `crates/mc-bamboo-game/src/drops.rs` 的 `pickup_for`：**每名玩家每刻都把整张
   `EntityStore` 遍历、克隆成 `Entity`，再按盒子过滤**。每组的玩家数和掉落物数都随 K
   线性增长，于是这一段的单价 ∝ K、总量 ∝ K²，互不相邻的组互相拖慢。分段计时和
   `sample` 把增长全归到这一段：微基准里实体 tick 每个物品的耗时在 N = 1→16 时
   稳定在 2.24–2.29 µs，捡起那一段却从 0.52 µs 涨到 8.30 µs（每次翻倍都正好翻倍）。
   修法是拿已有的空间索引 `EntityStore::for_each_in(reach)` 代替全表扫描；它内部已按
   `intersects` 精确过滤并按 uid 升序访问，候选名单和落地顺序逐项不变，所以行为逐位一致。

   **修后数字**（同一台机器、`INTERLEAVE=1` 同轮交替 3 轮中位数，`DURATION=35`、

   4.2 / 6.3 µs 同口径，比值一致），不是把两轮不同时间的数字混在一起比。
   修后单价 1.99–2.89 µs 不再随 K 增长（逐轮 K=8/K=1 的比值 0.74 / 0.66 / 1.06，

3. **其余阶段大体线性。** 每组的 `scheduled_ticks` 0.77–0.90 ms、`light_updates`

5. 已加载区块 483 / 772 / 1350 / 2506：每多一组正好多 289 个，组和组的已加载区域

## 15. 岛的实施计划第 8 步：分区器（只算不用，2026-11-17）

这一节只回答「按 6.1 的规则，现有压测场景能分出几个岛、合并 / 拆分多不多、
分区器自己每刻花多少」。第 8 步**不改运行时行为**：`Region`、Director 的交付
路径、`Owner::Region(id)`（恒为 0）全都照旧；分区器在主控侧按「票想要加载的
区块」（加载等级 ≤ 33）并上还没收回的区块维护 4×4 区块的 section 计数、
≤ 2 的合并和 ≥ 4 持续 200 刻的拆分。`BAMBOO_PROFILE_ISLANDS` 默认关，
`1` 打开统计，`2` 再打开每刻全量对照；关着时正式路径只有一次布尔判断。

### 15.1 怎么测

`run-heavy.sh` 加了 `ISLANDS`（默认 0），把开关透给服务端进程。7 个场景
按 `INTERLEAVE=1` 同一轮挨着跑，每场景一个全新进程、`DURATION=20`、
`PROFILE_SECS=5`，超平坦和真实地形各按场景自己的配置，`PARTITION=0`
（单元划分统计关闭，不和本次的数字混在一起）：

```bash
CARGO_PROFILE_RELEASE_DEBUG=0 cargo build --release -p mc-bamboo-loadtest
PORT=26596 DURATION=20 PROFILE_SECS=5 ROUNDS=1 SKIP_BUILD=1 PARTITION=0 \
    INTERLEAVE=1 ISLANDS=1 tools/mc-bamboo-loadtest/run-heavy.sh \
    /tmp/bamboo-island-step8/report \
    islands-1 islands-2 islands-4 islands-8 spread-16 normal-20-walk normal-20-fly
# 全量对照：2 会让分区器每刻断言增量 == 全量，并在 pump 收敛后对账等级 / owner
ISLANDS=2 DURATION=8 PROFILE_SECS=4 PORT=26594 SKIP_BUILD=1 PARTITION=0 \
    tools/mc-bamboo-loadtest/run-heavy.sh /tmp/bamboo-island-step8/verify \
    islands-2 normal-20-fly
```

报告里的 `island_partition (step 8, ...)` 段由 `island_partition_stats.rs` 生成：
`island_partition_ns` 是分区器 `tick` 自己（含常开的局部不变量检查），
`bookkeeping_ns` 是 `pump` 里把等级变化 / owner 事件折算成增量的耗时，
`verify_ns` 只在 `=2` 打开（每刻全量重算 + 全量对账）。`island-size-sections`
和 `island-size-chunks` 是两种大小分布（每岛非空 section 数、每岛依据区块数，
同一格在两套集合里只记一次）。合并 / 拆分给窗口内总数、每刻和每秒（20 TPS）。
数字按报告窗口的样本刻数加权，丢掉搭场景那一份报告；单轮、机器上有别的任务
在编译和测量，绝对耗时只作参考。

  才覆盖合并、拆分、登记取消这几条路径；「真实玩家轨迹下的迟滞参数合不合适」
  仍是第 11 步要量的东西，本节的数字不能代替。
- 不变量失败全为 0：不同岛的非空 section 距离 > 2（也就是票想加载的
  区块不相邻）、每个非空 section 恰好在一个岛、每个依据区块恰好在一个岛。
  `=2` 的 `islands-2` / `normal-20-fly` 冒烟跑完没有一次全量对照报错。

### 15.4 口径和限制

- 只有一轮、每场景 20 秒，不是长时间的玩家轨迹；合并 / 拆分的 0 次只说明
  稳态布局不动，不说明迟滞参数（4×4 网格、2 / 4 / 200 刻）已经在真实轨迹上
  验证过（第 11 步）。
- 报告窗口内 `desired` 的均值比 `held` 略小（`islands-1` 447 对 483），
  因为票想要加载的区块是等级 ≤ 33 的集合，已交付但仍在 100 刻逗留期的
  区块靠 owner 补进来；两套集合取并集，同一格只记一次。
- 分区器耗时的 `Instant` 取钟本身也在计时里，纳秒级的 p50 只作量级参考。
- `=2` 的全量对账按 Director 当前视图扫描等级表和 owner 表，开销随已加载
  区块数增长，是刻意的对照实现，不能当正式路径。

## 16. 岛的实施计划第 10 步 d 段：多岛的测量和缺省值（2026-11-18）

这一节回答三个问题：一个岛时多岛模式有没有退化；玩家分散时并行带来多少；一个特别重的
岛是不是只拖慢自己。并据此定 `islands` 和 `island_threads` 的缺省值（`docs/configuration.md`
「岛的 tick 线程」「多岛」）。

### 16.1 先补的盲点

- **混合驱动下主控的剖析**：以前家岛落后（不在主控手里）的那几刻，主控这一段记进一份
  不进报告的备用剖析器，报告里少了这些刻。现在混合驱动下打报告的就是主控自己的剖析器：
  主控的各段每刻都记；各岛的子段在岛交回时并进来，其余样本在打报告前并进来；报告末尾每个
  岛一行（`island N chunks= players= entities= ticks= tps= busy mean/p50/p99/max dropped=
  owed=`），岛不在手里时也有它这段时间跑完的刻数和耗时（主控在岛落座时记）。报告头多了
  「over X s」，TPS 按报告覆盖的墙上时间算。
- **交接两半**：`island_handoff` 以前每刻只记派出那一半、一刻一条。现在按岛记：派出到线程
  开跑（线程空着时），加上主控在等时岛跑完到主控接着干活；每个岛每刻一条。全部线程都忙、
  岛进了公共队列时，派出到开跑这段另记 `island_queue_wait`，不算交接。追赶时等岛的时间也
  不再算进 `master_busy`。
- **新指标**：`island_unify` / `island_divide`（整个世界的命令拼 / 拆，每次一条），
  `island_dropped_ticks`（岛落后超过 2 秒丢掉的刻）。测试
  `profiling_covers_every_master_tick_and_every_island_tick` 钉住「主控每刻进报告、每个岛
  每刻一条耗时和一条交接」，改坏确认：把家岛落后时的记录挪回备用剖析器、或者只记派出那半，
  都会失败。
- **压测场景的假玩家从没被送到各组**：14.1 说压测钩子用控制台 `/tp` 把第 `i` 名送到第
  `i % K` 组，但控制台的 `/tp <玩家> <x> <y> <z>` 要求来源有位置，报
  `permissions.requires.player`（这条检查 11-08 就在），所以 `islands-K` 一直是全部玩家在
  第 0 组、只有机器和掉落物分在各组。第 14 节的基线和 `performance-optimizations.md` 第 22 节
  的 `islands-8` 数字都是这样量的。现在钩子直接放置玩家（`command::place_player`，和 `/tp`
  同一段移动），岛不在手里时下一刻再试。
- **压测里撞出的 panic**：`islands-8`、8 条线程、假玩家进服时世界线程 panic「交回还没处理完
  就拆岛」。原因和修法见 `island-implementation-plan.md`「第 10 步 d 段的实测」；修好后下面的
  数字是重跑的。

### 16.2 场景、配置和怎么测

`tools/mc-bamboo-loadtest/compare-islands.sh`（汇总 `summarize-islands-compare.py`）：同一个
release 二进制，只换 `BAMBOO_ISLANDS` 和 `BAMBOO_ISLAND_THREADS`；每轮里 5 种配置各起一个
全新进程，轮与轮之间正反交替（A-B-C-D-E / E-D-C-B-A），每次 30 秒，只取全部假玩家进服 2 秒
以后的 5 秒报告，取中位数。每次开始和结束记 `uptime`，下表的「负载」是这一场景全部运行的
1 分钟负载范围。机器是 14 核（10 性能 + 4 能效）的 M4 Pro，**测量时同一台机器上别的任务在
编译**，1 分钟负载在 3 到 78 之间跳。所以只比同一轮里的相对差距。

| 场景 | 内容 |
|---|---|
| `islands-1` | 一组：10 名游走的假玩家、九台机器、256 个掉落物（第 14 节） |
| `islands-4` / `-8` / `-16` | 同样的组 4 / 8 / 16 个，沿 x 轴每隔 64 个区块，第 `i` 名假玩家放到第 `i % K` 组 |
| `islands-heavy-4` | `islands-4`，第 0 组另外多放 3 万把不能堆叠的钻石剑（`HEAVY_ITEMS=30000`），这一组单独就跑不满 20 TPS |
| `islands-shuttle` | 8 名站着的假玩家排成一列（相邻隔 30 个区块，并成一个岛）；每 400 刻单数号的人走开 200 个区块、再回来，量拆合 |

配置：`off-t1` = `islands = false`、1 条线程（多岛之前的缺省）；`on-tN` = `islands = true`、
N 条线程。4 轮（`islands-shuttle` 两轮、每次 90 秒）。

「每刻耗时」是主控一刻从开始到结束的墙上时间（`tick_total`）：多岛关着时主控等唯一的岛
回来；多岛开着时主控等到全部岛回来或者截止时间，所以它也是「全部岛的这一刻都做完」的
时间，但被截止时间封顶。「TPS」是主控的；多岛时每个岛自己的 TPS 另列。CPU 是进程 CPU
时间除以墙上时间（用了几个核）。

### 16.3 一个岛时有没有退化

`islands-1`，4 轮（负载 4–40）：

| 配置 | TPS | p50 | p99 | 最大 | 均值 (ms) | 逐轮均值比（对 `off-t1`） | CPU |
|---|---:|---:|---:|---:|---:|---|---:|
| off-t1 | 19.98 | 1.44 | 14.68 | 32.9 | 2.83 | 1 | 0.08 |
| on-t1 | 19.99 | 3.54 | 27.26 | 64.0 | 5.16 | 2.34 / 0.91 / 2.11 / 0.96 | 0.11 |
| on-t2 | 20.00 | 3.41 | 28.31 | 34.8 | 5.10 | 2.94 / 0.96 / 2.12 / 0.72 | 0.12 |
| on-t4 | 20.00 | 2.69 | 21.50 | 33.2 | 4.06 | 2.70 / 0.78 / 2.11 / 0.45 | 0.09 |
| on-t8 | 19.99 | 2.69 | 23.07 | 33.2 | 4.12 | 1.79 / 1.06 / 1.96 / 0.80 | 0.11 |

比值在 0.45 到 2.94 之间跳，是**整台机器的快慢状态**，不是多岛的开销：慢的那几次主控
（`master_busy`）和岛（`island_busy`）一起变慢 2.5–3.5 倍、p50 从 1.2 ms 到 4–5 ms，多岛关着的
`off-t1` 第 4 轮也一样（均值 5.69 ms、p50 3.93 ms），而且慢态多出现在负载低（4–8）的几轮
（推测是进程被放到能效核或降频，没有再查）。同一时段的专门 A-B-A-B（`off`、`on-t4` 各两份
配置名，3 轮、每次 20 秒，负载 6–11）：多岛关着 6 次的均值 1.84–2.40 ms（中位数 1.97），
开着 6 次 1.79–5.41 ms（中位数 2.29），其中 4 次的 p50 和关着的完全相同（1.05–1.18 ms），
另 2 次是上面的慢态（p50 1.84 / 4.19 ms，主控和岛一起慢）。

微基准把机器噪声去掉：`island_pool_tests::one_island_hybrid_cost`（release，已加载模式、一名
站着的玩家，两边背靠背不睡，A-B-A 交替 7 轮，跑 3 遍，负载 30–58）：多岛关着每刻 21–54 µs，
开着每刻多 **中位数 10.1 µs**（21 轮范围 −9 到 +30 µs），是混合驱动自己的记账（分区器、
截止时间、落地和追赶的检查、按岛的交接记录）。按 `islands-1` 每刻约 2 ms 算是 0.5%。

**结论**：一个岛时多岛模式每刻约多 10 µs，压测里看不出退化；逐轮的大幅波动来自机器状态，
两种配置都有。没有排除「多岛开着的进程更容易被放到慢核上」，这一点留给第 11 步在安静的
机器上复核。（第 11 步已复核：齐步、没有 tick 线程的精确模式同样出现这种慢态，和多岛无关，
见 17.4。）

### 16.7 判死有没有误判

正常负载下（上面全部运行，含重岛和负载 78 的几轮）**判死 0 次**（`declared dead` 0 条），
缺省 30 秒的时限离重岛最慢的一刻（0.35–0.42 秒）和追赶上限（2 秒）都很远。日志里的 `WARN`

### 16.8 口径和限制

- 机器不安静，每种配置只有 4 次（拆合 2 次），只看同轮相对差距；绝对数随负载变化很大。
- 每次只取 5 秒的稳态报告，拆合和整个世界的命令的样本数少（每轮 5–6 次）。
- `islands-1` 的慢态（16.3）没有查清是不是和多岛有关；长时间压力和真实玩家轨迹下的拆合
  频率是第 11 步。（都已在第 17 节回答：慢态和多岛无关；真实轨迹下的拆合见 17.3。）

### 17.4 `islands-1` 的慢态：不是多岛引起的

16.3 留下的问题：`islands-1` 偶尔整体慢 2.5–3.5 倍（主控和岛一起慢，p50 从约 1 ms 到
4–5 ms），没排除和多岛有关。这一步同一时段交替跑（`compare-islands.sh`，每次 20–25 秒、
全新进程）三种配置：`lock-t0`（`islands = false`、`island_threads = 0`，齐步，根本没有
tick 线程）、`off-t7`（一个岛、分离驱动、7 条线程）、`on-t7`（缺省，多岛开）。4 组共
40 次，负载 2.8–70.8，其中两组另外起 0 或 6 个空转的 shell 进程占核：

| 配置 | 次数 | 慢态（p50 > 2 ms）次数 | 每刻均值（ms，逐次） |
|---|---:|---:|---|
| `lock-t0` | 10 | 7 | 6.84 4.41 4.45 4.01 1.75 5.49 4.80 1.75 5.37 1.91 |
| `off-t7` | 12 | 11 | 6.83 5.28 6.78 6.69 6.41 5.91 6.72 6.86 6.73 4.54 5.57 1.99 |

- **齐步、没有任何 tick 线程的精确模式也有同样的慢态**（10 次里 7 次），三种配置慢态的
  比例相近（70% / 92% / 83%），同一组里相邻的两次（不同配置）多半一起快、一起慢。
- 慢态时主控（`master_busy`）和岛（`island_busy`）一起慢 3–5 倍；主控这一段的工作量和
  岛无关，只能是 CPU 本身慢了（核的频率或者被排到能效核上）。和负载高低没有固定关系：
  第一组负载 3–7 时全是慢态，后面几组负载 3–5 时又是快态；起空转进程占核也没有让它稳定
  变快或变慢。
- **结论：慢态是这台机器的调度 / 频率状态，和多岛无关，不用修。** 比较一个岛时的开销
  只能看同一时段交替的相对差距或者微基准（16.3 的每刻约 10 µs）。

六次全部 20 TPS，丢刻 0、判死 0，欠刻在报告时刻最多 3 刻。

- **迟滞 200 → 60 刻没有让岛变多、拆得更勤**：拆分次数反而在同一个范围（每小时 69–95 对
  63–114）。取消的待拆分每次只有 1–7 个（修了 17.2 第一行之后，待拆分几乎都等到了），
  说明拆不开的原因是连通（几处之间一直有人把它们连着），不是等得太久；缩短迟滞只会在
  有人短暂离开又回来时多拆合几次。**不改。**
- **拆分距离 4 → 3**：岛数、拆合次数在噪声内，每刻均值两次都比 `base` 第 1 次高（20.8 /
  19.9 对 17.1，但 `base` 第 2 次负载 23 时也有 21.5），拆合的单次耗时没有变小；合并和拆分
  之间不留余量还会让在边界上来回的人反复拆合。**不改。**
- **合并距离**没有单独试：它是「不同岛的已加载区块不相邻」的余量（计划 3.1），改小只会
  让更近的两群人分开，而这个场景里限制岛数的是路上的人，不是两群人离得近。
- **合并拆分的频率上限**：现在没有显式的上限，频率由迟滞（200 刻）和每 20 刻一次的连通性
  检查决定。长时间轨迹上每小时合并、拆分各 50–150 次，照做前最多等 3 刻（均值约 0.4 刻，
  17.3），单次耗时大多几毫秒；没有需要再加上限的证据。
- **会不会因为参数改坏 17.2 的修复**：三组参数都跑满、不变量（分区器局部不变量）0 失败。
- **线程数**：见 17.5，不改。

结论：**分区器的三个参数（合并 2、拆分 4、迟滞 200 刻）和 `island_threads` 的缺省都不改**；
这一步改的是迟滞的取消规则（17.2 第一行），它是正确性问题，不是参数。它的前后对比：同一个
场景（营地隔 96 个区块）修之前 4.5 分钟合并 5 次、拆分 0 次、取消 42 次，岛数的中位数 1.0；
修之后 20 分钟合并 20 次、拆分 17 次，岛数的中位数 1.12（全程全量对照），关掉全量对照的
十分钟一次里每小时合并 88–145 次、拆分 63–114 次，岛数中位数 1.5–2.0。

### 17.7 口径和限制

- 跨报告的分位数是「各份报告的分位数再取中位数 / 最大」，不是全程精确的分位数
  （`summarize-long.py` 的说明）。
- 一小时那轮开着全量对照，主控每刻多约 15 ms，耗时偏大；调参的六次关着，耗时和它不能
  直接比。调参每组只有两次、每次 10 分钟，机器负载 3–23，只看同一时段的相对差距。
- 假玩家飞着赶路（33 格/秒），主控在区块交付上的负担比走路的服务器重；`moved too
  quickly` 是被传送时正在赶路的那一下。
- 修 17.2 第二行之前的一次 4 分钟试跑里，不变量断言报过一次「玩家 PlayerId(2) 跟踪着别的岛
  7 的区块 (151, 78)」（这名玩家在岛 0；4 秒前刚有一次拆分，之后没有合并）。没能复现：之后
  同样的场景又跑了 10 分钟（2.5 分钟时撞上 17.2 第二行）、12.5 分钟（撞上第三行）、20 分钟
  和 1 小时，全程断言都没再出现；调参的六次只开分区器的局部不变量，也是 0 失败。可能的原因是一次拆分时用的 section 名单是做决定时的，照做前（岛不在手里或者
  有人正在跨岛时会晚几刻）有人移动了；也可能和第二行同源。断言消息已补上玩家所在区块、
  视野中心、两个区块在分区器里各属哪个岛、还有没有没做的拆合，再出现时能直接定位。
  **第 12 步的结论**：第一种猜测写成确定性测试后确实复现了原文，但根因不是名单过期，
  是「按瞬时位置分人 / 按视野中心查就绪」的口径不一致；已修，见 18.5。第二种猜测
  （与 17.2 第二行同源）不由这次修复覆盖，两者是不同的路径。

### 18.4 第 2 项继续优化：批量重建计划刻队列

`TickQueue::split_off` 原来对整条 `BTreeMap` 做 `retain`、把搬走的刻逐条 `insert` 进新树。
它只在 tick 边界的拆合里走，可以整批重建：搬走的多（≥ 1/8）时把有序条目分成两份升序
`Vec`、用便宜哈希判成员、两边都整批建树；搬走的少时仍走原来的就地删（不为几条刻建
散列集合）。排刻热路径一点没变。单元测试 `island_split_rebuilds_both_sides_identically_at_either_size`
在两种规模下都比「从没拆过」的参照逐条相同，改坏确认把成员判定改成恒假时两种规模都失败。

23:43–23:44 同一时段 A-B 交替 5 轮（负载 19–34，噪声比 18.2 大）的效果：

| 场景 | 再做之前 | 批量重建后 | 比 |
|---|---:|---:|---:|
| 对半 20000 区块 dense 拆 | 33.9 | 29.2 | 0.86 |
| 4 岛 × 4900 dense 拼 / 拆 | 24.4 / 59.4 | 22.2 / 50.8 | 0.91 / 0.86 |
| 3 岛 dense 拆 | 30.4 | 24.5 | 0.81 |
| 4 岛 sparse 拼 / 拆 | 7.1 / 14.1 | 7.3 / 14.6 | 1.03 / 1.04 |
| 2 万区块拆 400 块 dense | 2.66 | 2.94 | 1.10（噪声内） |

**收益明显变小了**：dense 的整个世界命令从 ≈ 84 降到 ≈ 73 ms，sparse 没有改善；再往下
要改的是结构，不是某一张表的常数（见下）。按第 12 步的取舍，到这里停。

**剩下的瓶颈和要改的结构**：命令语义要求它看到整个世界一个岛（4.5 的范围表 12 条命令
不变），现在的实现是把每个岛的 `Region` 整个并进发起人的岛、执行完再整个拆回去，
等于把 2 万个区块的所有表搬两遍，下界就是 O(已加载区块数)。要真正进 20 ms，得让命令
不再搬全部数据：例如把「整个世界」做成一层只读视图（按位置路由到各岛的表，写走一次
扇出），或者让这几条命令只作用于涉及的几个岛，并在命令解析阶段就判断范围。后者会改
4.5 的范围语义，这一步按任务书不做，列作建议。**另一个便宜的方向**：`unify` / `divide`
按岛逐个合并 / 拆分，每个岛都要把发起人的整张表碰一遍；改成一次把全部岛按归属切成
K 份可以省掉重复的整表扫描，但要重写 `Islands::unify` / `divide` 和全部的「拆合不改内容」
对照，代价不小。

### 18.5 第 3 项：那次不变量失败查清了，是真问题

第 17.7 的第一种猜测（「拆分用做决定那一刻的名单、照做前有人移动了」）写成确定性测试后
**在正常路径上就复现了 17.7 的原文**：`玩家 PlayerId(1) 跟踪着别的岛 0 的区块 (-3,-3)
（玩家在 (0,0)、视野中心 (0,0)……还有没做的拆合：true）`。这个窗口正式运行也走得到：
死亡重生在岛的这一刻里调 `command::place_player_at_respawn`（`player_respawn.rs`），它
直接把玩家放到任意位置、可能跨岛、不拼整个世界；压测钩子直接放人也是同一条路径。

根因不是名单过期：`apply_split` 在照做那一刻用 `split_parts` 重新收集，所以名单是新的；
但 `split_parts` 按**瞬时位置**分人，而 `split_ready` 只查**视野中心**。直接放人先改位置，
视野要到岛下一次 tick 才跟上；这中间照做拆分时位置与视野中心分在切口两边，玩家被算进
拆出去的一边，随后 `relocate_players` 把他连同旧岛的跟踪区块搬进新岛。那片区块之后的
方块更新只发给新岛自己的玩家，他会永久漏包，所以**不能靠放宽不变量断言来遮**。

修法（`world/island_runtime.rs`）：`split_parts` 按**视野中心**（正在跟踪的区块）分人；
`split_ready` 还要求每名玩家跟踪范围里没有任何一格落在切口另一边，否则推迟拆分、记一条
新指标 `island_split_deferrals`（`summarize-long.py` 打印总数），留给下一次连通性检查按
当时的连通块重新判；「跟踪区块属于本岛」的断言保持严格。推迟有界：视野跟上下一刻就拆，
测试断言 6 刻内消失；推迟计数让长压测能看出有没有忙岛因此永远拆不开（第 11 步那个坑）。

三条确定性测试（都在 `world/island_runtime_tests.rs`，各带改坏确认）：
① 拆分决定与照做之间直接放人；② 重生放置路径（`player_move::place_player`）；
③ 把视野钉在切口上，断言推迟 1 次、6 刻内消失。改坏钩子 `Master::split_by_position`
把分人口径改回瞬时位置并跳过视野检查：① ② 报出 17.7 的原文，③ 当场拆、推迟计数为 0。

**第二种猜测**（和第 17.2 第二行「搬人没等回执」同源）不由这次修复覆盖，两者是不同的
路径：那次修的是「回执交回前不能拆岛」（否则 panic「交回还没处理完就拆岛」），
管的是拆合的时机；这次是「玩家该分到哪一边」，管的是归属。17.2 的修复仍然必要，
本次改动没有动它，两条回归测试都还在。报告里不要写成「第二种猜测已被覆盖」。

| `delivery`（父阶段，混合驱动下只含与岛并行的那段） | 0.94 | 1.18 | Director 每刻推进 |
| `delivery_light_finish` | 0.67 | 2.88 | 交付 / 收回前强行算完光照 |
| `deliver_storage` + `deliver_tables` | 0.34 | 1.05 | 区块柱和各张表放进 region |
| `reclaim_storage` + `reclaim_tables` | 0.24 | 0.79 | 收回的盒子与按位置的表 |
| `levels_update` | 0.27 | 0.52 | 一批交付 / 收回后增量重算 `TickLevels` |
| `encode_body` + `make_frame` | 0.25 | 0.53 | 编区块包体、拼帧（在主控 / 岛线程上） |
| `compress_frame` | 0.97 | 2.62 | 共享帧压缩，**在连接任务里，不进 `tick_total`** |
| `director_ack` / `mail_sort` / `return_boxes` | 0.04 | 0.09 | 回执、信箱排序、交还盒子 |

注意：这些父阶段和子段是两套互不重叠的口径（2 节说明），不能相加；`inbox` 里还含
收包和分区器增量，不全是票 / 交付。真正「票 + Director + 区块交付」相关的子段合计约
2.7 ms/刻，剩下的在收包、出站刷出和收尾里。

可行办法和各自的代价（**都没有实现**）：

1. **把区块编码 / 交付挪到岛上或单独的线程**。现在岛在 tick 线程上跑，但票表、Director、
   区块信箱和 `deliver_*` / `reclaim_*` 都在主控；`encode_body` / `make_frame` 已经在
   连接任务里（`compress_frame` 明确不进 `tick_total`）。把编码整个挪出去，主控只剩
   「投信」和「收信」，理论上能省 `encode_body` 0.21 + `make_frame` 0.03 ms/刻，
   但区块内容是岛的 `ChunkStore`，跨线程要么复制（几 KB/区块）要么加锁，
   编码又要读光照和版本号；共享帧按引用展开的现有设计要改成带所有权的消息。
   **代价大、收益小**，不值得先做。
2. **把票表等级传播和 `TicketTable::run_updates` 挪到岛上**。票是全局的（玩家跨岛、
   强加载票可以落在任何位置），按岛分片要处理跨岛的票传播边界；17.2 的长压测里
   `ticket_update` p95 1.18 ms，不是主要瓶颈。**改的是 Director 的核心不变量**，
   风险最大、收益有限。
3. **让 `inbox` / `flush` / `tick_tail` 里的串行段并行**。这三个父阶段合计 17.7 ms/刻，
   远大于票和交付；但它们含收包（顺序敏感）、出站刷出（按连接分片）和存盘编排，
   和「岛的数目无关」不是同一件事。按玩家 / 连接分片出站刷出可能比动 Director 便宜，
   需要单独量 `flush` 的构成（现在只有一个父阶段，没有子段）。
4. **降低交付 / 收回的批次频率**（批量更大、更少次）。`delivery_light_finish` 和
   `deliver_*` / `reclaim_*` 都跟着批次数走；飞行场景里每刻都在装卸，批量调大能少几次
   全量重算，但会推高 `chunk_latency_us`（玩家看到新区块更晚），要按设计稿 1.2 的
   抖动口径和读盘延迟一起权衡。
5. **先量再动**：给 `inbox` / `flush` / `tick_tail` 补子段计时（和 `delivery` 一样按
   「每刻合计」记），把「5 ms」拆成可归因的几段。这是唯一零行为风险的一步，
   建议放在任何并行化之前。

**结论**：第 17.3 那 5 ms 不是「区块交付」一项，主要是主控的串行收包 / 刷出 / 收尾，
加上票表等级传播与 Director 推进；区块编码和压缩已经在别的线程里，挪动它们的收益
最多 0.25 ms/刻，却要改共享帧和 `ChunkStore` 的所有权。**不建议这一轮动结构**，
先补子段计时再判断。

### 18.7 口径和限制

- 18.2 / 18.4 是微基准，不是服务端整刻停顿：基准只调 `split_off` / `absorb` /
  `unify` / `divide`，不带收包、出站、不变量断言；真实一刻里这些还要排在主控的串行段里。
- 两个二进制共用同一份基准和分段计时，但**改前**那版是「第 11 步 main 的算法 + 新加的
  计时」，和 17.3 一小时压测的二进制不是同一个（那一轮之后 main 又合入了死亡 / 重生）。
  17.3 的 125 / 248 ms 只能当历史背景，不能当同一负载的改前数字。
- 18.2 负载 9.5–20，18.4 负载 19–34；同一时段的 A-B 交替是有效的相对比较，
  跨表（18.2 对 18.4）的绝对值不要直接比。
- 18.6 用的是前任留下的 3 分钟 `islands-roam` 冒烟，不是 10 分钟长压测；
  `BAMBOO_PROFILE_ISLANDS=2` 开着，全量对照每刻多约 6.9 ms。
- 第 2 项「20 ms」是目标不是硬线；dense 上界仍远超，sparse（更接近真实世界）压线。
  没删任何用例、没放宽比较；齐步和精确模式的逐位对照、`BAMBOO_TEST_LOADED=1`、
  探针两种配置都照旧要过。
