## 0. 摘要

1. **三个平面加一个主控。** 网络平面（连接任务）、模拟平面（region）、区块平面（Director 加后台计算池和 IO 线程）。主控只记账和路由，不在每刻的热路径上。
2. **所有游戏逻辑写成“对一个上下文接口的函数”。** 方块逻辑对 `Level`（已经如此），实体逻辑对 `EntityCtx`（新增）。同一份逻辑配不同的上下文：精确（立即生效）、并行（写操作变成命令）、录制（记下读写）、oracle（假世界）。并行和红石缓存都靠这一条，不需要把逻辑写两遍。
3. **区块束是唯一的搬运单位。** 一个区块的方块、光照、方块实体、计划刻、实体索引放在一个盒子里。加载、卸载、存盘、region 合并拆分都是搬盒子。
4. **region 不同步加载区块，隔离带比 Folia 小一半。** 视距 10 时两名玩家相距约 530–640 格就能分属两个 region。
5. **实体阶段分两步：并行算，按顺序落地。** 每个实体的感知、决策、寻路、移动并行执行，只读这一阶段开始时的世界，只写自己；对世界和别的实体的影响变成命令，之后按实体顺序串行应用。结果和线程数无关。
6. **红石热点优化可行，形式是“触发级的记录重放”。** 以一次触发（计划刻、流体计划刻、方块事件或方块实体 tick，见 9.1）为单位，把“读到的状态 → 产生的全部效果”缓存起来，状态相同就直接套用效果。不改变执行顺序，结果和解释执行相同。它不是第一优先，命中率实验已做完，缓存本身还没做。

（2026-11-12 按实现更新：设计稿 9.1 / 9.7、`docs/redstone-cache-experiment.md`）
7. **过载先降玩家看不见的东西**，按固定顺序，有下限。
8. **保留精确模式**：每个维度一个 region、串行、齐步走，所有 oracle 在这个模式下跑。精确和性能是同一套代码的两种配置。

## 1. 现状、目标、指标

### 1.1 现状 `[事实]`

- 一条世界线程：`World { global, region, inbox, host, pacer, .. }`，`World::tick` 串行跑完所有阶段（`mc-bamboo-game/src/world.rs`）。票表、Director 和剖析器也在这条线程上；主控和 region 调度还没建（`docs/profiling.md` 第 2 节、`crates/mc-bamboo-game/src/director_host.rs`）。
- 方块逻辑在 `mc-bamboo-blocks`，全部通过 `Level` trait 读写世界（`level.rs`）；计划刻、方块事件、方块实体各有一个入口函数，返回这一步产生的效果（`run_due_ticks`、`run_block_event_phase`、`run_block_entity_tick`）。`Level` 已拆成 `LevelSideState` / `LevelTables` 和 `LevelEntities` / `EntityTables` 两组「窄接口 + 整表接口」，另有一个默认空实现的 `observe` 钩子报出不经 `Level` 的事件（第 3 节）。
- 区块表是 `ChunkStore { template, edited, light, loaded, pristine }`（`mc-bamboo-world/src/store.rs`）。`template` 仍是超平坦生成器的输出；无限模式（只给测试和 oracle 用）下没改过的区块直接读它，正式入口 `loaded()` 下只有交付过的区块存在，每个已加载区块插进一份自己的 `ChunkColumn`，包体也各编一遍。`take_column` / `insert_column` 把方块、高度图、方块实体类型表、告示牌文字、`update tag` 和两层光照整柱搬走。**不给「没改过的超平坦区块」做共用模板（写时复制）**：真实地形下每个区块本来就各不相同，共用只在超平坦有用；`docs/profiling.md` 9.4 量到 `fly-20` 的 RSS 从约 135 MB 到约 622 MB（约 2.18 万个已加载区块），`docs/performance-optimizations.md` 第 9 节量到 `encode_body` 是 0.23 ms / p99 0.61 ms。
- 票表和 Director 决定谁加载、谁 tick；收回的 `Box<RegionColumn>` 整盒停放在内存里，没改过的直接丢掉重新生成（`crates/mc-bamboo-game/src/region/parking.rs`）。
- 带位置的上层状态在 region 里仍是整张表：`Region.containers`、`Region.block_ticks`、`Region.block_entities`、`Region.redstone`，另有按位置索引的四张表；它们各有按区块的取放接口，`RegionColumn` 把整批盒子（含 `ChunkEntities`）装在一起（`region/column.rs`）。存储内部仍是整张表，见 4.2。
- 实体只有下落方块、点燃的 TNT 和掉落物，没有生物。实体存成 `EntityStore`（公开 / 私有分开、uid 索引、16³ 段的空间索引），逻辑走 `EntityCtx`，有精确和并行两个驱动，并行由 `BAMBOO_ENTITY_THREADS` 切换（缺省精确）；每个实体自带随机源（`mc-bamboo-blocks/src/entity/`）。
- 区块包体在世界线程编码，按（位置，版本号）缓存；区块帧做成 `Arc<SharedFrames>`，压缩结果用 `OnceLock` 惰性缓存，第一条需要它的连接任务压一次，其余复用（`crates/mc-bamboo-game/src/outgoing.rs`）。
- 出站是每名玩家一串片段：`PlayerSink::send(frames: Outgoing) -> bool`，`Outgoing` 区分普通帧和共享帧（`crates/mc-bamboo-game/src/inbound.rs`）。
- 落后 2 秒以内连续追赶（`MAX_CATCH_UP`）。`TCP_NODELAY` 已开。节拍只用 `thread::sleep`（原来默认的 `hybrid` 先睡再自旋和世界线程 QoS 开关，2026-11-12 按用户决定删掉了）。实体线程数、交付 / 收回上限在 `bamboo.toml` 里配（`docs/configuration.md`），剖析器仍是环境变量 `BAMBOO_PROFILE`。没有自定义全局分配器。
- 存档先做**官方的 Anvil 格式**，不兼容 26.3 之前的老存档布局（读到当空世界）。`mc-bamboo-storage` 的区块 NBT、Anvil 区域文件、方块实体 / 计划刻 / 三种实体 / 整块组装的编解码已完成并与官方对拍，但还没接进加载和卸载（`docs/m3-storage.md` 第 2、12 节）。

### 1.2 玩家感觉到的是什么

| 玩家感觉 | 对应的量 | 目标 |
|---|---|---|
| 操作跟手 | 所在 region 的 tick 耗时和起点抖动 | p99 < 45 ms，抖动 < 2 ms |
| 跑图不卡 | 区块从“需要”到“发出”的延迟 | 读盘 p95 < 100 ms |
| 不顿挫 | 存盘、合并拆分、大批区块到达时不突刺 | 单次 < 5 ms |
| 别人卡不拖我 | region 之间隔离 | 别的 region 超时不影响本 region |
| 怪多不卡 | 单个 region 能用上多个核 | 实体阶段随线程数加速 |

### 1.3 不做什么

- 不做多进程、不做中央复制层（讨论稿 4.2、8.9）。
- 不做回滚式的乐观并行（发给玩家的包撤不回）。
- 不引入通用 ECS 框架（理由见 8.2）。

## 2. 总体结构

```text
连接任务（tokio）
   │ 每名玩家一条入站队列            ▲ 每名玩家一个出站缓冲
   ▼                                │
┌──────────── 模拟平面 ─────────────┴──┐
│ Region × N：tick 线程池，按截止时间调度    │
│ 每个 region 内部再把并行阶段拆成子任务     │
└───────┬───────────────────▲──────────┘
  票的增减、离境、            │ 区块交付、到达、
  卸载交还、全局效果          │ 合并拆分、全局快照
        ▼                   │
┌──────────────── 主控 ─────────────────┐
│ Global（20 TPS）+ 每个维度一个 Director   │
│ ticket 表、区块状态、分区器、停放的 region │
└───────┬───────────────────▲──────────┘
        │ 任务（带优先级）    │ 完成
        ▼                   │
 后台计算池（解析、生成、光照、编码、压缩、序列化）+ IO 线程
```

| 部件 | 独占的数据 | 跑在哪 |
|---|---|---|
| 连接任务 | socket、加解密、解码 | tokio，现状不变 |
| Region | 自己的区块束、实体、玩家、随机源、机器缓存 | tick 线程池 |
| Global | 计分板、游戏规则、时间天气、玩家名单、管理名单 | 主控 |
| Director（每维度一个） | ticket 表、每个区块的状态、生成中的 `ProtoChunk`、分区器、停放的 region | 主控 |
| 后台计算池 | 无，只跑纯函数 | 独立线程 |
| IO 线程 | 文件句柄 | 独立线程 |

- **主控是几个 actor**：各有状态和信箱，只靠消息来往。先放在一条线程上，以后要拆不用改设计。它只在有事时醒：票变了、流水线阶段完成了、region 跑完一刻了。
- **region 之间不直接通信。** 发给 region 的消息只有两个来源：主控，和这个 region 里玩家自己的入站队列。所以不需要并发的“位置 → region”路由表，这张表只有主控读写。
- **主控不会成为瓶颈** `[推导]`：200 名玩家都在移动，每人每秒最多跨 2 次区块边界，每次约 40 条票变化，合计约 1.6 万次记账每秒；加上每个 region 每秒 20 次交还和几千次阶段完成。约束是主控里不做超过约 100 微秒的事。**这一条现在只在票的差集上成立**：`set_player` 这一部分实测 ≈ 5 µs/次，正是设计时假设的「几微秒的表操作」；但随后的等级传播每次平均让约 1053 个区块变等级，微观基准里一次移动在优化之前是 301 µs（200 名玩家）/ 289 µs（1 名玩家），`aedaa96`..`b6596f2` 之后是 141 µs / 126 µs，仍没到 80 µs 的目标，单次都超过 100 µs。差集只做到了票，没做到等级；外圈「只到某个生成阶段」的等级继续落表，原因是生成依赖图要用它，所以约一千个区块变等级是固有的。再降要改两阶段传播算法的表示，还没有做、也没有验证。现在只有一个 region、Director 用内联执行器跑在世界线程上，主控和 tick 线程池都还没建，所以这些耗时先算在世界线程的 `inbox` 阶段上（`docs/chunk-tickets.md` 第 5 节、`docs/performance-optimizations.md` 第 7f、9 节、`docs/profiling.md` 第 2 节）。

## 3. 统一的逻辑接口

这是整套架构里最重要的一条约定，后面的并行、缓存、验证都建在它上面。

> 游戏逻辑不直接拿世界的 `&mut`。它只通过一个上下文接口读世界、写自己、提交对外的影响。

| 逻辑 | 上下文接口 | 现状 |
|---|---|---|
| 方块：放置、形状更新、计划刻、方块事件、方块实体 | `Level` | 已有，`mc-bamboo-blocks` 全部如此 |
| 实体：物理、AI、寻路、交互 | `EntityCtx` | 新增（第 8 节） |

同一份逻辑代码，配四种上下文实现：

| 实现 | 读 | 写 | 用途 |
|---|---|---|---|
| 精确 | 当前世界 | 立即生效 | 精确模式；和原版逐位一致 |
| 并行 | 阶段开始时的世界 | 只写自己；对外的影响进命令缓冲 | 性能模式的实体阶段 |
| 录制 | 透传，同时记下读了什么 | 透传，同时记下写了什么 | 红石机器缓存（第 9 节）、调试 |
| 假世界 | oracle 给的场景 | 记录下来和官方比 | `mc-bamboo-vanilla` 的各种 oracle |

方块逻辑这边已经完成的一件准备：方块状态装不下的世界数据（方块实体、方块事件、红石记忆）原先在 `Level` 上以整张表的引用交出去，现在收窄成 `LevelSideState` 里“一次调用一个具体读或写、位置当参数”的方法。`Level` 是 `LevelSideState` 的子 trait，方块逻辑拿到的 `&mut dyn Level` 只能走这些窄方法；用整张表存数据的实现者另实现 `LevelTables`，由 blanket impl 自动得到 `LevelSideState`。按区块存放、或者要录制读写的实现者可以直接实现 `LevelSideState`，不必交出整张表。

实体这一侧照同样的办法拆过一轮：`LevelEntities` 是带位置 / 范围 / uid 的窄方法，`EntityTables` 是整张 `EntityStore` 的接口，`Level: LevelSideState + LevelEntities`，方块逻辑拿不到整表接口。但并行驱动收尾时给 `LevelEntities` 又加了三个**必须实现**的方法（`entities_table`、`entities_table_mut`、`publish_entity_rows`），直接交出整张实体表：任何实现者都得持有一张 `EntityStore`，录制包装对这三个入口只能粗记成「碰了实体」（`docs/redstone-cache-experiment.md`「方法」一节）。把它们挪到单独的 trait 里，照 `LevelSideState` / `LevelTables` 的办法收窄，还没做。

录制也不只是「包住 `Level` 转发一遍」：世界时间、音效和世界事件、计划刻队列的读写都不经过 `Level`，包装看不见。为此 `Level` 上加了一个默认空实现的 `observe(&self, Observation<'_>)`，由方块逻辑那一侧的 `World` 在触发边界、读时间、发效果、查刻、排刻处各调一次；`Observation` 覆盖四种触发边界、时间读、效果、计划刻查询和新排的刻。默认实现为空时只有一次虚调用，实测开销 −0.5% / +1.2%，在噪声范围内（`docs/redstone-cache-experiment.md`「钩子开销」）。计划刻 `BlockTicks` 仍是单独传给驱动力循环的队列，不经过 `Level`；`observe` 让录制能精确记下它的读写。

实体逻辑从第一行起就按这个约定写。**这是对将来生物系统的硬约束：AI 和物理代码里不能出现直接改世界、直接改别的实体的调用。**

## 4. 数据模型

### 4.1 层次

```text
Server
├─ Global            全局状态（第 6.6 节）
└─ Dimension × 3
   ├─ Director        票、区块状态机、分区器
   └─ Region × N
      ├─ chunks       ChunkPos → Box<ChunkColumn>
      ├─ entities     EntityStore
      ├─ players      玩家的会话状态、入站队列、出站缓冲
      ├─ random       这个 region 的随机源
      └─ caches       机器缓存、导航缓存等，随时可以丢
```

### 4.2 区块束 `ChunkColumn`

```text
ChunkColumn
├─ sections       方块和生物群系的调色板容器
├─ light          每段的天空光和方块光（从 LevelLight 搬进来）
├─ heightmaps
├─ block_entities 这个区块里的方块实体，带内容
├─ block_ticks / fluid_ticks  这个区块里的计划刻
├─ entity_index   每段有哪些实体（实体本体在 EntityStore）
├─ poi
└─ revision、dirty、inhabited_time、time_offset
```

- **所有带位置的状态都进区块束**，region 级只留可以重建的索引（哪些区块有到期的计划刻、哪些方块实体要 tick）。这是 R8 的加强版。
- tick 中途才有的队列（方块事件、待广播的方块变化、实体命令）在 tick 边界一定是空的，合并拆分只在边界发生，不用搬。
- 快照就是复制：存盘时在 tick 边界 `clone` 这个区块。一个区块约 50–100 KB，复制约 10 微秒 `[推导：按内存拷贝速度]`。先不做写时复制。
- 读方块的热路径加“上次访问的区块”缓存。并行阶段里区块表是只读共享的；区块内部的惰性缓存（碰撞形状、导航类型）用原子类型或 `OnceLock`，可以在并行阶段里填。

已经做到的（第 1 步在这一层）：`mc-bamboo-world` 的 `ChunkStore` 用 `take_column` / `insert_column`
把方块、高度图、方块实体类型表、告示牌文字（含 `editor`）、`update tag` 和两层光照整柱搬走；
`mc-bamboo-blocks` 的 `BlockTicks` / `BlockEntities` / `RedstoneMemory` 各有按区块的取放接口，
计划刻按相对延迟、红石火把开关记录按相对年龄装盒；`mc-bamboo-game` 的 `RegionColumn` 把这些盒子
和 `containers`、`block_items`、`command_blocks`、讲台上的书按区块切成一份装在一起，
由 `Region::ready_to_move_columns` / `take_columns` / `insert_column` 整批取放，
`RegionColumn: Send`。`Level` trait 对外不变，方块逻辑和 oracle 不受影响。

**存储内部仍然是整张表**：region 里 `containers` 等四张表还是 `BTreeMap<BlockPos, _>`，
`BlockTicks` / `BlockEntities` / `RedstoneMemory` 也还是全 region 一张表，只是都加了按区块的
取放接口；按位置查容器、遍历容器重查开合人数这些路径一处没改，遍历和发包顺序也不变。
按区块取时只扫 `BlockPos` 的 x 带（16 格宽），和计划刻的批量取出一样要求调用方把一批攒齐。
以后真要多 region 并行，这些表再按区块分存，那时才需要改访问代码。

按区块取放已经覆盖到实体：`EntityStore::take_chunk` / `insert_chunk` 和 `ChunkEntities` 装的是这个区块的行和读盘时不认识的实体类型，`RegionColumn` 里也带上了 `ChunkEntities`，收回和交付都走它（`f918171`、`c396f2e`、`865bd3f`）。**还没做**的是把 `entity_tracking` 里的玩家配对也按区块切开：那张表仍是全 region 一张 `BTreeMap`，多 region 并行之前要跟着玩家一起搬。存储内部仍是整张表（见上一段），所以「实体表已有按区块的取放」说的是取放接口，不是分区存放。

`mc-bamboo-world` 里邻居段计数的限制已解决（`2635fe8`，现已合入 main）：柱里的 `sectionStates` 记着相邻段有没有方块，邻居柱里为它记下的计数留在原 store。现在 `take_column` / `insert_column` 会按目标世界此刻的方块重算这一柱和 8 个邻居柱的 26 个段状态（官方 `ThreadedLevelLightEngine.initializeLight` 的登记和 `updateChunkStatus` 的注销），所以单独把一柱放到一圈不同的邻居中间也正确；盒子自带的来源世界计数不跨世界沿用。已加载模式下还按 5.6 的规则给状态非 0 却没有数据层的段补建一层，状态变回 0 的段不丢数据层。

**方块实体里带绝对时刻的字段**：`HopperEntity.ticked_game_time` 和 `PistonMoving.last_ticked` 装在不公开的 `Box<dyn BlockEntity>` 盒子里，仍是绝对时刻，装盒时换算不了。官方根本不存这两个字段，读回来是构造器初值（漏斗的 `TransferCooldown` 是官方存盘的字段，照它读写）；Bamboo 的存档编解码照官方不写它们，单元测试也钉住读回来是初值。所以「存盘后重新加载」不需要换算；跨到模拟时间不同的 region 时照官方「读回来是初值」处理即可，也不需要随 6.3 的 `time_offset` 一起改（多 region 还没实现，这是设计上的结论）。现在只有**红石缓存**需要它们不读世界时间：按 9.3 的规则，漏斗和移动中的活塞读 `game_time()` 就直接判成不能缓存（`docs/redstone-cache-experiment.md` 结论第 4、5 条）。容器条目的 `recheck_at` 已按相对剩余刻数装盒，计划刻和红石火把记录同理。

菜单、`lecterns.views` / `pending`、链路、玩家表和其它与位置无关的字段按 4.4 留在 region，前者跟着玩家走，后者以后搬去 `Global`。跨区块双箱要两半一起搬（也就是「整片相邻区块一起搬」），玩家开着的菜单要求「玩家和他附近的区块一起搬」；`dead` 容器条目和告示牌编辑者原样装盒。

（2026-11-12 按实现更新：`crates/mc-bamboo-blocks/src/entity/store.rs`、`crates/mc-bamboo-game/src/region/column.rs`、`crates/mc-bamboo-blocks/src/archive/tests.rs`、`docs/m3-storage.md` 第 12 节、`docs/redstone-cache-experiment.md` 结论第 4、5 条；合并提交 `f918171`、`2635fe8`、`865bd3f`）

### 4.3 实体存储 `EntityStore`

```text
EntityStore（每个 region 一个）
├─ public: Vec<EntityPublic>   别人能读的部分：位置、速度、包围盒、朝向、类型、
│                              存活、生命值、常用标志、队伍、主人、载具、装备摘要
├─ state:  Vec<EntityState>    只有自己读写的部分：种类数据、AI、导航、物品栏、随机源
├─ grid                        空间索引：每个 16³ 的段里有哪些实体
└─ uid → 行号
```

- **公开和私有分开存**，为的是并行阶段不出数据竞争：每个实体的任务拿自己那一行 `state` 的 `&mut`，再拿整个 `public` 的 `&`。别的实体的数据只能从 `public` 读，读到的是实体阶段开始时的值。这个划分由借用检查器保证，不需要 `unsafe`。
- 一个字段要不要进 `public`，标准是“别的实体的逻辑会不会读它”。
- 实体之间的引用一律用 `uid`，每次重新查，查不到是正常情况（R4）。
- 实体种类用“固定的分层数据 + 种类枚举”：`Base`（所有实体）、`Living`、`Mob`，再加每种自己的数据。这和原版的继承层次对应，移植时一个类对一段数据。
- 玩家也在这张表里（种类是玩家），这样生物能感知到玩家；玩家的连接、物品栏、菜单另存在 `players` 里，用 `uid` 关联。

### 4.4 Region

region 是一个可以整个 move 的值，必须是 `Send`（R2）。它里面只有四类东西：区块束表、实体存储、玩家表、可以丢弃的缓存。现在 `Region` 里的服务器配置、管理名单、对端 IP 这些和位置无关的字段搬去 Global。

## 5. 区块平面（加载架构）

### 5.1 Ticket：照原版（讨论稿 D2 选 A）

- 语义照 26.3：加载票和模拟票两套，`TicketType` 的超时和标志照表，带“存盘”标志的写进 `chunk_tickets`。强制加载、传送门票、珍珠票保持一致。
- 玩家票单独优化：跨区块时只算两个方形视野的差集。其他票数量少，走通用的等级传播。
- region 不直接改票，票的变化是发给 Director 的消息。区块的生死只有 Director 一个入口（R7）。

### 5.2 Director

每个有票的区块一条记录：想要的等级、现在到了哪个阶段、在途任务、归谁（流水线 / 某个 region / 正在存盘）。Director 收到事件就推进状态，把活派出去，自己不干重活。

`ProtoChunk` 和生成依赖图归 Director（D3 选 A）。**region 只会收到完工的区块束**，所以两个 region 的生成依赖范围可以重叠。

### 5.3 流水线

```text
读盘（IO 线程）→ 解压和解析（计算池）
   → [缺什么补什么：structure_starts … terrain … features … light]（计算池）
   → 组装区块束（方块 + 方块实体 + 计划刻 + 实体 + POI）
   → 预编码并压缩区块包（计算池）
   → 交付给 region
```

- 阶段和依赖半径照 `ChunkPyramid`（讨论稿 2.4）。磁盘上 `Status = full` 的区块直接跳到组装。
- **并行规则**：任务声明自己要写的范围（`features` 半径 1，其余 0），写范围不相交的同时跑。原版是一条串行的生成队列。
- **实体和 POI 跟区块一起交付**（D8）：磁盘格式照原版分开存，读的时候并行读，凑齐了才交付。原版是区块先到、实体后到。
- 阶段函数是纯函数：`(阶段, 中心 ProtoChunk, 邻居只读视图) → 中心的新内容`。M4 接世界生成时只需要填这些函数。

### 5.4 优先级、取消、限速

- 优先级 = 离最近的请求者多远，再按用途加权：等着进服或传送的最高，模拟范围内的高于只在视野里的，移动方向前方的高于身后的。
- 玩家每跨一个区块重算；票撤了，没开始的任务直接取消。
- 三层限速：每名玩家的发送速率跟客户端的 `chunk_batch_received` 走（现有 `PlayerChunkSender`）；每名玩家的在途生成数有上限；在途和未交付的区块束有总量上限。
- 规模 `[推导]`：视距 10 的玩家往前走一个区块露出一排 21 个新区块。鞘翅加烟花约 33.5 格/秒，每秒约 44 个。读盘按每个 1.5 ms 算占 0.07 个核；新生成按每个 20 ms 算占 0.9 个核。一名在新地形上飞行的玩家约等于一个核的生成量。两个单位耗时 UNVERIFIED。

### 5.5 交付、卸载、保存

- 区块束通过信箱到达，region 在 tick 开头收，每刻有耗时上限（例如 2 ms），先插近的。
- 票没了 → Director 通知交还 → region 在 tick 边界把盒子移出来发回 → 计算池序列化压缩 → IO 线程写盘。
- **等级决定谁 tick 已经接上**：`Deliver` 带着当时的加载/模拟等级，之后任一套等级跨过
  31 / 32 / 33 边界时发 `LevelChanged`，收回时去掉记录；region 只从这三条消息记账，
  不查 Director 的票表。两套等级都 ≤32、且 3×3 都已交付的区块跑计划刻、流体刻、
  方块事件和方块实体；两套等级都 ≤31、且 5×5 都已交付的区块 tick 实体；逐区块 tick
  （随机刻等）再要求模拟等级 ≤31。两个集合在交付、换档、收回时增量重算受影响的
  半径 1 / 2 邻域，查询是常数时间。可见范围最外面一两圈因此「加载着但不 tick」，
  会 tick 的区块读不到没加载的邻居。「邻居已交付」写成显式判断，给上面的每刻
  交付上限留好位置（内联执行器下交付是当刻完成的，这一条恒成立）。
- 运行中的保存**匀速**进行（D6）：每刻存“脏区块数 ÷ 6000”个，至少 1 个，单区块 10 秒冷却照原版。磁盘结果和 300 秒集中保存一样，IO 是平的。同一区块有新快照时丢掉没写完的旧快照。
- 方块实体照官方 `saveAdditional` / `loadAdditional` 读写，不认识的键原样保留（D9 选 A）。
- 存储格式、崩溃安全见 `m3-storage.md`，这里只规定它接在流水线的哪两头。

### 5.6 光照（D7）

- 生成时的光照在流水线里（`initialize_light`、`light` 两个阶段），不占 tick。
- 运行时的光照留在 region 里，用每刻的时间预算（现状）。它是 region 独占的数据，改动通常很小。
- 已加载模式下，光照存储只为已加载的位置保存区块柱；没加载的位置没有柱、不传光，
  读那里的光照按天空光 15 / 方块光 0。一柱装进不同的邻居中间时按目标世界的方块
  重新登记/注销 26 个段状态，并给状态非 0 却没有数据层的段补建一层；
  状态变回 0 的段**不丢数据层**（邻居柱里从被收走那柱照过来的光要原样留着）。
- **已知差异**：区块不在的时候，紧挨着它的已加载区块里改方块或光源，这些变化的光
  不会传进不在的那个区块；它回来时带的还是走之前的光照。正常游戏走不到这一步：
  能改方块的区块（玩家够得着的、会 tick 的）周围一圈一定是加载好的，只有对着
  可见范围最外一圈用 `/setblock`、`/fill` 才会出现。官方靠外面那 11 圈
  「已加载但不可访问」的区块避免了这个问题，我们没有那 11 圈。见第 13 节第 9 条。

## 6. 模拟平面

### 6.1 Region 的形成

- 网格单位（section）是 4×4 个区块。section 里有已交付或正在交付的区块就是非空。
- 两个 region 的非空 section 切比雪夫距离 ≤ 2 就合并；一个 region 里的两块相距 ≥ 4 并持续 10 秒才拆分。三个数都是配置。
- `[推导]` 不同 region 的已加载区块之间至少隔 8 个区块。视距 10 时 `full` 级区块半径是 12（加载票等级 31，向外两圈到 33）。两名玩家的区块坐标差到 33（约 530 格）才可能不合并，到 36 一定不合并；已经在一起的要拉开到 37–40 个区块（约 590–640 格）并保持 10 秒才拆开。Folia 默认是 69–84 个区块（`folia.md` 2.3）。

**为什么能比 Folia 小** `[推导]`：Folia 的 48 个区块间隔，是因为正在 tick 的 region 可以当场创建 chunk holder、同步加载区块（`folia.md` 2.2 的不变量 2、3）。这里 region 从不当场加载：票是消息，区块是交付来的盒子，半成品不进 region。所以只需要一条不变量：

> **不同 region 的已加载区块不相邻。**

中间隔着没加载的区块，活塞、爆炸、红石、流体都到不了对面，读到的是“未加载”（R6），和原版在已加载范围边缘一样。Director 保证它：一次交付会让两个 region 靠得太近时，先合并再交付。

### 6.2 调度

- region **停放**时在主控手里，**运行**时被 move 给 tick 线程，跑完一刻交回。正在跑的 region 别的线程拿不到，“正在 tick 的 region 不能被合并”由类型系统保证。
- 主控把到期的 region 按截止时间派给 tick 线程池。尽量回到上次的线程。
- 交回时主控依次：应用等着它的结构操作（合并、拆分）→ 算下一次截止时间 → 重新排队。
- 落后时最多连续追赶 2 刻，之后 `下次开始 = max(现在, 理想时间)`。
- 没有玩家、也没有到期工作的 region 按需唤醒。

### 6.3 两种时间（R9）

| | 谁推进 | 用途 |
|---|---|---|
| 世界时间 `GameTime` | Global，固定 20 TPS | 昼夜、月相、天气显示、`/time`、存盘里的 `Time` |
| 模拟时间 `RegionTick` | 每个 region 自己 | 计划刻、冷却、方块实体计时、实体年龄、刷怪节拍 |

- 不卡时两者一比一。region 卡了，它里面的机器整体变慢、相对时序不变，太阳照常走。
- 每个区块束带 `time_offset`，计划刻按区块自己的时间存。合并时只改被吸收方每个区块的 offset。
- 时钟不需要对齐。没有任何东西要比较两个 region 的模拟时间（理由见 6.5），所以不做讨论稿 8.2 的时钟差约束。

### 6.4 合并和拆分

- **合并**：两个 region 都停放着才做，正在跑的那个等它跑完这一刻。小的倒进大的：区块束、实体、玩家并过去，改 offset，信箱接上，随机源留大的那个，各种缓存直接丢。
- **拆分**：只是优化，要迟滞。按 section 做连通性搜索，盒子分给新 region；实体和玩家跟着所在区块走；随机源按 section 坐标顺序从原来的派生。
- 每个 region 带代数，每次拆合加一。

### 6.5 跨 region：离境和到达

哪些东西会跨 region `[推导]`：

- **带票的东西不会“走”出 region。** 玩家和飞行中的珍珠自带票，走到哪区块加载到哪，快靠近别的 region 时先合并。
- **不带票的东西走不出已加载范围。** 生物、掉落物、矿车到了边缘，前面是没加载的区块；原版里它们停止 tick，随区块存盘。

所以跨 region 的只有：传送（`/tp`、传送门、珍珠落地、重生）、掉出已加载范围的实体、跨 region 的命令、全局效果。它们共用一条路：

1. 源 region 把对象从世界里拿掉，整个 move 进 `Depart { 对象, 目的地 }` 发给主控。
2. 主控按目的地处理：区块已在某个 region → 放进它的信箱；是传送而区块没加载 → 挂票（原版的 `portal`、`ender_pearl` 票），交付后送达；是掉出范围的普通实体 → 交给实体存储，下次区块加载时带上。
3. 目标 region 在下一刻开头把它放进世界。

票保证目的地区块一定会来，所以不需要确认和退回；在途的对象不在世界里，所以不需要缓冲对它的交互；主控手里的在途清单就是关服时要保存的东西。消息不带逻辑时钟：多 region 模式不保证跨 region 的先后可重现，按到达顺序处理。

### 6.6 全局状态

三类所有权（讨论稿 8.1）的落地方式：

- Global 每刻发布一份只读快照，region 在 tick 开头取一次。游戏规则、天气、时间、计分板从快照读，最多旧一刻。
- region 对全局的修改是效果消息，Global 下一刻按到达顺序应用。
- 实体 ID：Global 给每个 region 预发号段。
- 战利品随机序列：性能模式下每个 region 按（世界种子、序列名、region 起源 section）派生。
- 命令：目标都在本 region 的当场执行。涉及别的 region 的由主控分发，各 region 下一刻执行并回报，汇总后给反馈，最多晚两刻。
- 入站包：每名玩家一条队列，跟着玩家走；每条带全局递增的到达序号，region 在 tick 开头按序号归并。同一个 region 里两人抢同一个方块，仍然是先到的赢。

（2026-11-12 按实现更新）世界边界也按这套全局状态落了地。官方 `ServerLevel.getWorldBorder()`
按维度各有一份（存在世界的数据存储里），不是全服一份。Bamboo 现在只有主世界、只有一个 region，
权威副本放在 `Global`：它和游戏规则、天气一样是「和位置无关、整维度共用」的状态，
以后一个维度拆成多个 region 时它们必须看到同一份；`Region` 只留一份每刻发布的只读快照，
`RegionLevel` 和实体算阶段的只读视图各带一份，方块逻辑经 `Level` trait、实体碰撞经
`BlockView` 读它。渐变在 `ServerLevel.tick` 开头的 "world border" 阶段推进（天气和时间之前），
权威副本每刻推进后、以及 `/worldborder` 命令改完后重新发布快照。边界不写存档，
`mc-bamboo-blocks::world_border` 提供和官方 `Settings` codec 一一对应的导出 / 恢复函数，
等 M3 的 `data/` 接线。

## 7. 一刻的结构

性能模式下一个 region 的一刻。顺序和原版 `ServerLevel.tick` 相同，只是标明了每一段怎么执行。

| # | 阶段 | 原版对应 | 执行方式 |
|---|---|---|---|
| 0 | 收信箱：区块交付、到达的对象；玩家入站包按到达序号处理 | 处理包 | 串行，有耗时上限 |
| 1 | 运行时光照 | 光照队列 | 串行，有预算 |
| 2 | 取全局快照，推进模拟时间 | 天气、时间 | — |
| 3 | 方块计划刻、流体计划刻 | `tickBlocks`、`tickFluids` | 串行；热点走机器缓存（第 9 节） |
| 4 | 刷怪 | `chunkSource.tick` 前半 | 候选位置并行算，提交串行 |
| 5 | 随机刻 | `chunkSource.tick` 后半 | 串行 |
| 6 | 方块事件 | `runBlockEvents` | 串行；热点走机器缓存 |
| 7 | 实体：算 | `EntityTickList.forEach` | **并行**（第 8 节） |
| 8 | 实体：落地。应用命令，发布公开状态，更新空间索引 | 同上 | 串行，按实体顺序 |
| 9 | 方块实体 | `tickBlockEntities` | 串行；没事可做的休眠（9.5） |
| 10 | 只读收尾：实体追踪、方块变化和实体数据的组包 | 广播 | **按玩家并行** |
| 11 | 区块批次、flush、把票变化和离境对象发给主控 | — | 串行 |

精确模式下 7、8 合成一段（每个实体算完立刻落地），4 和 10 串行，其余相同。

第 10 段要求把广播从“推”改成“拉”：现在是“每个变化 → 找看得见的玩家 → 写进他的缓冲”，改成“每名玩家 → 收集视野里的变化 → 写自己的缓冲”。每个任务只写一名玩家的缓冲，字节不变。

## 8. 实体和生物 AI 的并行

### 8.1 时间花在哪

生物多的服务器里，实体 tick 的开销主要是三块：移动和碰撞、AI（感知、目标选择、行为）、寻路；其余是物品合并、追踪同步。这是公开的性能剖析里常见的分布，UNVERIFIED，Bamboo 自己的分布要等生物做出来再测。

这三块有一个共同点：**绝大部分是读**。读方块算碰撞，读周围实体找目标，读方块做 A*。真正写世界的动作很少，而且集中在几种（攻击、捡东西、踩压力板、开门、破坏和放置方块）。

### 8.2 做法：并行算，按顺序落地

现有的三种实体已经按这个约定写好了。签名（`mc-bamboo-blocks/src/entity/mod.rs`、`entity/ctx.rs`）：

```text
fn tick(me: &mut Entity, ctx: &mut dyn EntityCtx)
fn emit(&mut self, command: Command, me: &mut Entity)
fn apply(command: Command, me: &mut Entity, world: &mut World)
```

`me` 是发出者的完整视图，显式传给 `emit`：算阶段里驱动已经把这一行从实体表里取出来，落地函数可以直接改它，`emit` 之后 tick 函数看到的就是改完的自己。所有命令共用 `apply` 一个落地入口，两种驱动调的是同一个函数。

`EntityCtx` 现在提供：

| 能力 | 并行上下文里的实现 |
|---|---|
| 当前 uid、本刻参与 tick 的 uid（升序） | 从实体表取出阶段的行清单 |
| 读方块、流体高度、光照 | 只读的 `BlockView`（批量读有默认逐格实现；这次物理代码还没用） |
| 读别的实体、范围查询（按 uid 升序访问） | `public` 快照加空间索引，值是实体阶段开始时的 |
| 读写自己的状态 | `&mut Entity`，独占；不另设 `ctx.me()` |
| 随机数 | 实体自带 `Entity.random`（原版每个实体也有自己的随机源 `[事实]`）；世界随机源不在这里，意图命令在 `apply` 里跑完整原逻辑，取数顺序和精确模式相同 |
| 对世界和别的实体的影响 | `ctx.emit(command, me)`，进这个线程的命令缓冲 |

**第 7 段（算）**：`compute(只读方块视图, &mut EntityStore, 执行器) -> Computed` 把实体状态移出表、并行执行 `tick`，产出新状态、命令和移除标记。**还没实现**：载具和它的乘客、被拴着的一串算一个单位、在同一个任务里按原版顺序跑这条规则；现有三种实体没有载具、拴绳和乘客。

**第 8 段（落地）**：`commit(Computed, &mut World)` 先发布新公开状态、更新空间索引，再按（uid 升序，实体内序号）串行应用命令；`apply` 有整个 region 的 `&mut`，直接改世界、别的实体和发出者，没有回写补丁。发出者已被前面的命令移除时整批跳过。游戏层在两段之间重新构造 `World`，因为 `RegionLevel` 独占借着区块表。

命令按**意图**而不是底层操作划分，现有五种（`Command`，`entity/ctx.rs`）：

| 意图 | 做什么 | 现有冲突语义 |
|---|---|---|
| `Explode` | TNT 引信归零：整段爆炸，射线、洗牌、逐格破坏、连锁点燃、掉落和伤害物品 | 按 uid 升序落地，一条命令里跑完整的原逻辑 |
| `LandFallingBlock` | 下落方块这一刻的落地判定和后果：放不放得回去、发哪种事件、要不要掉成物品、自己消不消失 | 算阶段把只读事实带进命令，落地不重算 |
| `MergeWithNeighbours` | 与附近的物品合并 | 候选按 uid 升序，落地时重新读双方当前状态，后到的看到对方已变就作废 |
| `SuckIntoHopper` | 漏斗吸取，写容器也写发出者自己 | 跑 `HopperBlock.entityInside` 的整段 |
| `DropItem` | 生成一件掉落物 | 新实体下一刻才开始 tick |

给以后生物和 AI 预留、这次没有实现的意图：`ChangeBlock`、`TriggerBlock`、`Damage`、`Push`、`Spawn`、`Remove`、`ScheduleTick`、`Depart`。「先到的生效」「推力累加」这些冲突规则要等真有这些命令时逐个对着原版定（第 17 节第 5 条）。

性质：

- **结果和线程数无关。** 算的时候只读不变的快照和自己，落地的顺序是固定的。同样的输入一定得到同样的结果。
- **和原版的差异不止一条**：实体看到的别的实体是这一阶段开始时的样子，不是排在它前面的实体刚动完的样子；另外 `emit` 之后的语句在性能模式里先于命令落地执行。在现有三种实体上具体表现为三类，每一类都有回归测试钉住，逐条列在第 13 节第 5 条（物品合并少看一拍、爆炸的击退晚一刻体现在物理上、漏斗吸走后物品自己这一刻的 `age` 和位置仍按未被吸走算）。这些语句不依赖命令的结果，所以两种模式不会走上不同的逻辑分支。
- **精确模式用同一份代码**：精确上下文让读取看到当前世界、`emit` 当场调 `apply`，驱动按原版顺序逐个执行；语句顺序和迁移前一样，所以逐位一致是结构保证的。现有的下落方块、TNT、掉落物和它们的 oracle 走的就是这条路。
- 依赖冲突结果的自身变化（“捡到了才加进物品栏”）放在命令的处理函数里做，那时有完整访问权。tick 函数不能根据 `emit` 之后自己的状态分支。

**为什么不用通用 ECS 框架**：原版的实体逻辑是继承形的，一个实体的一刻是一段连贯的、顺序敏感的代码；精确模式要求按原版的实体顺序整段执行。通用 ECS 按组件把逻辑拆成系统、按系统遍历，和这两点都冲突。这里只取它的两个做法：公开数据连续存放，写操作走命令缓冲。

（2026-11-12 按实现更新：`crates/mc-bamboo-blocks/src/entity/ctx.rs`、`entity/parallel.rs`、`entity/mod.rs`、设计稿第 13 节第 5 条、`docs/performance-optimizations.md` 第 5 节；合并提交 `f918171`、`b99f8b5`）

### 8.3 AI 的各部分怎么落进来

| 部分 | 原版里是什么 | 在这套结构里 |
|---|---|---|
| 感知 | `Sensor`、`NearestAttackableTargetGoal` 等，查附近实体、视线检查 | 读 `public` 和空间索引，并行 |
| 决策 | `GoalSelector`、`Brain` 的行为和记忆 | 读写自己的状态，并行 |
| 寻路 | `PathFinder` 的 A*，读方块算节点类型 | 纯函数，在实体自己的任务里跑，并行 |
| 移动 | `MoveControl`、`Entity.move`，和方块碰撞 | 读方块、写自己的位置，并行 |
| 实体间挤压 | `pushEntities`，当场改双方速度 | 读快照里的位置，发“推力”命令 |
| 动手 | 各种会改世界的 Goal 和 Behavior | 发命令 |

原版的 Goal 和 Behavior 可以一对一移植：它们本来就是“读世界、改自己、偶尔动一下世界”，把“动一下世界”换成 `emit` 即可，不需要人为拆成两个函数。

### 8.4 寻路

寻路是实体 tick 里最容易出尖峰的部分，单独列出做法：

1. **节点类型缓存**：每个区块段缓存“这一格对某类生物是可走、阻挡还是危险”，惰性填充，方块变了按段失效。并行阶段可以安全地填（原子写，重复填的结果相同）。原版也有这样一层缓存（`PathTypeCache`）`[事实：官方 26.3 的类]`。
2. **同刻去重**：同一刻里起点格、终点格、生物尺寸和导航类型都相同的请求只算一次。结果和各算各的相同。
3. **每刻预算**（性能模式）：一个 region 每刻的寻路总耗时有上限。超了的请求顺延到下一刻，生物这一刻沿用旧路径或原地等待。这是降级阶梯的一级（第 10 节）。
4. **跨刻寻路**（以后）：特别长的路径拆成后台任务，算好了下一刻交给生物。原版也会在路径失效时重算，生物本来就容忍路径晚到。
5. **群体流场**（以后，开关）：很多生物追同一个目标时，从目标向外算一次距离场，每只生物沿梯度走。路径和原版 A* 不同，默认关。

### 8.5 刷怪

原版每刻对每个可刷怪的区块按类别尝试。候选位置的检查（碰撞、亮度、方块类型、上限统计）是只读的，按区块并行算；通过的候选按区块顺序串行提交，上限在提交时再查一次。每个区块用自己派生的随机源，所以随机数序列和原版不同（性能模式的差异 3）。

### 8.6 能快多少 `[事实：Bamboo 自己的基准]`

压力场景：3000 个掉落物加 300 个下落方块挤在一片平地上，release，每刻跑 10 次取总和再除以 10。
手工复现：`cargo test -p mc-bamboo-blocks --release --lib entity::parallel::tests::stress -- --ignored --nocapture`。

收尾优化之后的分段耗时（ms/刻）：

| 线程数 | 复制 | 算 | 发布 | 落地 | 整刻 |
|---|---|---|---|---|---|
| 1 | 0.061 | 3.942 | 0.218 | 0.002 | 4.22 |
| 2 | 0.056 | 2.401 | 0.210 | 0.002 | 2.67 |
| 4 | 0.056 | 1.131 | 0.207 | 0.002 | 1.39 |
| 8 | 0.056 | 0.789 | 0.206 | 0.002 | 1.05 |

单线程算占整刻约 93%；8 线程整刻比 1 线程快约 **4.0 倍**。串行部分（复制、发布、落地）
合计约 0.28 ms/刻，其中发布是主要的一项，8 线程时它占整刻约 20%，决定了上限。

收尾优化之前同一场景的分布是：单线程复制 0.03、算 3.4、发布 0.66、落地 1.28 ms/刻，
8 线程整刻只快约 1.8 倍。落地那 1.28 ms 全部是 `SuckIntoHopper`（10 刻共 30000 条命令，
即每刻 3000 条；爆炸、落地、合并、掉落命令都是 0 条；每条扫一小片格子找漏斗，
量到 1.56 ms/10 刻的处理时间）。世界里没有漏斗时两种驱动都不再发这条命令，这部分归零。
其余改动把发布从 0.66 降到 0.21 ms/刻左右（不再每刻重建空间索引和整张实体表）。

这只是「三千个掉落物挤在一起」的场景，实体逻辑全是物品和下落方块。**生物的 AI 和寻路
占比会不同，还没有量。** 8.1 里「85% 在算」的假设现在只对这一个基准成立，不能外推。

落地阶段在这个基准里已经不是瓶颈，按空间分组并行（棋盘着色，讨论稿第 10 节第 3 档）
先不做；等剖析器在有生物的负载里证明它是瓶颈再说。

### 8.6.1 两段式接口和开关 `[事实]`

`compute(只读方块视图, &mut EntityStore, 执行器) -> Computed` 算出每个实体的新状态、命令和移除标记，
`commit(Computed, &mut World)` 发布状态并按（uid 升序，实体内序号）串行应用命令。游戏层在
两段之间重新构造 `World`，因为 `RegionLevel` 独占借着区块表，没法同时借出只读视图。

`bamboo.toml` 里的 `entity_threads=<n>`（见 `configuration.md`）经 `ServerConfig` 和
`WorldConfig` 传给 `World`：0 是精确驱动（原行为），≥ 1 用并行驱动，n 是线程数
（1 表示走并行代码路径但单线程，用来对比）。算阶段用一份只读的
`ChunkStore` 视图，落地阶段照现在的办法构造 `RegionLevel`。执行器现在用 `ScopedThreads`，
**每刻起线程，开销大，只用于实验**；常驻线程池是任务系统（第 12 节）的事，这次不做。

剖析器把并行驱动的实体阶段记成 `entity_compute`（算）和 `entity_commit`（发布、落地、发效果）
两段；精确驱动仍是 `entities` 一段。

### 8.7 和 region 的关系

两层并行是叠加的：玩家分散时靠多个 region；玩家和生物扎堆在一个 region 时，靠这个 region 的实体阶段和收尾阶段吃满线程。Folia 只有前一层。

## 9. 红石热点优化（“JIT”）

### 9.1 结论

**可行，而且和现有架构很合。** 安卓那套结构可以照搬：解释执行、统计热点、热点换成更快的执行方式、条件不满足时退回解释。

要调整的是“把每次运行结果保存下来”的粒度。按“整台机器的一次运行”存，边界难定，机器之间的先后也容易弄错。**按“一次触发”存**就没有这些问题：

> 一次触发 = 四种驱动循环里的一条边界之间的全部读写，加上它引起的全部连锁更新：
> 一条到期的方块计划刻、一条到期的流体计划刻、一个方块事件，或方块实体 ticker 的一次 tick。
> 缓存的内容 = 这次触发读到的全部状态 → 它产生的全部效果。

四种是命中率实验里实际用的口径（`docs/redstone-cache-experiment.md`「触发的边界」）。只算计划刻和方块事件的话，漏斗链、物品分类机和熔炉的工作全在方块实体 tick 里，一次触发也录不到。边界由方块逻辑那一侧的 `World` 在 `Level::observe` 上报 `TriggerBegin` / `TriggerEnd`，结果按种类分开统计。

下次同一个触发到来时，如果它会读到的状态和记录时完全相同，就不再解释执行，直接套用效果。

（2026-11-12 按实现更新：`docs/redstone-cache-experiment.md`「方法 / 触发的边界」、`crates/mc-bamboo-blocks/src/level.rs` 的 `Trigger` / `Observation`；合并提交 `bec0707`）

### 9.2 为什么结果一定相同 `[推导]`

- 方块逻辑是确定的：一次触发的连锁更新只取决于它读到的东西。读到的都相同，执行路径就相同，写出的也相同。
- **执行顺序不变**：触发仍然按原版的（时间、优先级、子序号）一个个处理，只是其中一些从“解释”换成了“套用”。所以不需要判断机器的边界，也不存在机器之间先后弄错的问题。
- 缓存只是缓存，任何时候整个丢掉都不影响正确性。区块卸载、region 拆合时直接丢。

因此它在精确模式下也成立，可以直接用现有的方块 oracle 验证：开着缓存跑，应该仍然是 0 不一致。

### 9.3 设计

**录制**：`Recording` 直接实现 `Level`、`LevelSideState` 和 `LevelEntities`（不经过 `LevelTables` / `EntityTables`），每个方法先转发再记下这次读（位置、类别、值）或写；不经过 `Level` 的状态由 `observe` 补进来，驱动循环在四种触发的开头和结尾各报一次边界。这样绕开的世界时间、对外的效果、`has_scheduled_tick` / `will_tick_this_tick` 的查询结果、新排的计划刻都被精确记下，不必用「pending 差分 + 读过的每格都算进键」的保守近似。得到：

- 读集合：读了哪些位置的方块状态、两层亮度、告示牌、方块实体（含内部物品栏和数据槽）、红石记忆、容器槽位 / 模拟信号 / 双箱位置、游戏规则、天气、高度图、掉落表、发射器目标，以及计划刻查询和上面那些 `observe` 项；按读的先后顺序进键。
- 效果：写序列（方块、红石记忆、方块事件、方块实体的增删、容器、新排的计划刻、对外效果）加不可缓存标记。写方块记最终值，不含中间的邻居更新过程。

**键**：实验比了三种键（`docs/redstone-cache-experiment.md`「三种键」）。精确键 = 触发本身 + 全部读项按调用顺序的 64 位哈希；纯段哈希键 = 触发本身 + 读集合涉及的每个 16³ 段的整段方块状态哈希（128 位，写方块时增量异或更新）+ 非方块状态读项的精确值；混合段哈希键是两者的组合，留作对照。命中还要求那次记录的效果和这次相同；九台机器、约 16.4 万次触发、54 行统计里「键相同但效果不同」为 0。

段哈希比读集合粗：同一段里无关的东西变了也会让键不同，但它把键压小了 4–330 倍（红石线阵列 9 MB/条 → 27 KB/条）。实测它在多数机器上只比精确键低 0–0.1 个百分点，遇到几条时钟在同一段里交错写的「互质时钟汇合」掉 6.5 个百分点、记录数从 98 涨到 427。第一版可以就用纯段哈希，热点段里机器互相干扰时再细化到「每台机器一个哈希域」。

**不能缓存的触发**（录制时发现就不存）：实验里的「严格」口径就是这四条规则，命中的判定见 `docs/redstone-cache-experiment.md`「两种口径」。

| 读了什么 | 实测的例子 | 原因 |
|---|---|---|
| 随机数 | 投掷器和发射器选格子、掉落物的初速度；**活塞伸出 / 收回各取一次世界随机源算音效音高**（`PistonBaseBlock.triggerEvent`，每次只取 1 个数） | 结果不由状态决定 |
| 范围里有实体 | 活塞推实体、漏斗吸掉落物、压力板；漏斗上方没有容器时每次 tick 都扫实体表找掉落物 | 实体状态不在键里 |
| 世界时间、墙上时间 | 阳光探测器；**漏斗的 `tickedGameTime` 和移动中的活塞的 `lastTicked`** | 不重复。实测这是最大的拦路虎：漏斗链、分类机 100%，熔炉阵列 66.7%，活塞门 85.7% 的触发只因为读 `game_time()` 就不能缓存 |
| 内容一直在变的方块实体 | 熔炉的烹饪进度单调增长（不是「物品在流动的漏斗链」，那一条的真正原因是上一行的时间读） | 状态不重复，存了也命中不了；熔炉严格口径 4000 刻里记录数线性涨到 16000 条、约 19 MiB，命中率 0% |

“范围里没有实体”可以进键：记录时查到是空的，套用前再确认还是空的。

活塞的那 100 次方块事件占这台机器 51.5% 的耗时，取数只决定音效参数、不决定方块状态。可以考虑把「取一个数、按公式算音高、发音效」整体记成一条效果，重放时仍从世界随机源取这个数，否则后面所有用世界随机源的逻辑都会和解释执行不同。**2026-11-12 用户定了采用这个办法**（不改成自己的随机源，结果和官方逐位一致），排在方块实体休眠之后做；还没有实现。

**热点判断和退出**：每个区块段数“每秒执行了多少触发”，持续超过阈值才开始录制。每个触发点记命中率，长期命中不了的停止录制，过一段时间再试。每个 region 的缓存有内存上限，按最近使用淘汰。这三条是第一版缓存里**必须**有的：熔炉阵列就是「命中不了还一直录」的内存反例（`docs/redstone-cache-experiment.md` 结论第 6 条）。

**套用**：按记录写方块（走不触发邻居更新的底层写入，但照常登记“这一段变了”供广播和光照使用）、排计划刻、排方块事件、发音效。写的同时更新段哈希。实验只量了「算」，套用时省不掉的写、光照和发包还没有量。

（2026-11-12 按实现更新：`docs/redstone-cache-experiment.md`「方法 / 结果 / 活塞门的随机数 / 结论」、`docs/world-model-design.md` 9.4、9.7；合并提交 `bec0707`）

### 9.4 能快多少，对什么没用

`[推导]` 解释执行一次触发，每改一个方块要通知 6 个以上的邻居，每个邻居再读十几到几十个方块来算形状和信号。套用只需要一次查表加若干次底层写入。所以收益和“每次触发的连锁有多长”成正比，纯信号传递的部分可能有一个数量级，UNVERIFIED。

| 机器 | 效果 |
|---|---|
| 时钟、脉冲电路、显示屏 | 状态周期性重复，命中率高。**实测 98%–99.8%**，只要几条到几十条记录 |
| 反复开关的活塞门 | 原来预测“命中率高”，**按现在的规则实测一条也缓存不了**：活塞伸缩时取一次世界随机源算音效音高，移动中的活塞每刻读世界时间。把这两处处理掉之后是 96.5% |
| 观察者加活塞的收割机 | 信号传递的那几刻能命中；破坏作物、产生掉落物的那一刻不能 |
| 计数器、红石计算机 | 状态很少重复，命中率低，占内存。适合 9.6 的编译方式。**还没有被真正检验**：实验里没有搭出状态单调累加的电路 |
| 漏斗链、物品分类机 | 基本无效。**实测的原因比“状态不重复”更靠前**：漏斗每次 tick 都读世界时间算冷却，按 9.3 直接不缓存。忽略时间读的话命中率 99% 以上，但只省两成多的时间 |
| 刷怪塔、村民交易所 | 开销在实体，不在红石。靠第 8 节 |

还有一点要清楚：**套用省掉的是“算”，省不掉“写”。** 红石灯亮灭引起的光照更新、发给客户端的方块变化，一样要做。

### 9.5 先做这些更便宜的

它们都不改变结果，实现简单，而且对上表里“无效”的那几类机器正好有效：

1. **方块实体休眠**：熔炉没有燃料和原料、漏斗没东西可搬也没东西可吸时，从 tick 列表里摘掉，登记唤醒条件（物品栏变了、邻居变了、有物品实体进入上方）。漏斗是生存服里最常见的开销来源之一。**2026-11-12 用户把它扩展为“睡到下一个事件”**：正在烧的熔炉也不必每刻跑，算出这一个物品烧完、燃料烧完哪个先到，睡到那一刻、在原来的运行顺序位置醒来；外部变化立刻叫醒重算，睡着时被读的值（界面进度条、存盘）按公式现算，结果和官方逐位一致。正在做。
2. **容器引用缓存**：漏斗记住它朝向和上方的容器是谁，邻居变了再重查。
3. **信号查询缓存**：同一刻里对同一位置的 `getSignal` 之类的查询记下结果，该位置或邻居被写时失效。
4. **红石线算法做成选项**：原版红石线断电时的更新量很大。26.3 自带一套实验性的算法：特性开关 `FeatureFlags.REDSTONE_EXPERIMENTS`，实现是 `ExperimentalRedstoneWireEvaluator`，和默认的 `DefaultRedstoneWireEvaluator` 并列 `[事实：官方 26.3 的类]`。可以照它移植一份作为可选项，并用 oracle 在打开这个特性的条件下对比。它和默认算法的更新顺序不同，所以是开关，默认关。它具体快多少 UNVERIFIED。**已决定先不做，保持默认算法。** 要做的话不只是换一个类：开关打开后按钮、拉杆、中继器、侦测器、红石火把、活塞等十几个类发邻居更新时都要带上 `Orientation`；来向未知时它还会读世界随机源，这类触发按 9.3 不能缓存。

### 9.6 以后：编译成网表

对大型纯逻辑电路（红石计算机），更合适的是把一片静态的红石编译成节点和连线的图，直接在图上跑，不再逐方块更新。这是“真正的 JIT”，收益最大，工作量也最大：每种元件都要写编译规则，还要和原版的更新顺序对齐。已有先例是 MCHPRS（一个专门跑红石的 Rust 服务端），凭印象它不支持活塞、方块一变就要重新编译，UNVERIFIED。

这一层只在有人真的在服务器上造计算机时才值得做。到时候同样用“守卫加退回”的结构，并用 9.2 的办法验证：编译执行和解释执行跑同一段，逐刻比较。

### 9.7 动手之前先做的实验

> **已做，结果在 `redstone-cache-experiment.md`。** 要点：九台机器约 16 万次触发，“键相同但效果不同”为 0；纯信号电路命中 98%–99.8%；9.3 第一版的段哈希键在多数机器上只比精确键低 0–0.1 个百分点、键小 4–330 倍；读世界时间（漏斗的冷却、移动中的活塞）是最大的拦路虎，把这些绝对时刻改成相对量后活塞门和漏斗类机器才用得上缓存；熔炉这类进度单调增长的方块实体缓存不了，要靠 9.5 的休眠。实验只量了“算”，没有量套用时省不掉的写、光照和发包。上面 9.4 的表已按实测更正。

不写缓存，只在解释器里加统计：每次触发记（触发点，读集合的哈希，耗时，读和写的数量），离线算“如果有缓存，命中率是多少，能省多少时间”。在几种典型机器上跑（时钟、活塞门、分类机、农场、一台小计算机）。命中率和可省时间都高，再做 9.3。

## 10. 过载和降级

每个 region 一个控制器，盯着最近的 tick 耗时。超过预算（例如 40 ms）往下降一级，恢复后逐级升回。顺序按“玩家越看不见越先降”：

| 级 | 降什么 | 下限 |
|---|---|---|
| 1 | 这个 region 的存盘速率、运行时光照预算 | 存盘不停，只是变慢 |
| 2 | 区块发送速率、非模拟范围区块的插入预算 | 玩家脚下 3×3 不限 |
| 3 | 寻路预算（8.4 第 3 条）、远处实体的追踪更新频率 | 16 格内不降 |
| 4 | 远处生物的 AI 频率（Pufferfish DAB 的思路） | 32 格内不降 |
| 5 | 这个 region 的有效模拟距离 | 不低于配置的下限（默认 4） |

- 3–5 级会改变远处的行为（刷怪塔效率等），各自可以关。
- 都降完还超时，这一个 region 的 tick 速率自然下降，别的 region 不受影响。
- 讨论稿 8.6 的按 region 时间膨胀放在这之后做实验：先用真客户端验证 `ClientboundTickingStatePacket` 在低于 20 时是否平滑，UNVERIFIED。

## 11. 网络平面

1. **区块包只压缩一次。** 协议的压缩按包进行，加密在压缩之后按连接进行 `[事实：现有压缩和加密层的顺序]`，所以压好的区块包帧对所有玩家都一样。流水线交付前把帧做好，按（区块，版本号）缓存；区块改了在计算池里重做。
2. **出站缓冲分段。** `PlayerSink::send` 从一整块 `Vec<u8>` 改成一串片段，区分“原始帧，要压缩”和“已做好的帧”。共享的区块帧不再复制进每名玩家的缓冲。
3. **压缩后端和等级**：区块帧可以用更快的 zlib 实现和更低的等级，字节和原版不同，协议上等价。要用真实地形测体积和耗时再定。
4. 解码、心跳留在连接层。每名玩家仍然只有 region 一个写入者，包的先后和现在一样。

## 12. 任务系统

| 线程 | 数量（默认） | 跑什么 |
|---|---|---|
| 连接 | 2 | tokio |
| 主控 | 1 | Global、Director |
| tick 线程池 | 其余的一半以上 | region 的 tick，以及 region 内的并行子任务 |
| 后台计算池 | 至少四分之一 | 解析、生成、光照、编码、压缩、序列化 |
| IO | 2 | 读写文件 |

三条要求：

1. region 的 tick 按截止时间派发。
2. region 内的并行阶段（第 7、10 段）拆成子任务，空闲的 tick 线程可以拿去做。只有一个大 region 时，它能用上整个 tick 线程池。
3. **正在等自己子任务的线程，只能帮着做子任务，不能去开始另一个 region 的 tick。** 否则它自己的 region 要等那个 region 跑完才能继续。这条排除了“把 region tick 和子任务丢进同一个普通的工作窃取池”的做法。

其他：

- tick 线程空闲、并且离下一个 region 到期还有余量时，可以帮后台计算池干活；计算池的线程不跑 tick。
- tick 线程用高优先级并绑到性能核，IO 和存盘用低优先级。本机是 10 个性能核加 4 个能效核 `[事实]`。
- 精确模式和测试用内联执行器：提交的任务当场跑完，结果可重现。

## 13. 两种模式和差异清单

| | 精确模式 | 性能模式 |
|---|---|---|
| region | 每个维度一个 | 动态拆合 |
| tick | 所有维度齐步走，按原版顺序 | 各走各的 |
| 实体阶段 | 逐个算完立刻落地 | 并行算，按顺序落地 |
| 后台任务 | 内联执行 | 计算池 |
| 机器缓存 | 可开（结果不变） | 开 |
| 用途 | oracle、probe、单元测试、调试 | 正式运行 |

**所有 oracle 继续在精确模式下跑。**

性能模式相对原版的差异：

1. 跨 region、跨维度的传送晚一刻到达。
2. 全局状态的读取最多旧一刻；跨 region 的命令反馈最多晚两刻。
3. 每个 region 有自己的随机源和战利品随机序列；刷怪每个区块有自己的随机源。
4. 不同 region 之间事件的先后不固定。
5. 实体看到的别的实体是这一刻实体阶段开始时的样子。这一条在现有三种实体上
   具体表现为下面三类，每一类都有回归测试钉住（`crates/mc-bamboo-blocks/src/entity/parallel/tests.rs`）：

   1. **物品合并少看一拍。** 精确模式下 uid 小的物品先 tick，可能当场把 uid 大的物品
      合并掉，后者这一拍不再 tick；性能模式里所有物品都先算完，落地时按 uid 升序应用
      `MergeWithNeighbours`，后者的命令看到对方已变就作废。差别是后者这一刻多跑了一次
      物理和年龄，最多晚一刻合并。
   2. **爆炸的击退晚一刻体现在物理上。** 精确模式下 TNT 爆炸当场伤害并击退排在它后面、
      还没 tick 的物品；性能模式里那些物品已经算完，击退要等下一刻才影响位置。
   3. **漏斗吸走物品后，物品自己这一刻的 `age` 和位置仍按未被吸走算。** 精确模式下
      `HopperBlock.entityInside` 在物品 tick 里同步改容器和物品自己；性能模式把它变成
      `SuckIntoHopper` 命令，物品这一刻剩下的语句已经跑完。

   `emit` 之后的语句在性能模式里先于命令落地执行，具体是这几处，逐条列出：
   - 下落方块：`LandFallingBlock` 之后的 `delta *= air_drag`、写回 `kind`（累积 `time`）、
     `set_requires_precise_position`；
   - 点燃的 TNT：`Explode` 之后的 `set_requires_precise_position`；
   - 掉落物：`SuckIntoHopper` 之后本拍的其余伤害循环；`MergeWithNeighbours` 之后的
     `age += 1`、第二次流体扫描、6000 刻超时判定。
   这些语句不依赖命令的结果（`EntityCtx` 的硬约束：tick 不能根据 `emit` 之后自己的状态分支），
   所以差别只体现在「别人何时看到」，不会让两种模式走上不同的逻辑分支。

   不属于差异的：方块状态、`Effect` 顺序、实体 ID 分配、新实体的随机源播种、
   `level.random` 的消费序列。意图命令在串行落地阶段跑完整的原逻辑（含所有世界随机数），
   所以这些和精确模式逐位相同。两种模式共用一个 `apply`，命令按（uid 升序，实体内序号）
   落地；发出者若已被前面的命令移除，它的命令整批跳过。

6. region 卡的时候，它的模拟时间比世界时间慢。
7. 过载时按第 10 节降级。
8. 区块包的压缩字节不同；实体随区块一起到达；存盘匀速进行。
9. **区块不在时的光照不跟着邻居更新。** 一个区块卸载后，紧挨着它的已加载区块里
   方块或光源变了，这些变化的光不会传进不在的那个区块；它重新加载时带的还是
   走之前的光照，边界上可能和邻居对不上。原版靠可见范围外面那 11 圈
   「已加载但不可访问」的区块避免了这个问题（那些区块仍参与光照计算），
   这里在等级 34 就把区块收走，没有那 11 圈。正常游戏走不到这一步：能改方块的
   区块（玩家够得着的、会 tick 的）周围一圈一定加载好了，只有对着最外一圈用
   `/setblock`、`/fill` 才会出现。见 5.6 节。
10. **等级 34 就装盒收走，计划刻的到期时刻是相对的。** 官方把等级 34–45 的区块
   留在内存里（那 11 圈「已加载但不可访问」的区块），计划刻按绝对 `gameTime` 存，
   区块回到能 tick 的状态时按原到期时刻一次补跑。这里等级 34 就把区块装盒收回，
   盒子里的计划刻是相对延迟，放回来时还没到期的刻整体往后挪「被收走的时长」。
   收走之前区块已在等级 33 冻结了一段时间（还有 100 刻的收回延迟），短延迟的刻
   那时都已到期，装盒时相对延迟是负数或 0，放回后立刻补跑，和官方一致；只有
   延迟超过冻结时长的刻才有差别。官方自己存盘再读回时用的也是相对延迟，所以
   这条差异只在「同一局里区块被收回又重新交付」时出现。见 5.5 节。

同一个 region 内部，性能模式的结果仍然是确定的：同样的输入、不同的线程数，结果相同。这让性能模式自己也能做回归测试。

## 14. 生命周期

**玩家进服**：连接层完成登录 → Global 准入（封禁、白名单、同名）→ Director 在出生点挂票 → 区块交付到某个 region → 玩家作为“到达”对象进入 → region 下一刻开头放进世界并发进服序列。

**玩家离开**：连接结束 → 入站队列里出现 `Leave` → region 移除玩家，把玩家数据快照发给主控存盘 → Global 更新名单。

**关服**：Global 广播停止 → 各 region 跑完当前这一刻后交还全部区块束和玩家数据 → Director 等所有写入落盘 → 在途的离境对象按目的地写回。

**出错**（R12）：任何 region 的 tick 里 panic 都是全局致命错误，停止所有 region，走关闭流程。

## 16. 实施顺序

每一步都能单独合并、单独测量。前五步不改变任何可观察的行为。

| 步 | 内容 | 得到什么 | 状态 |
|---|---|---|---|
| 0 | 剖析器：每个 region、每个 tick 阶段的耗时直方图；区块从请求到发出的延迟；各队列长度；tick 起点抖动；主控处理延迟 | 后面每一步的依据 | **做了一部分**：`mc-bamboo-game` 的剖析器、假玩家压测工具和基线已落地（`a1fd1a0`、`b841143`、`docs/profiling.md`），阶段直方图、墙上时间的区块延迟、起点抖动 / 刻间隔偏差、flush 字节数、按阶段和子项拆分都有；「主控处理延迟」要等主控建起来才有，`chunk_latency_us` 只覆盖排队到写出、不含读盘，和 1.2 的「读盘 p95 < 100 ms」不是一个量 |
| 1 | 数据模型：区块束；光照和带位置的状态进区块；`Level` 的写入口收窄（第 3、4 节） | 存档、合并拆分、录制的前提。oracle 全绿是验收条件 | **做了一部分**：`Level` 已收窄成 `LevelSideState` / `LevelTables` 和 `LevelEntities` / `EntityTables`（`0442bc4`、`f918171`），`ChunkStore::take_column` / `insert_column`、`RegionColumn::take_columns` / `insert_column` 和实体的按区块取放都能整盒取放（`2b2d5f5`、`a62f179`、`5c1c0d9`、`c396f2e`、`f918171`），每一步的 oracle 都全绿。**存储内部仍是整张表**：`ChunkStore` 是「模板 + 改过的表 + 四份光照表」，计划刻、方块实体、红石记忆和容器等四张表仍按全 region 存，只加了按区块的取放接口（见 4.2）；`LevelEntities` 上又开了三个交出整张实体表的入口，还没收窄到单独 trait（见第 3 节） |

## 17. 风险和要先测的东西

1. **“不同 region 的已加载区块不相邻”是多 region 的地基。** 第 5 步要有专门的随机测试：随机移动玩家，每刻断言不变量。
2. **小网格带来更多合并拆分。** 每次合并要等两边都停下，快的一方最多白等慢的一方一刻。第 5 步要测合并频率和等待时间，不行就调大网格。
3. **实体并行的收益取决于“算”的占比**。第 7 步已经做完，3000 个掉落物加 300 个下落方块的压力场景里，收尾优化之后单线程算占整刻约 93%、8 线程整刻快约 4.0 倍，上限由「发布」那 0.21 ms 决定（8.6）。优化之前串行部分占三分之一以上（复制 0.03、发布 0.66、落地 1.28 ms/刻）、8 线程只快 1.8 倍，原因不在设计而在实现：每个掉落物每刻都发一条「被漏斗吸」的命令、空间索引每刻重建，两处都改掉了。**落地阶段不用着色并行**：在这个基准里它只占 0.002 ms/刻，等剖析器在有生物的负载里证明它是瓶颈再说。还没量的是生物的 AI 和寻路；现在 `ScopedThreads` 每刻起线程，并行驱动只能做实验（8.6.1、`docs/performance-optimizations.md` 第 5 节）。

   （2026-11-12 按实现更新：设计稿 8.6 / 8.6.1、`docs/performance-optimizations.md` 第 5 节；合并提交 `f918171`、`b99f8b5`）

4. **`public` 里放什么会不断被追加。** 每加一个字段都增加每刻的拷贝量。要有评审规则：只有被别的实体的逻辑读到的才能进。
5. **命令落地的语义要逐个对着原版定。** “后到的看到状态已变就作废”在大多数情况下合理，但每种命令都要想一遍原版里两个实体同刻抢同一个东西会怎样。
6. **机器缓存的收益已有命中率实验。** 9.7 的实验做完（`docs/redstone-cache-experiment.md`）：九台机器约 16.4 万次触发、严格和乐观两种口径、三种键，「键相同但效果不同」为 0；纯信号电路精确键命中率 98.1%–99.8%、可省 96.0%–99.7% 的「算」的时间，只要 3–98 条记录（6 KiB–4.3 MiB）。活塞门、漏斗链、分类机、熔炉按现在的规则用不上缓存，原因和乐观口径的上界见 9.3、9.4。还要测的：写屏障给普通写方块增加的开销（预期是一次分支）、**套用时省不掉的写、光照更新和发包**（实验只量了「算」），以及真正单调累加的计数器式电路。缓存本身还没实现。

   （2026-11-12 按实现更新：`docs/redstone-cache-experiment.md` 结论、设计稿 9.4 / 9.7；合并提交 `bec0707`）

7. **主控是单点。** 它卡住，所有 region 的重新排队都会晚。
8. **广播从推改成拉**在“变化很多、玩家很少”时可能更慢，第 2 步两种都测。
9. **各平台的睡眠精度**影响 tick 起点抖动（**2026-11-12 用户决定不追求精确节拍**：`hybrid` 和 QoS 开关废弃，下面是当时的实测记录），剖析器直接显示，也已经有实测：原来的 `thread::sleep`（现在叫 `plain`）每刻起点稳定晚 3–5 ms、刻间隔偏差 p50 1.3–1.5 ms / p99 4.5–7.3 ms（`docs/profiling.md` 第 5b 节）；默认的 `hybrid`（先睡再自旋）把 p50 降到 0.01–1.5 ms、p99 降到 3.9 ms，**仍没到 1.2 的 2 ms**，原因是 `thread::sleep` 有时睡过头 9 ms 以上、超过 6 ms 的自旋上限。代价是每刻自旋 0.5–2.4 ms，占一个核的 1%–5%（`docs/profiling.md` 第 5c、7 节、`docs/performance-optimizations.md` 第 6 节）。把上限调大能不能解决、要多付多少自旋，没有测；Linux 和 Windows 上两种睡法的表现也没有测。把世界线程设成用户交互级 QoS 对睡过头的幅度没有可测影响，默认不开；绑核没有做。

   （2026-11-12 按实现更新：`docs/profiling.md` 第 5b / 5c / 7 节、`docs/performance-optimizations.md` 第 6 节；提交 `3cfb30c`、`e9a555d`）

10. 文中提到的外部实现（Moonrise 的区块调度、MCHPRS、Pufferfish DAB）都是凭印象写的，没有在这次核对源码。原版的类名（`Sensor`、`GoalSelector`、`Brain`、`PathFinder`、`MoveControl`、`pushEntities` 等）对着官方 26.3 的 jar 确认过存在，具体行为要在移植时逐个读。用到它们的那一步开始前，照 `folia.md` 的方式读一遍，只取思路。
