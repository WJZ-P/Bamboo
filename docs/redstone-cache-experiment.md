# 红石机器缓存命中率实验

对应 `docs/world-model-design.md` §9.7 的「动手之前先做的实验」。**没有实现缓存**，
只测量：解释执行时录制每次触发读到什么、写了什么、花了多久，离线算「如果有缓存，
命中率是多少、能省多少算的时间」。录制不改变行为。

复现：

```bash
cargo run --release -p mc-bamboo-hit-rate --bin hit_rate -- 4000 > report.md
cargo run --release -p mc-bamboo-hit-rate --bin bench -- 5
```

`hit_rate` 对每台机器同时跑两份世界，一份套 `Recording`、一份不套，逐刻比较世界状态；
输出的是本文的全部数字。`bench` 是不套录制包装的钩子开销基准。

## 方法

### 触发的边界

`Level` 上加了一个默认空实现的 `observe(&self, Observation<'_>)`。`World` 在四种驱动循环
每次触发的开头和结尾各报一次：到期的方块计划刻、到期的流体计划刻、方块事件、
方块实体 ticker 的一次 tick。**后两种是对设计稿 9.1 定义的扩展**：设计稿只算了计划刻和
方块事件，但漏斗、分类机、熔炉的全部工作都在方块实体 ticker 里，不加边界就量不到它们。
结果按种类分开列出。

一次触发 = 一条边界之间的全部读写（包括它引起的连锁邻居更新）。`observe` 还把不经过
`Level` 读写方法的状态报出来：读世界时间、对外的效果（音效 / levelEvent / 方块事件包）、
`has_scheduled_tick` / `will_tick_this_tick` 的查询结果、新排的计划刻（相对延迟和优先级）。
所以计划刻队列的读写是**精确记录**的，没有用设计稿 §9.7 / 任务书里那个「pending 差分 +
读过的每格都算进键」的保守近似。默认实现是空的，正常执行时只有一次虚调用。

### 键

- **精确键** = 触发本身（种类、位置、方块 / 流体 / 方块实体类型）+ 这次触发读到的全部
  （位置、类别、值的 64 位哈希），按读的先后顺序。顺序进键是刻意的：读集合相同但顺序
  不同说明执行路径不同。读项覆盖 `Level` / `LevelSideState` 上的每个读方法：方块状态、
  两层亮度、告示牌、头颅音效、方块实体（含内部物品栏和数据槽）、红石记忆、
  容器槽位 / 模拟信号 / 双箱位置、`is_unobstructed`、游戏规则、天气、天空可见性、
  高度图、降水条件、掉落表、发射器目标、实体接口、计划刻查询，以及上面那些 `observe` 项。
- **段哈希键** = 精确键 + 读集合涉及的每个 16³ 区块段的**整段方块状态哈希**（128 位，
  写方块时增量异或更新）。设计稿 9.3 的第一版打算只用段哈希；这里把精确读集合也留在
  键里，因为段哈希只含方块状态，容器、红石记忆、计划刻查询这些非方块状态只能由精确
  读项补上。这样段哈希键**不会比精确键粗**：同一段里无关的方块变了也会失配，
  命中率不高于精确键。这是本次实验对 9.3 口径的一处收紧。

「命中」= 这个键在这次运行里之前出现过，而且那次记录的效果和这次相同。效果 =
写序列（方块、红石记忆、方块事件、方块实体的增删、容器、新排的计划刻、对外效果）
加不可缓存标记。方块实体 ticker 把实体临时拿出去再放回去不算效果，只是驱动的实现细节。
**键相同但效果不同的次数在八台机器上全部为 0**（见下表），没有发现录制漏洞。

### 两种口径

| 口径 | 定义 |
| --- | --- |
| 严格 | 读了随机数、碰了实体、读了世界时间，任意一条满足就不缓存（设计稿 9.3 的规则） |
| 乐观 | 忽略「读世界时间」这一条，只看随机数和实体；并把记录里带绝对时刻的字段换成相对量。这是「如果把这些时间比较改成相对量，最多能到多少」的上界 |

时间读的来源逐台列在下面。本次全部是 `minecraft:hopper`（`tickedGameTime`）和
`minecraft:moving_piston`（`lastTicked`）；红石火把的烧毁窗口在场景里没被触发。

### 机器

八台都摆得出来，没有跳过。方块直接按状态摆进稀疏的假世界，再给需要起振的方块排一条
计划刻；周期性输入统一用「这一格在红石块（满信号）和空气之间翻转」+ 邻居更新，
等价于一个由实验程序驱动的开关。

| 机器 | 摆法 |
| --- | --- |
| 中继器时钟 | 4 个中继器（2 刻档）串成一列 + 一小段红石线 + 一盏红石灯，输入每 8 刻翻转 |
| 侦测器时钟 | 两个侦测器直接对脸，A 的背面接一盏灯，起振后排 2 刻脉冲往复 |
| 活塞门 | 2×2 四个粘性活塞分两列朝中间推，门块是石头，红石线绕到两列背后，输入每 40 刻翻转 |
| 红石线阵列 | 15×15 的红石线，一格中继器把输入放大成方波，边上接一盏灯，输入每 12 刻翻转 |
| 漏斗链 | 12 个漏斗朝东首尾相接，源头箱子 3 组物品，末端一个箱子，每 8 刻补货 |
| 物品分类机 | 4 个「漏斗 + 减法比较器 + 红石线」单元并排，上游一条 8 格漏斗链送物品，每 8 刻补货 |
| 计数器 | 4 组「中继器 + 比较比较器 + 减法反馈比较器 + 红石灯」，输入每 10 刻翻转 |
| 熔炉阵列 | 4 个烧铁矿的熔炉，每个上下各一个漏斗，末端箱子，每 40 刻补货 |

### 近似与影响方向

- **耗时含录制开销**。每条记录的纳秒是 `Instant::now()` 到触发结束，里面含记哈希、
  维护段快照、追加 Vec 的时间。所以「可省耗时占比」是**上限，偏高**。
- **段哈希只含方块状态**，不含光照、容器、红石记忆、计划刻。精确读项补上了后三者，
  光照在本次机器里不参与方块逻辑。段内无关方块变化会让段哈希失配（命中率偏低）。
- **读集合按调用顺序进键**，比集合语义更严，命中率偏低；好处是执行顺序不同的触发
  不会误命中。
- **只统计 4000 刻内见过的键**，第一次出现按「未命中」计，所以短机器的命中率略偏低。
  记录数增长曲线在 500 刻处就已平掉，这个偏差在几千刻的尺度上可忽略。
- **假世界是稀疏的 HashMap**，没有区块加载、发包、光照引擎和玩家。9.4 里「套用省不掉
  写、光照更新、发包」那部分开销不在测量范围内，因此「可省耗时」只对应「算」。
- **实体开销不在场景里**：漏斗上方没有可吸的物品实体，但漏斗 tick 仍会调 `entity_ids()`
  遍历实体表，按 9.3 的规则「碰了实体」就标记不可缓存。这是保守的，命中率偏低。
- **周期输入（翻红石块、补箱子）发生在触发边界之外**，不计入任何触发，也不进键。
  它只影响读到的状态。

### 录制不改变行为

八台机器各跑 4000 刻，开录制和不录制两份世界逐刻比方块状态、容器内容、红石记忆的
可见读、世界随机源种子、排队的计划刻：**0 刻不一致**。`mc-bamboo-blocks` 的单元测试也
覆盖了录制包装的转发（`recording::tests`）。方块 oracle 和 machine oracle 的基线不变
（见下）。

## 结果

每台跑 4000 刻。`不能缓存` 是严格口径；`命中率` 的分母是可缓存触发数；
`可省耗时` 是命中的那些触发的耗时之和占全部触发耗时的比例（精确键、严格口径）。
`记录数` = 运行里出现过的不同精确键数；`漏洞数` = 键相同但效果不同的次数。

| 机器 | 触发数 | 不能缓存 | 精确命中率 | 段哈希命中率 | 可省耗时（精确） | 记录数 | 漏洞数 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 中继器时钟 | 2490 | 0.0% | 99.5% | 99.4% | 99.3% | 12 | 0 |
| 侦测器时钟 | 3333 | 0.0% | 99.8% | 99.8% | 99.8% | 5 | 0 |
| 活塞门 | 702 | 100.0% | — | — | 0.0% | 0 | 0 |
| 红石线阵列 | 333 | 0.0% | 99.1% | 99.1% | 99.2% | 3 | 0 |
| 漏斗链 | 48000 | 100.0% | — | — | 0.0% | 0 | 0 |
| 物品分类机 | 48000 | 100.0% | — | — | 0.0% | 0 | 0 |
| 计数器 | 3985 | 0.0% | 99.5% | 99.4% | 99.5% | 20 | 0 |
| 熔炉阵列 | 48000 | 66.7% | 0.0% | 0.0% | 0.0% | 16000 | 0 |

### 每台的分布、口径差异和增长曲线

#### 中继器时钟

- 触发 2490 次，全部是方块计划刻；平均每刻 0.6 次，有触发的刻 998 / 4000，
  每刻触发数 min 1 / p50 2 / p90 3 / max 3。
- 每次触发读位置数 p50 15 / p90 25 / p99 25；写位置数 p50 2 / p90 2 / p99 3；
  耗时 p50 46 µs / p90 138 µs / p99 152 µs（含录制开销）。
- 不能缓存 0 次；严格和乐观口径相同（没有时间读）。
- 严格精确 2478 / 2490（99.5%），段哈希 2476 / 2490（99.4%），可省耗时 99.3%。
- 不同精确键数：第 500 刻已经到 12，之后到 4000 刻一直是 12；段哈希是 14。
- 平均每条记录读 33 项、写 1 项、涉及 3 个段，约 1368 字节；12 条缓存记录约 16 KiB。

#### 侦测器时钟

- 触发 3333 次，全部是方块计划刻；有触发的刻 2000 / 4000。
- 读位置数 p50 12 / p90 16 / p99 16；写 p50 2 / p90 3 / p99 3；
  耗时 p50 116 µs / p90 205 µs / p99 231 µs。
- 不能缓存 0 次。严格精确 3328 / 3333（99.8%），段哈希同为 99.8%，可省 99.8%。
- 不同键数第 166 次触发时就到 5，之后不变；5 条记录约 6 KiB。

#### 活塞门

- 触发 702 次：方块事件 100 次（占耗时 50.9%，平均读 188.7 项）、
  方块实体 tick 602 次（49.1%，平均读 29.9 项）。有触发的刻 298 / 4000。
- 读位置数 p50 1 / p90 40 / p99 42；写 p50 1 / p90 3 / p99 3；
  耗时 p50 0.6 µs / p90 179 µs / p99 206 µs。
- **全部不能缓存**：随机数 100 次（伸出 / 收回的方块事件取一次世界随机源算音高），
  时间 602 次（全部是 `minecraft:moving_piston` 的 ticker 读 `game_time()`），实体 0 次。
- 乐观口径（忽略时间读）下 602 次触发的精确命中率仍是 **0.0%**，602 条记录全部不同：
  活塞动画的进度每刻推进半格，状态不重复。
- 平均每条记录读 52 项、写 3 项、2 个段，约 2088 字节。

#### 红石线阵列

- 触发 333 次，全部是计划刻；有触发的刻 333 / 4000。
- 一次触发就是整片线的一次功率重算：读位置数 1178（p50/p90/p99 相同），
  写位置数 183；耗时 p50 12.0 ms / p90 28.8 ms / p99 30.9 ms。

  这是八台里内存最贵的：精确读集合按调用次数记，跑一次整片更新就是几十万项。

### 精确键 vs 段哈希键

| 机器 | 精确严格 | 段哈希严格 | 差值 |
| --- | --- | --- | --- |
| 中继器时钟 | 99.5% | 99.4% | −0.1 pp |
| 侦测器时钟 | 99.8% | 99.8% | 0.0 pp |
| 红石线阵列 | 99.1% | 99.1% | 0.0 pp |
| 计数器 | 99.5% | 99.4% | −0.1 pp |
| 熔炉阵列 | 0.0% | 0.0% | 0.0 pp |

最大差值 0.1 个百分点。原因见「键」一节：段哈希键里带着精确读集合，段里无关方块的
变化只额外打掉极少数几次命中。9.3 里「第一版先这样，命中率不够再细化」的担心，
在这八台机器上没有出现。

### 钩子开销

`observe` 的默认实现是空的，但经过 `dyn Level` 是一次虚调用。按主代理的要求，
在**不套录制包装**的情况下，release，对中继器时钟和红石线阵列各跑 10000 刻，
每轮 5 次取最小，共 3 轮，和加钩子之前的提交 `790fc69` 对比：

| 机器 | 加钩子前最小 | 加钩子后最小 | 差 |
| --- | --- | --- | --- |
| 中继器时钟 | 73.985 ms | 73.633 ms | −0.5% |
| 红石线阵列 | 6439.710 ms | 6513.907 ms | +1.2% |

把每轮的最小值再取全局最小：加钩子前 73.985 / 6439.710 ms，加钩子后
73.633 / 6513.907 ms，分别 −0.5% 和 +1.2%。**都不到 2%**，在测量噪声范围内
（同一配置连续三轮的抖动本身就有 ±2%）。按约定不需要换成不走虚调用的做法。

| 「时钟、脉冲电路、反复开关的活塞门、显示屏：状态周期性重复，命中率高」 | 中继器时钟 99.5%、侦测器时钟 99.8%、红石线阵列 99.1%，记录数在 500 刻内平掉；**活塞门 0.0% 可缓存**（移动中的活塞读世界时间，伸出 / 收回取随机数），乐观口径也只有 0.0% | **部分对上**。时钟类完全对上；活塞门这一项没对上：在 Bamboo 现在的方块实现下它整台机器都进了「不能缓存」名单，不是命中率高，而是根本进不了缓存 |
| 「观察者加活塞的收割机：信号传递的那几刻能命中；破坏作物、产生掉落物的那一刻不能」 | 本次没有摆收割机（要作物破坏和掉落物）；纯侦测器时钟 99.8% 命中，没有不能缓存的触发 | **没测这一行**。能确定的只是「纯信号传递的那几刻」确实高命中 |
| 「计数器、红石计算机：状态很少重复，命中率低，占内存。适合 9.6 的编译方式」 | 本次的 4 位计数器 99.5% 命中、20 条记录、51 KiB，第 199 次触发后记录数就不涨了 | **没对上**。因为这台计数器的状态其实周期性重复（输入每 10 刻翻转，比较器输出跟着回到同一组值），不是 9.4 设想的那种「状态很少重复」的计算机。要检验这一行得摆一台真正累加的、状态单调增长的电路；本次场景不足以否定预测 |
| 「漏斗链、物品分类机：物品在流动，状态不重复，基本无效」 | 严格口径下两台都 100% 不能缓存，命中率无从谈起；乐观口径（忽略时间读）下 99.6% / 99.4% 命中，但可省耗时只有 21.7% / 28.3% | **对上**。而且原因比 9.4 写的更靠前：不是「状态不重复」，是**漏斗 tick 每次都读 `game_time()`**，按 9.3 的规则直接不缓存。乐观口径说明：真把时间改成相对量后，大部分漏斗 tick 其实是重复的空转，能省下两成多的算的时间 |
| 「刷怪塔、村民交易所：开销在实体，不在红石。靠第 8 节」 | 没有摆（世界里没有生物和村民） | **没测** |
| 「收益和每次触发的连锁有多长成正比，纯信号传递的部分可能有一个数量级」 | 红石线阵列一次触发读 1178 个位置、写 183 格、耗时 12.0 ms（p50；p90 28.8 ms），命中后能省 99.2% 的算的时间；中继器时钟一次触发只读 15 个位置、46 µs，命中率同为 99%+ | **方向对上**：连锁越长，命中后省下的绝对时间越多（12.0 ms vs 46 µs，差两到三个数量级）。但命中率本身和连锁长度无关，两类都是 99%+，所以「一个数量级」说的是绝对耗时，不是命中率 |

## 结论

1. **纯信号电路值得做缓存**：中继器时钟、侦测器时钟、红石线阵列、这台计数器在
   4000 刻里精确键命中率 99.1%–99.8%，可省 99.2%–99.8% 的「算」的时间，
   只需 3–20 条记录（6–51 KiB），记录数在头 500 刻就平掉。这是 §9.7 要的正信号。
2. **精确键和段哈希键差 0–0.1 个百分点**。9.3 第一版用段哈希不会明显损失命中率，
   代价是段哈希键里还是要带精确读集合（本次口径），内存并不比精确键省。
   红石线阵列的精确读集合极大（每次触发 28 万项、约 9 MB/条），真要做缓存时
   这一台要么按段存、要么直接走 9.6 的编译路线，不能按调用次数存读项。
3. **读集合的漏洞数 0**：八台机器、约 16 万次触发里，没有一次出现「键相同但效果不同」。
   这是「录到的读集合足以决定效果」的必要检查，过了。
4. **时间读是最大的拦路虎**：漏斗链、物品分类机 100%，熔炉阵列 66.7%，活塞门 85.7%
   的触发只因为读了 `game_time()` 就不能缓存。读时间的行为只有 `minecraft:hopper`
   的冷却 / `tickedGameTime` 和 `minecraft:moving_piston` 的 `lastTicked`。
   若把这些绝对时刻改成相对量（乐观口径）：漏斗链 99.6%、分类机 99.4% 命中，
   可省 21.7% / 28.4% 的算的时间；活塞门仍然 0%，熔炉阵列只有 3.2%（烹饪进度
   每刻加一，状态不重复）。**改时间表示对漏斗类机器有明显收益，对活塞和熔炉没有。**
5. **活塞门按现在的规则完全用不上缓存**：移动中的活塞读时间、伸出 / 收回取世界
   随机源，100% 落在不能缓存里；就算忽略时间读，动画进度每刻推进半格，
   602 次触发的键全不相同。9.4 把活塞门列进「命中率高」与本次数据不符。
6. **熔炉阵列是内存反例**：严格口径 16000 条记录、曲线随刻数线性增长、
   约 18 MiB，命中率 0%。它正是 9.3 里「长期命中不了的停止录制」该拦住的那类。
7. 本实验只量「算」，量不到 9.4 提醒的「套用省不掉写、光照更新、发包」。
   决定做不做缓存前，这部分的开销还得单独量。
8. `observe` 钩子的虚调用开销在 release、10000 刻、取最小的基准里不到 2%，
   不需要改成不走虚调用的方案。
