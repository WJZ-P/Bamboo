# 红石机器缓存命中率实验

对应 `docs/world-model-design.md` §9.7 的「动手之前先做的实验」。**没有实现缓存**，
只测量：解释执行时录制每次触发读到什么、写了什么、花了多久，离线算「如果有缓存，
命中率是多少、能省多少算的时间」。录制不改变行为。

复现：

```bash
cargo run --release -p mc-bamboo-hit-rate --bin hit_rate -- 4000 > report.md
cargo run --release -p mc-bamboo-hit-rate --bin bench -- 5
```

`hit_rate` 对每台机器同时跑两份世界，一份套 `Recording`、一份不套，逐刻比较世界状态；
输出的是本文的全部数字。`bench` 是不套录制包装的钩子开销基准。

## 方法

### 触发的边界

`Level` 上加了一个默认空实现的 `observe(&self, Observation<'_>)`。`World` 在四种驱动循环
每次触发的开头和结尾各报一次：到期的方块计划刻、到期的流体计划刻、方块事件、
方块实体 ticker 的一次 tick。**后两种是对设计稿 9.1 定义的扩展**：设计稿只算了计划刻和
方块事件，但漏斗、分类机、熔炉的全部工作都在方块实体 ticker 里，不加边界就量不到它们。
结果按种类分开列出。

一次触发 = 一条边界之间的全部读写（包括它引起的连锁邻居更新）。`observe` 还把不经过
`Level` 读写方法的状态报出来：读世界时间、对外的效果（音效 / levelEvent / 方块事件包）、
`has_scheduled_tick` / `will_tick_this_tick` 的查询结果、新排的计划刻（相对延迟和优先级）。
所以计划刻队列的读写是**精确记录**的，没有用设计稿 §9.7 / 任务书里那个「pending 差分 +
读过的每格都算进键」的保守近似。默认实现是空的，正常执行时只有一次虚调用。

录制包装直接实现 `Level`、`LevelSideState` 和合并后的 `LevelEntities` 三个 trait，
不经过 `LevelTables` / `EntityTables`。凡是经过实体窄接口的读写都只标记「碰了实体」，
不再细分。

### 三种键

- **精确键** = 触发本身（种类、位置、方块 / 流体 / 方块实体类型）+ 这次触发读到的全部
  （位置、类别、值的 64 位哈希），按读的先后顺序。顺序进键是刻意的：读集合相同但顺序
  不同说明执行路径不同。读项覆盖 `Level` / `LevelSideState` / `LevelEntities` 上的每个
  读方法：方块状态、两层亮度、告示牌、头颅音效、方块实体（含内部物品栏和数据槽）、
  红石记忆、容器槽位 / 模拟信号 / 双箱位置、`is_unobstructed`、游戏规则、天气、
  天空可见性、高度图、降水条件、掉落表、发射器目标、实体接口、计划刻查询，以及上面
  那些 `observe` 项。
- **纯段哈希键**（设计稿 9.3 第一版）= 触发本身 + 读集合涉及的每个 16³ 区块段的
  **整段方块状态哈希**（128 位，写方块时增量异或更新）+ 那些「不在方块状态里」的读项
  的精确（位置，类别，值）。方块状态类读项只进段哈希；红石记忆、方块实体内容、
  容器内容、计划刻查询、亮度、告示牌等仍按精确值进键。段内容全相同则读到的方块状态
  一定相同，所以它天然不粗于精确键。
- **混合段哈希键** = 精确读集合 + 各段整段状态哈希。这是第一版实现里为「保证不比精确
  键粗」而把精确读集合塞进段哈希键的口径，留作对照。

「命中」= 这个键在这次运行里之前出现过，而且那次记录的效果和这次相同。效果 =
写序列（方块、红石记忆、方块事件、方块实体的增删、容器、新排的计划刻、对外效果）
加不可缓存标记。驱动循环把方块实体临时拿出去再放回去、取事件、开 / 关 ticker 阶段、
ticker 的内部递增 id 都是实现细节，不进读集合也不进效果；否则周期性开合的活塞门
明明状态重复，键却永远不同。由世界随机源决定的音效音高 / 种子也不进效果。
**键相同但效果不同的次数在九台机器、严格和乐观两种口径的全部 54 行统计里都是 0**。

### 两种口径

| 口径 | 定义 |
| --- | --- |
| 严格 | 读了随机数、碰了实体、读了世界时间，任意一条满足就不缓存（设计稿 9.3 的规则） |
| 乐观 | 忽略「读世界时间」这一条，只看随机数和实体；并把记录里带绝对时刻的字段从键里排除 |

方块实体内部由绝对游戏时刻决定的字段（漏斗 `tickedGameTime`、移动活塞 `lastTicked`）
单独记成一种读项，乐观口径把它和 `game_time()` 读项一起排除。这是「如果把这些时间
比较改成相对量，最多能到多少」的上界。

时间读的来源逐台列在下面。本次全部是 `minecraft:hopper`（`tickedGameTime`）和
`minecraft:moving_piston`（`lastTicked`）；红石火把的烧毁窗口在场景里没被触发。

### 机器

九台都摆得出来，没有跳过。方块直接按状态摆进稀疏的假世界，再给需要起振的方块排一条
计划刻；周期性输入统一用「这一格在红石块（满信号）和空气之间翻转」+ 邻居更新，
等价于一个由实验程序驱动的开关。**用红石块而不是直接写拉杆的状态**，原因：
直接改拉杆的方块状态不会走玩家右键拉杆时那套对所附着方块的邻居更新，
后面的中继器看不到；这是摆法的问题，不是方块行为的问题。

| 机器 | 摆法 |
| --- | --- |
| 中继器时钟 | 4 个中继器（2 刻档）串成一列 + 一小段红石线 + 一盏红石灯，输入每 8 刻翻转 |
| 侦测器时钟 | 两个侦测器直接对脸，A 的背面接一盏灯，起振后排 2 刻脉冲往复 |
| 活塞门 | 2×2 四个粘性活塞分两列朝中间推，门块是石头，红石线绕到两列背后，输入每 40 刻翻转 |
| 红石线阵列 | 15×15 的红石线，一格中继器把输入放大成方波，边上接一盏灯，输入每 12 刻翻转 |
| 漏斗链 | 12 个漏斗朝东首尾相接，源头箱子 3 组物品，末端一个箱子，每 8 刻补货 |
| 物品分类机 | 4 个「漏斗 + 减法比较器 + 红石线」单元并排，上游一条 8 格漏斗链送物品，每 8 刻补货 |
| 比较器阵列 | 4 组「中继器 + 比较比较器 + 减法反馈比较器 + 红石灯」，输入每 10 刻翻转 |
| 互质时钟汇合 | 三个周期 6 / 10 / 14 刻的独立时钟各经一串中继器，汇到同一小片红石线和两个比较器上（全局周期 210 刻） |
| 熔炉阵列 | 4 个烧铁矿的熔炉，每个上下各一个漏斗，末端箱子，每 40 刻补货 |

「比较器阵列」原先叫「计数器」，改名是因为实测下来它的状态每 10 刻就重复，
其实是又一个时钟，不是状态很少重复的计数器。另摆了「互质时钟汇合」来检验
9.4 里关于计数器的那一行预测。

### 近似与影响方向

- **耗时含录制开销**。每条记录的纳秒是 `Instant::now()` 到触发结束，里面含记哈希、
  维护段快照、追加 Vec 的时间。所以「可省耗时占比」是**上限，偏高**。
- **段哈希只含方块状态**，不含光照、容器、红石记忆、计划刻。纯段哈希键把这些非方块
  状态读项按精确值补进键，光照在本次机器里不参与方块逻辑。段内无关方块变化会让
  段哈希失配（纯段哈希命中率偏低）。
- **读集合按调用顺序进键**，比集合语义更严，命中率偏低；好处是执行顺序不同的触发
  不会误命中。
- **只统计 4000 刻内见过的键**，第一次出现按「未命中」计，所以短机器的命中率略偏低。
  记录数增长曲线在 500 刻处就已平掉，这个偏差在几千刻的尺度上可忽略。
- **假世界是稀疏的 HashMap**，没有区块加载、发包、光照引擎和玩家。9.4 里「套用省不掉
  写、光照更新、发包」那部分开销不在测量范围内，因此「可省耗时」只对应「算」。
- **实体开销不在场景里**：漏斗上方没有可吸的物品实体，但漏斗 tick 仍会扫一遍实体表，
  按 9.3 的规则「碰了实体」就标记不可缓存。这是保守的，命中率偏低。
- **周期输入（翻红石块、补箱子）发生在触发边界之外**，不计入任何触发，也不进键。
  它只影响读到的状态。

### 录制不改变行为

九台机器各跑 4000 刻，开录制和不录制两份世界逐刻比方块状态、容器内容、红石记忆的
可见读、世界随机源种子、排队的计划刻：**0 刻不一致**。`mc-bamboo-blocks` 的单元测试也
覆盖了录制包装的转发（`recording::tests`）。方块 oracle 和 machine oracle 的基线不变
（见下）。

## 结果

每台跑 4000 刻。`不能缓存` 是严格口径；`命中率` 的分母是可缓存触发数；
`可省耗时` 是命中的那些触发的耗时之和占全部触发耗时的比例（精确键、严格口径）。
`记录数` = 运行里出现过的不同精确键数；`漏洞数` = 键相同但效果不同的次数。

| 机器 | 触发数 | 不能缓存 | 精确命中率 | 纯段哈希命中率 | 混合段哈希命中率 | 可省耗时（精确） | 记录数 | 漏洞数 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 中继器时钟 | 2490 | 0.0% | 99.5% | 99.4% | 99.4% | 99.3% | 12 | 0 |
| 侦测器时钟 | 3333 | 0.0% | 99.8% | 99.8% | 99.8% | 99.7% | 5 | 0 |
| 活塞门 | 702 | 100.0% | — | — | — | 0.0% | 0 | 0 |
| 红石线阵列 | 333 | 0.0% | 99.1% | 99.1% | 99.1% | 99.2% | 3 | 0 |
| 漏斗链 | 48000 | 100.0% | — | — | — | 0.0% | 0 | 0 |
| 物品分类机 | 48000 | 100.0% | — | — | — | 0.0% | 0 | 0 |
| 比较器阵列 | 3985 | 0.0% | 99.5% | 99.4% | 99.4% | 99.5% | 20 | 0 |
| 互质时钟汇合 | 5102 | 0.0% | 98.1% | 91.6% | 91.6% | 96.0% | 98 | 0 |
| 熔炉阵列 | 48000 | 66.7% | 0.0% | 0.0% | 0.0% | 0.0% | 16000 | 0 |

### 每台的分布、口径差异和增长曲线

#### 中继器时钟

- 触发 2490 次，全部是方块计划刻；平均每刻 0.6 次，有触发的刻 998 / 4000，
  每刻触发数 min 1 / p50 2 / p90 3 / max 3。
- 每次触发读位置数 p50 15 / p90 25 / p99 25；写位置数 p50 2 / p90 2 / p99 3；
  耗时 p50 45 µs / p90 139 µs / p99 161 µs（含录制开销）。
- 不能缓存 0 次；严格和乐观口径相同（没有时间读）。
- 严格精确 2478 / 2490（99.5%），纯段哈希 2476 / 2490（99.4%），
  混合段哈希同为 99.4%，可省耗时 99.3%。
- 不同精确键数：第 500 刻已经到 12，之后到 4000 刻一直是 12；两种段哈希都是 14。
- 平均每条记录读 33 项、写 1 项、涉及 3 个段，约 1368 字节；12 条缓存记录约 16 KiB。
  纯段哈希键的键部分平均 188 字节/条（精确键读集合 792 字节/条），约省 4 倍。

#### 侦测器时钟

- 触发 3333 次，全部是方块计划刻；有触发的刻 2000 / 4000。
- 读位置数 p50 12 / p90 16 / p99 16；写 p50 2 / p90 3 / p99 3；
  耗时 p50 119 µs / p90 211 µs / p99 237 µs。
- 不能缓存 0 次。三种键都是 3328 / 3333（99.8%），可省 99.7%。
- 不同键数第 166 次触发时就到 5，之后不变；5 条记录约 6 KiB。
  纯段哈希键 243 字节/条。

#### 活塞门

- 触发 702 次：方块事件 100 次（占耗时 51.5%，平均读 195.2 项）、
  方块实体 tick 602 次（48.5%，平均读 33.7 项）。有触发的刻 298 / 4000。
- 读位置数 p50 1 / p90 40 / p99 42；写 p50 0 / p90 3 / p99 3；
  耗时 p50 0.8 µs / p90 186 µs / p99 223 µs。
- **严格口径全部不能缓存**：随机数 100 次（伸出 / 收回的方块事件取一次世界随机源算
  音高），时间 602 次（全部是 `minecraft:moving_piston` 的 ticker 读 `game_time()`），
  实体 0 次。
- 乐观口径下 602 次触发，精确命中 581 次（96.5%）、纯段哈希 579 次（96.2%），
  可省耗时约 47%，只要 21 / 23 条记录。修正前（键里还带着绝对时刻换算出来的
  `lastTicked - now` 和 ticker 的内部递增 id）乐观精确命中率是 **0.0%**：
  门明明周期性开合，键却因为时刻字段每刻都不同而全部不重复。
- 平均每条记录读 56 项、写 2 项、2 个段，约 2144 字节；纯段哈希键 466 字节/条。

#### 红石线阵列

- 触发 333 次，全部是计划刻；有触发的刻 333 / 4000。
- 一次触发就是整片线的一次功率重算：读位置数 1178（p50/p90/p99 相同），
  写位置数 183；耗时 p50 10.8 ms / p90 29.5 ms / p99 31.2 ms。
- 不能缓存 0 次。三种键都是 330 / 333（99.1%），可省 99.2%。
- 不同键数第 16 次触发时到 3，之后不变。
- 平均每条记录读 281250 项（`block_state` 每次被调用都记一笔，整片线的连锁更新会
  重复读同一格）、写 420 项、10 个段，约 9 MB；去重后 3 条缓存记录约 26 MiB。
  **纯段哈希键的键部分平均 27230 字节/条**，比精确键的读集合（约 9 MB/条）小
  三百多倍 —— 这正是 9.3 用段哈希的动机。真要做缓存时这一台要么按段存、
  要么直接走 9.6 的编译路线，不能按调用次数存读项。

#### 漏斗链

- 触发 48000 次，全部是方块实体 tick（12 个漏斗 × 4000 刻）；每刻 12 次。
- 读位置数 p50 1 / p90 9 / p99 13；写 p50 0 / p90 3 / p99 3；
  耗时 p50 333 ns / p90 7 µs / p99 65 µs。
- **严格口径 100% 不能缓存**：时间 48000 次（全部 `minecraft:hopper`），
  实体 5910 次（漏斗上方没有容器时会扫一遍实体表找掉落物），随机数 0 次。
- 乐观口径下 42090 次可缓存触发，三种键都是 41918 次命中（99.6%），
  可省耗时 21.7%，只要 172 条记录。但**严格口径下一条也缓存不了**。
- 平均每条记录读 17 项、写 1 项、1 个段，约 760 字节；纯段哈希键 398 字节/条。
  乐观命中率在修正绝对时刻前后都是 99.6%（漏掉的只是内部 id，不影响整体）。

- 不能缓存 32000 次（66.7%）：时间 32000 次（`minecraft:hopper`），
  实体 16000 次（熔炉 ticker 扫实体表找余料掉落），随机数 0 次。
- 严格口径 16000 次可缓存触发（熔炉 ticker），三种键都 **0.0% 命中**：烹饪进度每刻
  加一，键从不重复；不同键数随刻数线性增长（500 刻 2000 条，4000 刻 16000 条），
  16000 条记录约 19 MiB。
- 乐观口径 32000 次可缓存触发，三种键都是 1036 次命中（3.2%），可省 0.3%，
  30964 条记录。
- 平均每条记录读 32 项、写 1 项、1 个段，约 1272 字节；纯段哈希键 695 字节/条。

### 三种键的对比

| 机器 | 精确严格 | 纯段哈希严格 | 混合段哈希严格 | 纯段哈希减精确 |
| --- | --- | --- | --- | --- |
| 中继器时钟 | 99.5% | 99.4% | 99.4% | −0.1 pp |
| 侦测器时钟 | 99.8% | 99.8% | 99.8% | 0.0 pp |
| 红石线阵列 | 99.1% | 99.1% | 99.1% | 0.0 pp |
| 比较器阵列 | 99.5% | 99.4% | 99.4% | −0.1 pp |
| 互质时钟汇合 | 98.1% | 91.6% | 91.6% | −6.5 pp |
| 熔炉阵列 | 0.0% | 0.0% | 0.0% | 0.0 pp |

纯段哈希和混合段哈希的命中率在所有机器上都相同，但**纯段哈希键小得多**：
红石线阵列 27 KB/条 vs 精确读集合 9 MB/条（约 330 倍），互质时钟汇合
585 字节/条 vs 46 KB/条（约 79 倍），小机器也从 1.2–2.6 KB 降到 188–486 字节。
9.3 第一版「用段哈希省键的存储」的动机成立；代价是遇到「几条时钟在同一段里
交错写」这类机器会掉 6.5 个百分点的命中率。

### 乐观口径：时间字段修正前后

录制时方块实体内容的哈希里确实含有绝对游戏时刻换算出来的字段（`PistonMoving.lastTicked`、
`HopperEntity.tickedGameTime`）以及 ticker 的内部递增 id。把这些从乐观口径的键里排除后：

| 机器 | 乐观精确命中率（修正前 → 修正后） | 乐观纯段哈希（修正前 → 修正后） |
| --- | --- | --- |
| 活塞门 | 0.0% → 96.5% | 0.0% → 96.2% |
| 漏斗链 | 99.6% → 99.6% | 99.6% → 99.6% |
| 物品分类机 | 99.4% → 99.4% | 99.4% → 99.4% |

漏斗链和分类机本来就是「大部分漏斗 tick 空转」主导，内部 id 只让键多出极少几种，
修不修不影响整体；活塞门受影响最大：把时刻改成相对量确实能让周期性开合的门
命中，可省约 47% 的算的时间。**改时间表示对活塞门和漏斗类机器有明显收益，
对熔炉阵列没有（3.2%，因为烹饪进度本身就是单调增长的）。**

### 活塞门的随机数

100 次方块事件因为取了世界随机源而不能缓存，占这台机器 51.5% 的耗时。
取数在 `PistonBaseBlock.triggerEvent` 里：伸出和收回各调一次
`world.random().next_float()`，用来算活塞音效的音高
（伸出 `nextFloat() * 0.25 + 0.6`，收回 `nextFloat() * 0.15 + 0.6`），
**每次事件只取 1 个数**。这些数只决定音效参数，不决定方块状态；以后可以考虑把
「只用来决定音效参数的取数」连同音效一起记成效果的一部分重放，从而让这 100 次
事件也能进缓存。本次没有实现这一点。

### 钩子开销

`observe` 的默认实现是空的，但经过 `dyn Level` 是一次虚调用。按主代理的要求，
在**不套录制包装**的情况下，release，对中继器时钟和红石线阵列各跑 10000 刻，
每轮 5 次取最小，共 3 轮，和加钩子之前的提交 `790fc69` 对比：

| 机器 | 加钩子前最小 | 加钩子后最小 | 差 |
| --- | --- | --- | --- |
| 中继器时钟 | 73.985 ms | 73.633 ms | −0.5% |
| 红石线阵列 | 6439.710 ms | 6513.907 ms | +1.2% |

把每轮的最小值再取全局最小：加钩子前 73.985 / 6439.710 ms，加钩子后
73.633 / 6513.907 ms，分别 −0.5% 和 +1.2%。**都不到 2%**，在测量噪声范围内
（同一配置连续三轮的抖动本身就有 ±2%）。按约定不需要换成不走虚调用的做法。

## 结论

1. **纯信号电路值得做缓存**：中继器时钟、侦测器时钟、红石线阵列、比较器阵列、
   互质时钟汇合在 4000 刻里精确键命中率 98.1%–99.8%，可省 96.0%–99.7% 的
   「算」的时间，只需 3–98 条记录（6 KiB–4.3 MiB），记录数在头 500 刻就平掉。
   这是 §9.7 要的正信号。
2. **纯段哈希键（9.3 第一版）在大多数机器上只掉 0–0.1 个百分点，但键小 4–330 倍**，
   红石线阵列尤其明显（9 MB/条 → 27 KB/条）。遇到多条时钟在同一段里交错写的
   「互质时钟汇合」会掉 6.5 pp、记录数从 98 涨到 427。9.3 第一版可以作为默认，
   热点段里机器互相干扰时再细化到「每台机器一个哈希域」。
3. **读集合的漏洞数 0**：九台机器、约 16.4 万次触发、54 行命中率统计里，
   没有一次出现「键相同但效果不同」。这是「录到的读集合足以决定效果」的必要检查，
   过了。修正过程中发现的漏洞都是录制层自己的（把 ticker 内部 id、取事件、
   临时拿放方块实体误记成读/写），已全部修掉。
4. **时间读是最大的拦路虎**：漏斗链、物品分类机 100%，熔炉阵列 66.7%，活塞门 85.7%
   的触发只因为读了 `game_time()` 就不能缓存。读时间的行为只有 `minecraft:hopper`
   的 `tickedGameTime` 和 `minecraft:moving_piston` 的 `lastTicked`。把绝对时刻
   改成相对量后：活塞门 96.5%、漏斗链 99.6%、分类机 99.4% 命中，
   可省 47.2% / 21.7% / 28.1% 的算的时间；熔炉阵列只有 3.2%（烹饪进度单调增长）。
   **改时间表示对活塞门和漏斗类机器有明显收益，对熔炉没有。**
5. **活塞门按现在的规则完全用不上缓存**：移动中的活塞读时间、伸出 / 收回各取一次
   世界随机源算音效音高，100% 落在不能缓存里。把这两点都处理掉之后它其实是
   96.5% 命中的周期机器。9.4 把活塞门列进「命中率高」与本次的严格口径不符，
   但状态周期性这一半是对的。
6. **熔炉阵列是内存反例**：严格口径 16000 条记录、曲线随刻数线性增长、
   约 19 MiB，命中率 0%。它正是 9.3 里「长期命中不了的停止录制」该拦住的那类。
7. **9.4 关于计数器的预测还没被真正检验**：互质时钟汇合让记录数涨了一个数量级
   （方向对上「占内存」），但精确命中率仍有 98.1%。要检验这一行得摆一台真正
   单调累加、局部状态很少回到同一组值的电路。
8. 本实验只量「算」，量不到 9.4 提醒的「套用省不掉写、光照更新、发包」。
   决定做不做缓存前，这部分的开销还得单独量。
9. `observe` 钩子的虚调用开销在 release、10000 刻、取最小的基准里不到 2%，
   不需要改成不走虚调用的方案。
